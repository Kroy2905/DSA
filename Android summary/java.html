OOP Fundamentals

Q1Explain the four pillars of OOP — encapsulation, inheritance, polymorphism, abstractionEasy

Encapsulation hides internal state behind methods so invariants can't be violated from outside. Inheritance lets a class reuse and extend another's fields/behavior. Abstraction exposes "what" an object does while hiding "how". Polymorphism lets the same call site behave differently depending on the actual runtime type.

// Encapsulation: hide internal state behind methods
public class BankAccount {
    private double balance; // private = encapsulated

    public void deposit(double amount) {
        if (amount > 0) balance += amount; // controlled access
    }

    public double getBalance() { return balance; }
}

// Inheritance: SavingsAccount reuses BankAccount's state/behavior
public class SavingsAccount extends BankAccount {
    private double interestRate;

    public void applyInterest() {
        deposit(getBalance() * interestRate); // reuse via superclass
    }
}

// Abstraction: expose "what", hide "how" via an abstract class
public abstract class Shape {
    abstract double area(); // no implementation here
}

// Polymorphism: same call, different behavior at runtime
public class Circle extends Shape {
    double radius = 2.0;
    @Override
    double area() { return Math.PI * radius * radius; }
}

Shape s = new Circle(); // reference type Shape, object type Circle
s.area(); // JVM dispatches to Circle.area() at runtime
Q2Interface vs abstract class — and what changed with Java 8+ default/static methodsMedium 
interface Vehicle {
    void start(); // implicitly public abstract

    default void honk() { // Java 8+: default method, HAS a body
        System.out.println("Beep!");
    }

    static Vehicle create() { // Java 8+: static factory method
        return new Car();
    }
}

abstract class AbstractVehicle implements Vehicle {
    protected int speed; // abstract classes CAN hold instance state

    abstract void accelerate(); // still abstract

    void brake() { speed = 0; } // concrete method with logic
}
  • Multiple inheritance: a class can implements many interfaces but extends only one class.
  • State: interfaces can only hold public static final constants; abstract classes can hold real mutable fields.
  • Constructors: abstract classes can have constructors (run via super()); interfaces cannot.
  • Default methods let library authors add new methods to an interface without breaking every existing implementer.
Q3Method overloading vs overriding — compile-time vs runtime polymorphismEasy 
class Calculator {
    // Overloading: same name, different parameter list — resolved at COMPILE time
    int add(int a, int b) { return a + b; }
    double add(double a, double b) { return a + b; }
    int add(int a, int b, int c) { return a + b + c; }
}

class Animal {
    void sound() { System.out.println("Some sound"); }
}

class Dog extends Animal {
    @Override
    void sound() { System.out.println("Bark"); } // Overriding: resolved at RUNTIME
}

Animal a = new Dog();
a.sound(); // prints "Bark" — dynamic dispatch via the method table (vtable)

Overload resolution is decided purely from the declared argument types at compile time; overriding is decided from the object's actual runtime type via dynamic (virtual) dispatch. Overriding also requires the same signature and a covariant (or same) return type, and can't reduce visibility or add new checked exceptions.

Q4Constructors and constructor chaining with this() and super()Easy 
class Person {
    String name;
    int age;

    Person() {
        this("Unknown", 0); // must be the FIRST statement — delegates to another ctor
    }

    Person(String name, int age) {
        this.name = name;
        this.age = age;
    }
}

class Employee extends Person {
    double salary;

    Employee(String name, int age, double salary) {
        super(name, age); // must be the FIRST statement — calls the parent ctor
        this.salary = salary;
    }
    // If you don't call super() explicitly, the compiler inserts a no-arg super() call
    // this() vs super(): 'this' reaches another constructor in the SAME class;
    // 'super' reaches the immediate PARENT class — a constructor can call only one of them
}
Q5Static vs instance members — memory, access, and initialization orderEasy 
class Counter {
    static int totalCount = 0;   // ONE copy shared by all instances, lives in the Metaspace
    int instanceId;               // a separate copy per object, lives on the heap with it

    static {
        System.out.println("static block — runs ONCE, at class-load time");
    }

    {
        System.out.println("instance block — runs EVERY time, before the constructor body");
    }

    Counter() {
        totalCount++;             // shared state — visible to every instance
        instanceId = totalCount;  // per-object state
    }

    static void printTotal() { // static method: no 'this', can't touch instance members directly
        System.out.println(totalCount);
    }
}

Initialization order: static fields/blocks run once, in declaration order, the first time the class is loaded — before any instance exists. Instance fields/blocks run every time an object is constructed, in declaration order, immediately before the constructor body executes.

Q6The final keyword — final variable, method, and classEasy 
final class ImmutablePoint {       // final class: cannot be subclassed at all
    final int x, y;                // final field: must be assigned exactly once

    ImmutablePoint(int x, int y) {
        this.x = x;
        this.y = y;
    }

    final int getX() { return x; } // final method: cannot be overridden by subclasses
}

final List<String> names = new ArrayList<>(); // the REFERENCE is final, not the contents
names.add("Alice"); // legal — mutating the object, not reassigning the variable
// names = new ArrayList<>(); // ERROR: cannot reassign a final variable
A final reference only freezes what the variable points to — the referenced object can still be fully mutable. Don't confuse "final" with "immutable"; true immutability requires the class itself to never expose mutating methods (see records, Q49).
Q7Access modifiers (public/protected/default/private) and package visibilityEasy
  • private: visible only within the declaring class (including inner classes of it).
  • default (package-private): no modifier written — visible only within the same package.
  • protected: visible within the same package, plus subclasses in other packages (accessible only through inheritance, not via an arbitrary instance).
  • public: visible from anywhere.
package com.example.model;

public class User {
    private String ssn;         // only User itself
    String nickname;                // package-private: only com.example.model
    protected String email;    // package + subclasses elsewhere
    public String username;     // everyone
}

Object Class & Core Semantics

Q8What is the difference between == and .equals()?Easy 
String a = new String("hello");
String b = new String("hello");
a == b;        // false — different objects on the heap
a.equals(b);   // true — String overrides equals() to compare content

Integer x = 1000, y = 1000;
x == y;        // false — outside the Integer cache range, two distinct boxed objects
x.equals(y);   // true

int p = 5, q = 5;
p == q;        // true — primitives always compare by VALUE, no boxing involved

== on reference types always compares object identity (same memory address); it never calls any method. .equals() is a regular method that a class can override to compare logical/structural content — Object's default implementation just falls back to ==.

Q9The equals()/hashCode() contract — why breaking it corrupts HashMap/HashSetMedium

The contract: if a.equals(b) is true, then a.hashCode() == b.hashCode() must also be true. The reverse isn't required — unequal objects are allowed to share a hash code (a collision), it's just slower to resolve.

class BadKey {
    int id;
    BadKey(int id) { this.id = id; }

    @Override
    public boolean equals(Object o) {
        if (!(o instanceof BadKey)) return false;
        return ((BadKey) o).id == id;
    }
    // hashCode() NOT overridden — still uses Object's identity-based hash!
}

Map<BadKey, String> map = new HashMap<>();
map.put(new BadKey(1), "value");
map.get(new BadKey(1)); // returns null! Different hashCode -> lands in a different bucket

class GoodKey {
    int id;
    GoodKey(int id) { this.id = id; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof GoodKey)) return false;
        return ((GoodKey) o).id == id;
    }

    @Override
    public int hashCode() {
        return Objects.hash(id); // consistent with equals()
    }
}
Silent corruption, not a crash: breaking the contract doesn't throw anything. The object simply lands in the wrong bucket, so get()/contains() quietly return wrong results — one of the nastiest classes of bug to track down.
Q10toString() and clone() — shallow vs deep copyEasy 
class Point {
    int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }

    @Override
    public String toString() { return "Point(" + x + ", " + y + ")"; } // used by println, +, debuggers
}

class Container implements Cloneable {
    int[] data;

    @Override
    protected Object clone() throws CloneNotSupportedException {
        Container copy = (Container) super.clone(); // shallow copy: copies field references as-is
        copy.data = data.clone();                    // manual deep copy of the mutable array field
        return copy;
    }
}

A default (shallow) clone() copies each field's bit pattern — primitives are duplicated, but reference fields still point at the same nested objects as the original. A deep copy requires manually cloning every mutable nested object too. In practice, most modern codebases avoid Cloneable entirely — it's a checked-exception-throwing, oddly-typed, constructor-skipping API — and prefer a copy constructor, a static factory, or a Builder instead.

Q11String immutability and the String pool — what does intern() do?Medium 
String a = "hello";              // literal — placed in the String pool
String b = "hello";              // reuses the SAME pooled object
String c = new String("hello");  // forces a NEW object on the heap, outside the pool
String d = c.intern();           // returns the pooled reference for this content

a == b;        // true — same pooled reference
a == c;        // false — c is a distinct heap object
a == d;        // true — intern() looked it up in (or added it to) the pool

Why String is immutable:

  • Pool safety: many references can safely share one pooled instance only because nobody can mutate it out from under the others.
  • Security: class names, file paths, and network hosts are often passed as String; immutability prevents them from changing after being validated.
  • Hash caching: String.hashCode() is computed once and cached, since the value can never change — makes it a very cheap HashMap key.
  • Thread safety: an immutable object can be freely shared across threads with no synchronization.
Q12String vs StringBuilder vs StringBufferEasy 
String s = "a";
for (int i = 0; i < 5; i++) {
    s += i; // creates a NEW String object every iteration — O(n^2) for n concatenations
}

StringBuilder sb = new StringBuilder();
for (int i = 0; i < 5; i++) {
    sb.append(i); // mutates an internal char[] buffer — O(n) amortized, NOT thread-safe
}

StringBuffer sbuf = new StringBuffer(); // same API as StringBuilder
sbuf.append("x");                        // but every method is synchronized — thread-safe, slower

Use String for fixed/rarely-changed text, StringBuilder for single-threaded mutation (loops, building output), and StringBuffer only when the same builder is genuinely shared across threads — which is rare enough that most code should just use StringBuilder.

Q13Autoboxing/unboxing pitfalls, Integer caching, and instanceof pattern matchingMedium 
Integer a = 100, b = 100;
a == b;          // true — both fall inside the cached range [-128, 127]

Integer c = 200, d = 200;
c == d;          // false — outside the cache, two distinct Integer objects

Integer maybeNull = null;
int crash = maybeNull; // NullPointerException — auto-unboxing null throws NPE

int total = 0;
for (Integer n : List.of(1, 2, 3)) total += n; // unboxing happens on every '+='

// instanceof pattern matching (Java 16+): binds the cast variable directly
Object obj = "hello";
if (obj instanceof String str) {       // no separate cast statement needed
    System.out.println(str.length()); // 'str' is already a String here
}
Why the cache exists: the JVM pre-creates and reuses Integer objects for -128..127 (the range most programs use most often) purely as a memory optimization. Relying on == for boxed types is a bug waiting to surface the moment a value exceeds 127 — always use .equals() for boxed-type comparison.

Exception Handling

Q14Checked vs unchecked exceptions and the exception hierarchyEasy 
Throwable
├── Error                     // OutOfMemoryError, StackOverflowError — not meant to be caught/recovered from
└── Exception
    ├── IOException, SQLException, ...     // CHECKED — compiler forces you to catch or declare (throws)
    └── RuntimeException                    // UNCHECKED — compiler does NOT enforce handling
        ├── NullPointerException
        ├── IllegalArgumentException
        └── IndexOutOfBoundsException
// Checked: compiler forces you to handle or declare it
void readFile(String path) throws IOException {
    FileReader fr = new FileReader(path); // IOException is checked
}

// Unchecked: usually signals a programming bug, not a recoverable external condition
void divide(int a, int b) {
    int result = a / b; // ArithmeticException is unchecked
}

Checked exceptions represent conditions a well-written caller could reasonably recover from (a missing file, a network timeout). Unchecked exceptions typically represent bugs (a null you shouldn't have passed, an index that was never valid) — forcing every caller to declare or catch them would just add boilerplate without real safety.

Q15try-catch-finally execution order — what happens when finally meets return?Medium 
static int test() {
    try {
        return 1;
    } finally {
        System.out.println("finally runs even though try already returned");
        // return 2; // if uncommented, this SWALLOWS the try's return value — finally wins!
    }
}
// test() returns 1

static int trap() {
    int x = 10;
    try {
        return x;      // the value of x (10) is copied/saved BEFORE finally runs
    } finally {
        x = 20;        // too late — the returned value was already captured
    }
}
// trap() returns 10, NOT 20
finally always runs — even after a return, break, continue, or an uncaught exception in try/catch — except if the JVM itself exits (System.exit()) or crashes. But a return or throw written directly inside finally silently discards whatever the try/catch was about to return or throw. Treat that as a bug pattern to avoid, not a feature.
Q16try-with-resources and AutoCloseableMedium 
class DbConnection implements AutoCloseable {
    DbConnection() { System.out.println("opened"); }

    @Override
    public void close() { System.out.println("closed"); } // called automatically, even on exception
}

try (DbConnection conn = new DbConnection();
     DbConnection conn2 = new DbConnection()) { // multiple resources: closed in REVERSE order
    // use conn, conn2
} // conn2.close() runs, then conn.close() — no explicit finally block needed

Any class implementing AutoCloseable (or the older, IO-specific Closeable) can be declared inside the parentheses of a try. The compiler guarantees close() runs, in reverse declaration order, no matter how the block exits. If the body throws and close() also throws, the close-time exception is attached to the original as a suppressed exception (retrievable via getSuppressed()) instead of masking it.

Q17Custom exceptions, exception chaining, and why finalize() is deprecatedMedium 
class InsufficientFundsException extends Exception { // a checked, domain-specific exception
    public InsufficientFundsException(String message, Throwable cause) {
        super(message, cause); // chaining: preserves the original low-level cause
    }
}

try {
    transfer();
} catch (SQLException e) {
    throw new InsufficientFundsException("Transfer failed", e); // wrap, don't swallow
}
// e.getCause() on the new exception still returns the original SQLException + its stack trace

finally vs finalize() vs try-with-resources: finally is a deterministic block that always runs right after try/catch. finalize() was Object's hook for the garbage collector to run cleanup before reclaiming an object — but it's deprecated since Java 9 and removed in Java 18, because it runs on an unpredictable GC thread at an unpredictable time (or may never run at all), can resurrect "dead" objects, and can hang the collector. try-with-resources (Q16) is the deterministic, immediate replacement for cleanup logic that used to live in finalize().

Collections Framework

Q18ArrayList vs LinkedList — internals and when to use whichMedium

Quick hierarchy refresher: Collection branches into List (ArrayList, LinkedList, Vector), Set (HashSet, LinkedHashSet, TreeSet), and Queue/Deque (LinkedList, ArrayDeque, PriorityQueue). Map is a separate hierarchy — it does not extend Collection at all, since it stores key-value pairs, not single elements.

List<Integer> arrayList = new ArrayList<>(); // backed by a resizable Object[] array
arrayList.get(500);      // O(1) — direct index access
arrayList.add(x);        // O(1) amortized; occasionally O(n) when the array must grow & copy
arrayList.add(0, x);     // O(n) — shifts every following element right

List<Integer> linkedList = new LinkedList<>(); // backed by a doubly-linked list of nodes
linkedList.get(500);           // O(n) — must walk from head or tail
linkedList.addFirst(x);        // O(1) — just relinks a couple of pointers
linkedList.addLast(x);         // O(1)

Use ArrayList by default — it has better cache locality and is faster for nearly all real workloads, including most "insert in the middle" cases at typical sizes. Reach for LinkedList only when you need O(1) insertion/removal at both ends with no random access (e.g. implementing a Deque), and even then ArrayDeque usually wins.

Q19HashMap internals — buckets, hashing, resize, and Java 8+ treeificationHard 
// Simplified internal structure
class HashMap<K,V> {
    Node<K,V>[] table; // array of buckets, default capacity 16

    static class Node<K,V> {
        final int hash;
        final K key;
        V value;
        Node<K,V> next; // linked list for collisions within one bucket
    }
}

// put(key, value):
// 1. hash = key.hashCode() ^ (hash >>> 16)     -- spreads high bits into low bits
// 2. bucketIndex = hash & (table.length - 1)    -- fast modulo since capacity is a power of 2
// 3. bucket empty -> insert a new Node
// 4. collision -> walk the bucket's list/tree, replace value if a key.equals() match is found,
//    otherwise append
  • Load factor (default 0.75): once size > capacity * loadFactor, the table resizes — capacity doubles and every entry is rehashed into the new table.
  • Treeification (Java 8+): if a single bucket's linked list grows to 8 nodes and the table capacity is at least 64, that bucket converts to a red-black tree — worst-case lookup becomes O(log n) instead of O(n). It untreeifies back to a list if the bucket shrinks to 6 nodes.
Complexity summary: average-case get/put is O(1). Worst case (many collisions) is O(n) pre-Java-8 and O(log n) from Java 8 onward, thanks to treeification.
Q20HashMap vs Hashtable vs ConcurrentHashMap vs LinkedHashMap vs TreeMapMedium
  • HashMap: not synchronized, allows one null key and multiple null values, no ordering guarantee, best general-purpose performance.
  • Hashtable: legacy (JDK 1.0), synchronizes every method with one coarse lock, disallows null keys/values — effectively obsolete, kept only for backward compatibility.
  • ConcurrentHashMap: thread-safe via fine-grained locking / CAS on individual bins (not one global lock), disallows null keys/values, iterators are weakly consistent (never throw ConcurrentModificationException), far better concurrent throughput than Hashtable.
  • LinkedHashMap: a HashMap plus a doubly-linked list threading through the entries to preserve insertion order (or access order) — the standard base for building an LRU cache.
  • TreeMap: a red-black tree keeping keys in sorted order (natural ordering or a supplied Comparator), O(log n) operations, implements NavigableMap (floorKey, ceilingKey, firstKey, ...).
// LinkedHashMap as an LRU cache
class LruCache<K,V> extends LinkedHashMap<K,V> {
    private final int maxSize;

    LruCache(int maxSize) {
        super(16, 0.75f, true); // accessOrder = true -> re-orders on get(), not just put()
        this.maxSize = maxSize;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K,V> eldest) {
        return size() > maxSize; // evict the least-recently-used entry automatically
    }
}
Q21Fail-fast vs fail-safe iterators, and Iterator vs ListIteratorMedium 
List<Integer> list = new ArrayList<>(List.of(1, 2, 3));
for (Integer n : list) {
    if (n == 2) list.remove(n); // ConcurrentModificationException — fail-fast!
}
// ArrayList's iterator tracks a modCount; a structural change made OUTSIDE the
// iterator itself causes the next next()/hasNext() call to throw

Map<String, String> map = new ConcurrentHashMap<>();
for (String key : map.keySet()) {
    map.put("newKey", "value"); // NO exception — fail-safe, iterates a weakly-consistent view
}

List<Integer> nums = new ArrayList<>(List.of(1, 2, 3));
ListIterator<Integer> it = nums.listIterator();
while (it.hasNext()) {
    int val = it.next();
    it.set(val * 2);      // ListIterator supports set()/add(), plus backward traversal
}

Iterator is forward-only with hasNext()/next()/remove(), and works on any Collection. ListIterator (available only on List) is bidirectional (hasPrevious()/previous()) and additionally supports set() and add() during traversal.

Q22Comparable vs ComparatorMedium 
class Employee implements Comparable<Employee> { // natural ordering — exactly ONE per class
    int salary;

    @Override
    public int compareTo(Employee other) {
        return Integer.compare(this.salary, other.salary); // ascending by salary
    }
}
Collections.sort(employees); // uses compareTo() automatically

Comparator<Employee> byName = Comparator.comparing(e -> e.name); // external — as many as you like
Comparator<Employee> byNameThenAge = byName.thenComparing(e -> e.age);
employees.sort(byNameThenAge.reversed());

Comparable defines a class's single "natural" ordering, implemented inside the class itself. Comparator is an external strategy object — use it whenever you need multiple orderings, or need to sort a type you don't own/can't modify.

Generics

Q23Type erasure and its consequencesMedium 
List<String> strings = new ArrayList<>();
List<Integer> ints = new ArrayList<>();
strings.getClass() == ints.getClass(); // true! Both are just ArrayList at runtime

// Consequence: no runtime type checks on a generic type parameter
// if (list instanceof List<String>) {} // ERROR: illegal generic type for instanceof

// Consequence: overloading on erased types collides
// void process(List<String> l) {}
// void process(List<Integer> l) {} // ERROR: identical erasure -> duplicate method

public class Box<T> {
    private T value;
    public T get() { return value; }
    // compiled bytecode roughly becomes:
    // public class Box { private Object value; public Object get() { return value; } }
    // with compiler-inserted casts at every call site
}

Generics exist only at compile time, for type-checking; the JVM sees raw, erased types (bounded by their first bound, or Object if unbounded). This is why generics were "free" to retrofit onto the JVM in Java 5 without a bytecode format change — but it also means you can never reliably ask "what T is this at runtime" without external help.

Q24Bounded type parameters and wildcards — the PECS principleMedium 
// Bounded type parameter: T must be a Number or a subtype of it
static <T extends Number> double sum(List<T> list) {
    double total = 0;
    for (T n : list) total += n.doubleValue(); // Number's methods are now available
    return total;
}

// Upper-bounded wildcard (? extends): a PRODUCER — safe to READ, not to write
static double sumAll(List<? extends Number> list) {
    double total = 0;
    for (Number n : list) total += n.doubleValue(); // fine — reading as Number
    // list.add(1); // ERROR — compiler can't prove which exact subtype it holds
    return total;
}

// Lower-bounded wildcard (? super): a CONSUMER — safe to WRITE, reads come out as Object
static void addNumbers(List<? super Integer> list) {
    list.add(1);          // fine — an Integer fits any supertype's slot
    // Integer x = list.get(0); // ERROR — could really be a List<Number> or List<Object>
}

PECS: Producer extends, Consumer super. If a parameterized collection only feeds values out to you, use ? extends. If you only push values into it, use ? super. If you do both, don't use a wildcard at all.

Multithreading & Concurrency

Q26Thread vs Runnable vs CallableMedium 
class MyThread extends Thread {           // extends Thread: uses up your one shot at extending a class
    @Override
    public void run() { System.out.println("running"); }
}

class MyRunnable implements Runnable {     // implements Runnable: preferred — free to extend something else too
    @Override
    public void run() { System.out.println("running"); }
}
new Thread(new MyRunnable()).start();

Callable<Integer> task = () -> {           // Callable: CAN return a value AND throw checked exceptions
    return 42;
};
ExecutorService executor = Executors.newSingleThreadExecutor();
Future<Integer> future = executor.submit(task);
future.get(); // 42 — blocks the caller until the result is ready

run() returns void and can't throw checked exceptions; call() returns a value and can throw. Prefer Runnable/Callable submitted to an ExecutorService over directly extending Thread — it decouples the task from the execution mechanism and lets you reuse thread pools.

Q27Thread lifecycle statesEasy
  • NEW: created but start() not yet called.
  • RUNNABLE: executing, or eligible to run and waiting for CPU time from the OS scheduler.
  • BLOCKED: waiting to acquire an intrinsic lock (a synchronized block/method held by another thread).
  • WAITING: waiting indefinitely for another thread's signal — via Object.wait(), Thread.join(), or LockSupport.park() with no timeout.
  • TIMED_WAITING: same as WAITING but with a timeout — sleep(ms), wait(ms), join(ms).
  • TERMINATED: run() has completed (normally or via an uncaught exception).
Thread t = new Thread(() -> {});
t.getState();  // Thread.State.NEW
t.start();
t.getState();  // Thread.State.RUNNABLE (typically)
Q28The synchronized keyword — method vs block, intrinsic locks and monitorsHard 
class Counter {
    private int count = 0;

    public synchronized void increment() {  // method-level lock: acquires 'this' as the monitor
        count++;
    }

    public void incrementBlock() {
        synchronized (this) {                // block-level lock: same monitor, finer-grained scope
            count++;
        }
    }

    public static synchronized void staticMethod() { // locks the Class object itself, not an instance
        // ...
    }
}

Every Java object has an associated intrinsic lock (monitor). Entering a synchronized region acquires that object's monitor; leaving it (normally or via exception) releases it automatically. The lock is reentrant — a thread already holding it can enter another synchronized block guarded by the same monitor without deadlocking itself. Block-level synchronization is generally preferred over method-level because it locks the smallest critical section necessary, reducing contention.

Q29volatile and the Java Memory Model — visibility vs atomicityHard 
class Flag {
    private volatile boolean running = true; // guarantees VISIBILITY across threads

    public void stop() { running = false; }   // the write is immediately visible to other threads

    public void run() {
        while (running) {                     // without volatile, a thread might cache 'running' in a
            // do work                         // register/CPU cache and loop forever, never seeing the write
        }
    }
}

// volatile does NOT guarantee atomicity for compound actions:
private volatile int counter = 0;
counter++; // NOT atomic! read-modify-write is 3 separate steps — still needs
           // synchronized or an Atomic class (Q35) even though it's volatile

The Java Memory Model (JMM) defines when writes by one thread are guaranteed to become visible to another. Without synchronization, the compiler, CPU, and cache hierarchy are all free to reorder or locally cache reads/writes for performance — perfectly legal for single-threaded correctness, but dangerous across threads. volatile establishes a happens-before relationship: every write to a volatile field happens-before every subsequent read of it, and the JVM disables reordering around it. The same happens-before guarantee is also established by entering/exiting a synchronized block and by Thread.start()/Thread.join().

Rule of thumb: use volatile for a simple flag or a "publish this reference once" pattern. The moment you need to read-then-write based on the current value, you need real mutual exclusion (synchronized or an Atomic* class), because visibility alone doesn't prevent a race between two threads' read-modify-write sequences.
Q30wait()/notify()/notifyAll() vs modern concurrency utilitiesHard 
class SharedBuffer {
    private final Object lock = new Object();
    private int data;
    private boolean available = false;

    void produce(int value) {
        synchronized (lock) {
            while (available) {          // ALWAYS a while loop, never 'if' — guards against spurious wakeups
                try { lock.wait(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            }
            data = value;
            available = true;
            lock.notifyAll();            // wake ALL waiters — plain notify() risks missed/starved signals
        }
    }
}

// Modern alternative — prefer this in real code:
BlockingQueue<Integer> queue = new LinkedBlockingQueue<>();
queue.put(value);   // blocks internally if full — no manual wait/notify needed
queue.take();        // blocks internally if empty

wait()/notify()/notifyAll() must be called from inside a synchronized block on that exact object, or the JVM throws IllegalMonitorStateException. They're low-level and easy to misuse; java.util.concurrent (BlockingQueue, CountDownLatch, Semaphore, CompletableFuture, locks/conditions) provides the same coordination with far fewer footguns and should be the default choice today.

Q31Deadlock — causes, a code example, and preventionHard 
Object lockA = new Object();
Object lockB = new Object();

Thread t1 = new Thread(() -> {
    synchronized (lockA) {
        sleep(100);
        synchronized (lockB) { /* ... */ }   // t1 waits for lockB, held by t2
    }
});

Thread t2 = new Thread(() -> {
    synchronized (lockB) {
        sleep(100);
        synchronized (lockA) { /* ... */ }   // t2 waits for lockA, held by t1 -> DEADLOCK
    }
});

Deadlock requires all four Coffman conditions at once: mutual exclusion (locks aren't shareable), hold-and-wait (a thread holds one lock while waiting for another), no preemption (a lock can't be forcibly taken away), and circular wait (a cycle of threads each waiting on the next).

Prevention: always acquire multiple locks in the same fixed global order across all threads (breaks circular wait); use tryLock(timeout) from java.util.concurrent.locks to back off instead of blocking forever; keep critical sections small and avoid nested locks where possible; prefer higher-level, deadlock-resistant utilities (concurrent collections, executors) over hand-rolled locking.

Q35Atomic classes (AtomicInteger) vs synchronizedMedium 
private AtomicInteger counter = new AtomicInteger(0);

void increment() {
    counter.incrementAndGet();      // lock-free — uses CAS (compare-and-swap) at the hardware level
}

// vs the synchronized version — an OS-level monitor lock, heavier under contention
private int syncCounter = 0;
synchronized void incrementSync() { syncCounter++; }

// CAS loop, conceptually:
int prev, next;
do {
    prev = counter.get();
    next = prev + 1;
} while (!counter.compareAndSet(prev, next)); // retry if another thread won the race

Atomic classes are typically faster under low-to-moderate contention because they never block a thread or trigger an OS context switch — a losing thread just retries the CAS. synchronized is simpler to reason about when multiple related fields must change together as one atomic unit, since a CAS only protects a single variable.

Q37Lambda expression syntax and the effectively-final capture ruleMedium

Q39Stream API basics — pipeline, laziness, intermediate vs terminal operationsMedium 
List<String> names = List.of("Alice", "Bob", "Charlie", "Dave");

List<String> result = names.stream()
    .filter(n -> n.length() > 3)   // intermediate — LAZY, does nothing yet
    .map(String::toUpperCase)      // intermediate — LAZY
    .sorted()                       // intermediate — LAZY
    .collect(Collectors.toList()); // TERMINAL — triggers the whole pipeline to actually run, once

int totalLength = names.stream()
    .mapToInt(String::length)
    .reduce(0, Integer::sum);       // terminal — folds all elements into a single result

Intermediate operations (filter, map, sorted, peek) are lazy — they just build up a pipeline description and return a new Stream. Nothing actually executes until a terminal operation (collect, forEach, reduce, count) is called, at which point the whole pipeline runs element-by-element in a single pass.

A Stream is single-use — calling a terminal operation twice on the same stream throws IllegalStateException. Streams also don't mutate their source collection; they produce new results.

JVM & Memory

Q41JVM architecture, and how it relates to ART on AndroidHard
  • Class Loader Subsystem: loads .class files via Bootstrap → Extension/Platform → Application class loaders (delegation model), then links (verify, prepare, resolve) and initializes each class.
  • Runtime Data Areas: the Method Area/Metaspace (class metadata, static fields), the Heap (all objects, shared across threads), per-thread Stacks (frames of local variables/call state), PC registers, and native method stacks.
  • Execution Engine: an interpreter runs bytecode directly; the JIT (Just-In-Time) compiler profiles hot methods and compiles them to native machine code for speed; the garbage collector reclaims unreachable heap objects.

Relation to ART: Android apps don't run on a standard JVM at all. Source compiles to .class files, which are then converted to DEX bytecode — a register-based instruction set (vs the JVM's stack-based one), optimized for a constrained mobile environment. ART (Android Runtime, which replaced Dalvik starting with Android 5.0) executes that DEX code using a hybrid of AOT (ahead-of-time) compilation at install/idle time and JIT profiling at runtime (since Android 7/Nougat) to balance install time, storage, and steady-state performance. The Java language semantics, garbage collection concepts, and memory model you're tested on all still apply — only the bytecode format and runtime differ.

Q42Stack vs heap memoryMedium 
void method() {
    int localVar = 5;               // primitive -> lives on the STACK frame for this call
    Person p = new Person("Alice"); // 'p' (the reference) is on the stack;
                                     // the actual Person OBJECT is on the HEAP
} // when method() returns, its whole stack frame is popped instantly — localVar and 'p' vanish;
  // the Person object on the heap survives until the GC decides nothing references it anymore

Stack

Per-thread, LIFO. Stores local variables, references, and call frames. Extremely fast to allocate/deallocate (just move a pointer). Fixed size per thread — exceeding it throws StackOverflowError (classic cause: unbounded recursion).

Heap

Shared across all threads. Stores every object and array. Managed by the garbage collector, larger and slower to allocate than the stack. Exhausting it throws OutOfMemoryError.

Q43Garbage collection basics — generational GC and common algorithmsHard

GC is built on the generational hypothesis: most objects die young, so it's cheaper to collect young objects frequently and cheaply, and old objects rarely.

  • Young Generation (Eden + two Survivor spaces, S0/S1): new objects are allocated in Eden. A Minor GC runs often, is fast, and uses a copying algorithm — live objects are copied between Eden/Survivor spaces; objects that survive enough cycles get promoted to the Old Generation.
  • Old Generation: holds long-lived objects. A Major/Full GC runs far less often but is much more expensive since it scans a much larger heap region.

Common collectors: Serial (single-threaded, small heaps); Parallel (multi-threaded, throughput-focused, tolerates longer pauses); CMS (Concurrent Mark-Sweep — low pause but deprecated/removed, suffered from fragmentation); G1 (Garbage First — the default since Java 9, splits the heap into regions and prioritizes collecting the regions with the most garbage first, aiming for predictable pause-time targets); ZGC/Shenandoah (very low, near-constant pause times, designed to scale to huge multi-GB heaps concurrently with the application).

Q47Annotations basics, and how reflection uses themMedium 
@Retention(RetentionPolicy.RUNTIME)    // must be RUNTIME to be readable via reflection
@Target(ElementType.METHOD)
@interface Benchmark { }               // a custom annotation definition

class Service {
    @Benchmark
    void slowMethod() { /* ... */ }
}

// Reflection reads the annotation and invokes the method dynamically
for (Method m : Service.class.getDeclaredMethods()) {
    if (m.isAnnotationPresent(Benchmark.class)) {
        long start = System.nanoTime();
        m.invoke(new Service());               // dynamic invocation — bypasses compile-time type checks
        System.out.println(System.nanoTime() - start);
    }
}

Built-in annotations like @Override, @Deprecated, @SuppressWarnings, and @FunctionalInterface are checked by the compiler itself. Custom annotations are inert metadata by default — they only do something once a tool reads them, either at compile time (an annotation processor generating code, e.g. Dagger/Room) or at runtime via reflection (e.g. Gson, older Retrofit). Reflection is powerful but costly: it skips JIT inlining, performs extra security/access checks, boxes primitives, and breaks encapsulation when combined with setAccessible(true) — which is exactly why performance-sensitive Android libraries increasingly favor compile-time codegen over runtime reflection.

Q49Records as immutable data carriers (vs Kotlin data classes), and switch expressionsMedium 
// Record (Java 16+ stable): auto-generates constructor, accessors, equals/hashCode/toString
record Point(int x, int y) { }               // immutable by construction — fields are implicitly final

Point p = new Point(1, 2);

p.equals(new Point(1, 2)); // true — structural equality, like Kotlin's data class

        if (start > end) throw new IllegalArgumentException("invalid range");
    }
}

    case MONDAY, FRIDAY, SUNDAY -> "short";
    case TUESDAY -> "long";
    default -> {
        String s = "other";

};

Compared to a Kotlin data class: both auto-generate equals()/hashCode()/toString() and per-field accessors. A classic switch statement falls through by default and returns nothing; a switch expression is exhaustiveness-checked by the compiler for enums and produces a value directly.

Q50Singleton pattern implementations, and the Builder patternHard 
// 1. Eager initialization — instance created at class-load time; thread-safe by the JVM's class-init
// guarantee, but wastes memory/startup time if the instance is never actually used
class EagerSingleton {
    private static final EagerSingleton INSTANCE = new EagerSingleton();
    private EagerSingleton() {}
    public static EagerSingleton getInstance() { return INSTANCE; }
}

// 2. Lazy initialization — NOT thread-safe as written; two threads can both pass the null check
class LazySingleton {
    private static LazySingleton instance;
    private LazySingleton() {}
    public static LazySingleton getInstance() {
        if (instance == null) instance = new LazySingleton(); // race condition!
        return instance;
    }
}

// 3. Double-checked locking — lazy AND thread-safe, minimal synchronization overhead after warm-up
class DclSingleton {
    private static volatile DclSingleton instance; // volatile stops other threads seeing a half-built object
    private DclSingleton() {}
    public static DclSingleton getInstance() {
        if (instance == null) {                      // first check — skip locking on the common warm path
            synchronized (DclSingleton.class) {
                if (instance == null) {                // second check — only one thread actually constructs it
                    instance = new DclSingleton();
                }
            }
        }
        return instance;
    }
}

// 4. Enum singleton — considered the SAFEST: the JVM guarantees a single instance, it's
// serialization-safe out of the box, and immune to reflection-based attacks that can normally
// force a "private" constructor to run a second time

    private final boolean cheese;    // optional
    private final boolean pepperoni; // optional

        this.cheese = b.cheese;
        this.pepperoni = b.pepperoni;
