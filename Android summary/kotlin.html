Q1Explain all scope functions: let, run, with, apply, also — when to use eachHard

Kotlin doesn't have one general-purpose way to reach into an object — it has five scope functions, and the trick to keeping them straight is two independent questions: what do you call the receiver inside the block, and what does the whole expression return? let, run, and with return whatever the lambda's last line evaluates to, which makes them a good fit for computing a derived value or chaining a null check straight into a transform. apply and also instead hand back the original receiver itself, which is why they're the right choice for configuring an object in place or peeling off a side effect — like a log line — mid-chain without breaking the chain. with is the odd one out because it isn't an extension function at all — it takes the receiver as a plain argument — so it's mainly used to group several calls on an already non-null object rather than to chain safely off a nullable one.

// let: non-null receiver, returns lambda result, 'it' as reference
val result = user?.let {
    processUser(it) // returns processed value
}

// run: 'this' as reference, returns lambda result. Good for null checks + transform
val result = user?.run {
    "Name: $name, Age: $age" // this = user
}

// with: 'this' as reference, NOT extension function, returns lambda result
val result = with(user) {
    println(name) // use on non-null objects
    email
}

// apply: 'this' as reference, returns THE RECEIVER. Good for initialization
val intent = Intent().apply {
    action = Intent.ACTION_VIEW
    data = uri
    addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
} // returns the Intent

// also: 'it' as reference, returns THE RECEIVER. Good for side effects
val users = repository.getUsers()
    .also { log("Fetched ${it.size} users") } // returns the list
    .filter { it.isActive }

Memory trick:

  • let/also: use it | run/apply/with: use this
  • let/run/with: return lambda result | apply/also: return receiver
  • apply: configure objects | also: side effects on existing objects
Q2What is the difference between inline, noinline, and crossinline?Hard

These four modifiers all deal with how the compiler treats a lambda parameter, and interviewers ask this to see if you understand what "inline" actually buys you. Marking a function inline tells the compiler to paste its body — and the bodies of any lambda parameters passed to it — directly into every call site, so no Function object gets allocated and no virtual call happens; that's why higher-order functions like map and filter can be used pervasively in Kotlin without a real performance tax. Once a function is inline, every lambda parameter is inlined by default, but that's not always desirable: noinline opts one specific lambda back out, typically because you need to store it in a variable or hand it to a non-inline function, both of which require it to exist as a real object. crossinline solves a different problem — it doesn't stop inlining, it forbids that particular lambda from using a non-local return, because the lambda is about to be invoked from another execution context (inside another function object, or later via a callback) where jumping back out of the original caller no longer makes sense. reified is only legal on an inline function because inlining is exactly what preserves the real type argument at each call site, letting you write T::class or is T checks that the JVM would otherwise erase at runtime.

// WITHOUT inline: creates a lambda object on heap, indirect call
fun <T> myWith(receiver: T, block: T.() -> Unit) { receiver.block() }

// WITH inline: lambda body pasted inline, no object created
inline fun <T> myWith(receiver: T, block: T.() -> Unit) { receiver.block() }

// noinline: don't inline THIS specific lambda (when you need to pass it around)
inline fun doSomething(inlined: () -> Unit, noinline notInlined: () -> Unit) {
    inlined()
    storeForLater(notInlined) // can store because it's a real object
}

// crossinline: lambda can't use 'return' (non-local return not allowed)
inline fun runOnMainThread(crossinline block: () -> Unit) {
    Handler(Looper.getMainLooper()).post { block() }
    // Without crossinline: block() could 'return' from an outer function
    // crossinline prevents non-local returns in this context
}

// reified: access type T at runtime (normally erased by JVM)
inline fun <reified T> Context.startActivity() {
    startActivity(Intent(this, T::class.java)) // T::class.java works because reified
}
startActivity<MainActivity>() // Clean API!
Q3Explain sealed classes vs enums vs abstract classesMedium

Enums, sealed classes, and abstract classes all model "this thing is one of a fixed set of options," just at different levels of flexibility. An enum is the most restrictive: every constant is the same type with the same shape, just different values — perfect for something like a Direction with four interchangeable variants. A sealed class raises the ceiling: it fixes the set of subtypes at compile time, but each subtype can carry completely different data and shape, which is exactly what you need to model something like a network Result that's Success with a payload, Error with an exception, or Loading with nothing at all. A plain abstract class doesn't fix anything — arbitrary subclasses can be defined anywhere, even in another module — so the compiler has no way to help you catch a missing case. The real payoff of sealed classes is that a when over them is exhaustive: the compiler forces you to handle every subtype, and adding a new one later breaks the build everywhere it isn't handled — a safety net neither plain enums nor abstract classes give you for free.

// Enum: fixed set of constants, same type, no state variation
enum class Direction { NORTH, SOUTH, EAST, WEST }

// Sealed class: fixed set of TYPES, each can have different data
sealed class Result<out T> {
    data class Success<T>(val data: T) : Result<T>()
    data class Error(val exception: Exception) : Result<Nothing>()
    object Loading : Result<Nothing>()
}

// when() is exhaustive — compiler forces you to handle all cases
when (result) {
    is Result.Success -> showData(result.data)   // smart cast: result.data accessible
    is Result.Error -> showError(result.exception)
    Result.Loading -> showLoading()
    // No 'else' needed — compiler knows all cases covered
}

// Sealed interface (Kotlin 1.5+) — more flexible, no single file restriction
sealed interface UiState
data class Loaded(val items: List<Item>) : UiState
object Empty : UiState
object Loading : UiState
Q4Explain Kotlin generics: variance, in/out, and when to use eachHard

Generic variance answers one question: if Dog is a subtype of Animal, is Box<Dog> a subtype of Box<Animal>? By default, Kotlin generics are invariant, so the answer is no — the two are unrelated types even though Dog and Animal aren't. Marking a type parameter out makes the class covariant: it can only ever produce or return that type, never accept it as an input, and that restriction is exactly what lets the compiler safely treat a Cage<Dog> as a Cage<Animal>. Marking a type parameter in makes it contravariant — the opposite trade: the class can only consume that type as a parameter and never hand it back out, which is why a Feeder<Animal> can safely stand in for a Feeder<Dog> — anything that can feed any animal can certainly feed a dog. The mnemonic PECS — Producer Extends, Consumer Super — captures this, and it's exactly why the built-in List<out T> is covariant and read-only, while MutableList<T> stays invariant since it both produces and consumes T.

// Invariant: default. Box<Dog> is NOT a subtype of Box<Animal>
class Box<T>(var item: T)

// Covariant (out): Producer. Box<Dog> IS a subtype of Box<Animal>
// T can only be returned (produced), not consumed
class Cage<out T>(val animal: T) // val, not var — only readable
val dogCage: Cage<Dog> = Cage(Dog())
val animalCage: Cage<Animal> = dogCage // OK with 'out'

// Contravariant (in): Consumer. Accepts Animal where Dog expected
// T can only be accepted (consumed), not returned
class Feeder<in T> {
    fun feed(animal: T) { /* ... */ }
}
val animalFeeder: Feeder<Animal> = Feeder()
val dogFeeder: Feeder<Dog> = animalFeeder // OK with 'in'

// Real example: List is covariant (out), MutableList is invariant
val dogs: List<Dog> = listOf(Dog())
val animals: List<Animal> = dogs // OK! List<out T>

PECS rule: Producer = out (extends/covariant), Consumer = in (super/contravariant)

Q5What is delegation in Kotlin? lazy, observable, and interface delegationMedium

Kotlin's by keyword covers three distinct but related ideas, all under the umbrella of delegation — handing off responsibility for a property or an interface to another object instead of implementing it yourself. by lazy defers a val's initialization until the first time it's actually read, then caches the result, which is ideal for something expensive like opening a database that you don't want to pay for unless it's needed; it's thread-safe by default, though you can relax that with a LazyThreadSafetyMode when you know only one thread will ever touch it. Delegates.observable and vetoable let a var run a callback on every change — observable purely for notification, vetoable to actually reject a write by returning false. Interface delegation is different again: class Foo : List<T> by inner tells the compiler to implement every method of List by forwarding to inner automatically, so you only write the one or two methods you actually want to customize. Under the hood, all three are backed by the same mechanism — a class exposing operator fun getValue()/setValue() that the compiler wires up for you — which is also how you'd build a fully custom property delegate, like a SharedPreferences-backed property.

// by lazy: computed once on first access, thread-safe by default
val database: RoomDatabase by lazy {
    Room.databaseBuilder(context, AppDb::class.java, "app.db").build()
}
// LazyThreadSafetyMode:
val single by lazy(LazyThreadSafetyMode.NONE) { compute() } // single thread only

// by observable: callback on every change
var userName: String by Delegates.observable("") { _, old, new ->
    println("Changed: $old -> $new")
}

// by vetoable: can reject changes
var age: Int by Delegates.vetoable(0) { _, _, new -> new >= 0 }

// Interface delegation — implement interface by forwarding to another object
class LoggingList<T>(private val inner: MutableList<T>) : MutableList<T> by inner {
    override fun add(element: T): Boolean {
        println("Adding: $element")
        return inner.add(element) // override only what you want
    }
} // All other MutableList methods automatically delegated to inner

// Custom property delegate
class PrefsDelegate(private val key: String, private val default: String) {
    operator fun getValue(thisRef: Any?, property: KProperty<*>) =
        prefs.getString(key, default) ?: default
    operator fun setValue(thisRef: Any?, property: KProperty<*>, value: String) =
        prefs.edit().putString(key, value).apply()
}
var username: String by PrefsDelegate("user_name", "")
Q6What is the difference between data class, regular class, and object?Easy

These three keywords solve different problems even though they all define a "class" in the loose sense. A regular class is the general-purpose tool — you write whatever state and behavior you need, and equality defaults to reference identity unless you override equals() yourself. A data class is specifically for classes whose whole purpose is holding a bundle of values: the compiler generates equals(), hashCode(), toString(), copy(), and componentN() functions from the primary constructor properties, so two instances with the same field values compare as equal and you get a readable toString() for free. object is a completely different axis — it's not about what the class holds, it's about how many instances exist: declaring object Foo gives you a single, lazily-initialized, thread-safe singleton, and a companion object is the same idea scoped to live inside a class, so it can attach static-like factory methods or constants to it.

// data class: auto-generates equals(), hashCode(), toString(), copy(), componentN()
data class User(val id: Int, val name: String)

val u1 = User(1, "Alice")
val u2 = u1.copy(name = "Bob") // User(1, "Bob")
val (id, name) = u1 // destructuring
u1 == User(1, "Alice") // true (structural equality)

// object: singleton, thread-safe initialization
object AppConfig {
    const val BASE_URL = "https://api.example.com"
}

// companion object: static-like members, can implement interfaces
class MyClass {
    companion object Factory {
        fun create(): MyClass = MyClass()
        const val TAG = "MyClass"
    }
}
MyClass.create() // accessed like static method

// Differences to remember:
// data class: primary purpose = holding data, can be instantiated multiple times
// object: singleton, initialized lazily on first access
// companion: belongs to a class, one per class
Q7What is the difference between == and === in Kotlin? What about equals()?Easy

Kotlin splits what Java conflates into two separate operators. == is structural equality — it calls equals() under the hood, so for a data class it's comparing field values, and it's null-safe by construction: a == b compiles to a check that never throws even if either side is null, unlike Java's raw a.equals(b), which NPEs if a is null. === is referential equality — it asks whether both sides point to the exact same object in memory, the thing Java's == does for objects. So two separately-constructed String objects with identical characters are == (same content) but not === (different objects), and two data class instances with equal fields are == but not === for the same reason. Calling .equals() directly is essentially the same as ==, just without the null-safety wrapper Kotlin adds around the operator.

val a = String("hello".toCharArray())
val b = String("hello".toCharArray())

a == b   // true — structural equality, calls equals() — SAME AS .equals()
a === b  // false — referential equality, same object in memory?

// For data classes: == uses generated equals() (compares fields)
data class Point(val x: Int, val y: Int)
Point(1,2) == Point(1,2)  // true
Point(1,2) === Point(1,2) // false (different objects)

// Null-safe: a == null compiles to a?.equals(null) ?: (b === null)
// Never throws NPE unlike Java's a.equals(b)

Q8Explain ?., ?:, !!, as? and why smart-casting fails on var propertiesHard

Kotlin gives you four tools for a nullable value, each trading off safety differently. ?. short-circuits to null instead of crashing. ?: (elvis) supplies a fallback when the left side is null. as? is a "safe cast" — it produces null instead of throwing ClassCastException. !! is the odd one out: it asserts "trust me, this isn't null" and throws an NPE immediately if you're wrong — it's the one operator that reintroduces Java's crash behavior, so treat it as a code smell outside of tests/prototypes.

val len: Int? = str?.length          // null-safe call — null in, null out
val len2: Int = str?.length ?: 0   // elvis — default when null
val forced: Int = str!!.length        // throws NPE right here if null
val asInt: Int? = obj as? Int       // safe cast — null instead of a crash

class Session(var token: String?) {
    fun show() {
        if (token != null) {
            // println(token.length)   // ERROR: 'token' is a var — could change before use
            token?.let { println(it.length) } // re-check safely instead
        }
    }
}

Java interop adds a third state: a method with no @Nullable/@NonNull annotation is exposed as a platform type (shown as String!). The compiler doesn't know its nullability, so it doesn't force a check either way — you can assign it to a nullable or non-null variable, and an incorrect guess still fails as a plain NPE at the point of use, exactly like unchecked Java code.

Smart-cast rule: the compiler only smart-casts when it can prove the value can't change between the null-check and the use. That's true for local vals and simple val properties. It's never true for a var property — another thread, a custom getter, or code between the check and the use could mutate it — and it's never true for anything mutable captured inside a lambda that might run later. The fix is always the same: copy the value into a local val first.
Q9How are extension functions resolved? Why can't they access private members?Medium

An extension function is compiled as an ordinary static function that takes the receiver as a hidden first parameter — it's not injected into the class at all. Two consequences follow. First, resolution is static: the compiler picks which extension to call based on the declared (compile-time) type of the expression, not the object's actual runtime type — unlike member functions, which dispatch dynamically and support real overriding. Second, because the generated function lives outside the class, ordinary JVM visibility rules apply: it can only see public/internal members of the receiver, never private ones.

open class Shape
class Circle : Shape()

fun Shape.describe() = "Shape"      // extension on Shape
fun Circle.describe() = "Circle"    // a DIFFERENT function — not an override

fun show(s: Shape) = println(s.describe())
show(Circle())                    // prints "Shape" — picked by the declared type

class Greeter { fun greet() = "member" }
fun Greeter.greet() = "extension"  // shadowed — unreachable, member always wins

This is also why a member function always wins when signatures collide: the compiler resolves members first, and an extension is really just sugar for calling a free function with dot-syntax — it can never override, and it can never be overridden.

Q10Function types, trailing lambdas, SAM conversion, and function referencesMedium

A function type like (Int) -> Boolean describes a value that can be called — Kotlin treats lambdas as first-class values of that type, which is what makes higher-order functions like filter/map possible. When the last parameter of a call is a function type, Kotlin lets you move the lambda outside the parentheses (the "trailing lambda" convention) — that's why list.filter { ... } reads like a language keyword instead of a function call. For interop, a Java single-abstract-method interface accepts a lambda directly (SAM conversion); a Kotlin interface needs the fun interface modifier to get the same treatment. Finally, :: turns an existing function, method, or constructor into a function value without writing a wrapping lambda.

val isEven: (Int) -> Boolean = { it % 2 == 0 }
listOf(1, 2, 3, 4).filter { it % 2 == 0 }   // trailing lambda syntax

fun interface Validator { fun validate(s: String): Boolean }
val notBlank = Validator { it.isNotBlank() } // SAM conversion (needs 'fun interface')

fun square(x: Int) = x * x
listOf(1, 2, 3).map(::square)          // unbound function reference
val bound = someInstance::toString      // bound reference — carries its receiver
Q11What are @JvmInline value classes for, and what are their restrictions?Hard

Passing three String parameters in a row is easy to get wrong — nothing stops you from swapping accountId and userId, both are just strings to the compiler. Wrapping each in its own class fixes that, but a normal wrapper class means a real heap allocation for every value. A value class gets both: type safety at compile time, and (in the common case) the wrapper disappears entirely at runtime — the compiler substitutes the raw underlying value, so calling a function that takes an AccountId costs no more than passing a String directly.

@JvmInline value class AccountId(val value: String)
@JvmInline value class Cents(val value: Long)

fun transfer(from: AccountId, to: AccountId, amount: Cents) { /* ... */ }
// transfer(toId, fromId, amount)   // ERROR now — a raw String can't be passed anymore

val boxed: AccountId? = null          // nullable -> boxed at runtime
val list: List<AccountId> = listOf()     // generic type argument -> boxed at runtime

Restrictions keep the "zero-cost" guarantee possible: a value class holds exactly one val property in its primary constructor, can't extend a class or be extended, but can implement interfaces and declare functions/operators. equals()/hashCode() are generated from the underlying value automatically. Boxing still happens whenever the compiler can't guarantee an unwrapped representation — a nullable value class type, a generic type argument, or a reference through a supertype all force a real object to be allocated. This beats a plain typealias, which is just a compile-time name with zero type-safety — a typealias for String still lets you pass any String anywhere.

Q12Sequence vs List/Collection — lazy vs eager evaluationMedium

List operations are eager: each call like .map or .filter runs to completion over the whole list and allocates a brand-new list before the next call even starts. Sequence is lazy: nothing runs until a terminal operation (first(), toList(), sum()...) is called, and then each element is pulled through the entire chain of operations one at a time, with no intermediate collections at all.

listOf(1, 2, 3, 4, 5)
    .map { println("map $it"); it * 2 }      // List: ALL 5 mapped first (new list of 5)
    .filter { println("filter $it"); it > 4 } // then ALL 5 filtered (another new list)
    .first()

listOf(1, 2, 3, 4, 5).asSequence()
    .map { println("map $it"); it * 2 }      // Sequence: map -> filter per element...
    .filter { println("filter $it"); it > 4 } // ...before the next element is read
    .first()                                    // stops the instant a match is found

Use List when

  • the collection is small/medium
  • you need the result more than once (materialize once)
  • you want to inspect/debug an intermediate step easily

Use Sequence when

  • you have long chains of map/filter/etc. over large data
  • you only need a few results — first()/take()/find() short-circuit
  • you want to avoid allocating an intermediate list per step
Q13Kotlin syntax to know cold: tailrec, labeled break/continue, operator overloading, destructuringMedium

Four small pieces of syntax show up constantly in interviews and real code. tailrec asks the compiler to rewrite a self-recursive function into a plain loop, as long as the recursive call is the very last thing the function does — this keeps stack usage constant no matter how deep the recursion goes (a non-tail call, like doing math after the recursive call, disqualifies it). Labeled break/continue let you target an outer loop from inside a nested one, which plain break/continue can't do. operator fun lets a class opt into built-in syntax like + or indexing. And any class — not just data class — can support destructuring by declaring componentN() operator functions itself.

tailrec fun factorial(n: Long, acc: Long = 1): Long =
    if (n <= 1) acc else factorial(n - 1, acc * n) // compiled to a loop, no stack growth

outer@ for (i in 1..3) {
    for (j in 1..3) {
        if (j == 2) continue@outer   // jumps to the next iteration of the OUTER loop
        if (i == 3) break@outer
    }
}

data class Vec(val x: Int, val y: Int) {
    operator fun plus(o: Vec) = Vec(x + o.x, y + o.y)  // enables: vecA + vecB
}

class Range(val start: Int, val end: Int) {
    operator fun component1() = start        // enables: val (a, b) = Range(0, 10)
    operator fun component2() = end
}

Kotlin Basics: Types, Null Safety & Strings

Q14What makes Kotlin's null safety different from Java? Nullable types and platform typesEasy

Kotlin bakes nullability into the type system itself: a plain String can never hold null, and the compiler enforces it at every assignment and function call. To allow null, you opt in explicitly with String?. This turns most NPEs into compile-time errors instead of runtime crashes — the one gap is Java interop, where an unannotated method exposes a platform type (shown as String! in tooltips) that the compiler can't verify either way.

val name: String = "Alice"       // non-null by default — compiler guarantees this
// name = null                       // compile error

var nickname: String? = null     // nullable — must opt in with '?'
// nickname.length                   // ERROR: must check or use ?.
nickname?.length                        // OK — safe call

// Platform type from Java — compiler can't verify nullability either way,
// so it trusts your declared type and won't force a check
val header: String = javaClient.getHeader()   // may NPE at runtime if Java actually returns null
val safeHeader: String? = javaClient.getHeader() // safer default when unsure
Rule of thumb: when consuming unannotated Java (no @Nullable/@NonNull), assume it can return null and assign to a nullable type first — promote to non-null only after checking.
Q15What are Kotlin's basic types, and what do Any, Unit, and Nothing mean?Easy

Kotlin's basic types are the usual primitives you'd expect — Int, Long, Double, Float, Char, Boolean — but they're represented as real objects in the type system, even though the compiler optimizes them down to JVM primitives whenever possible to avoid boxing. Three special types are what interviewers actually care about here. Any is the root of the entire type hierarchy, playing the role Java's Object does, except Any by itself is non-nullable — you need Any? to also allow null. Unit is Kotlin's equivalent of void, but unlike void it's a genuine type with exactly one instance, which is what lets a function returning Unit still be treated as a value wherever a function type is expected. Nothing is the type of an expression that never successfully produces a value — a thrown exception, an infinite loop, a TODO() — and because it's defined as a subtype of every other type, the compiler can still type-check an if/else or a when where one branch produces Nothing, letting the rest of the expression through cleanly.

val i: Int = 42          // inferred as Int from the literal
val l = 42L              // Long literal
val d = 3.14             // Double
val f = 3.14f            // Float
val c: Char = 'K'
val ok: Boolean = true

// Any is the root of the type hierarchy — like Object, but non-null
fun printAny(x: Any) = println(x)   // Any, not Any? — null isn't allowed here

// Unit is Kotlin's "void" — but it's a REAL type with exactly one instance
fun logMessage(msg: String): Unit { println(msg) }  // return type can be omitted

// Nothing — the type of an expression that never completes normally
fun fail(msg: String): Nothing = throw IllegalStateException(msg)

// Nothing is a subtype of every type, so mismatched branches still type-check:
val value: Int = if (ready) 5 else fail("no value")

// List<Nothing> is the type of emptyList() — safely assignable to any List<T>
val empty: List<String> = emptyList()
Nothing shows up whenever a branch can't produce a value — TODO(), a throw expression, an infinite loop — letting the rest of the surrounding expression still type-check cleanly.
Q16String templates, raw strings, and the string functions you'll actually useEasy

Kotlin string templates let you embed a variable or an arbitrary expression directly inside a string literal with $ or ${...}, which eliminates the string-concatenation-with-+ style you'd write in Java and reads far closer to the final output. Triple-quoted raw strings are the other big string feature: they don't process escape sequences at all, so something like a regex or a JSON blob with lots of backslashes and quotes can be written literally instead of escaped, and they can span multiple lines — trimIndent() and trimMargin() exist specifically to strip the leading whitespace that naturally shows up when you indent a multi-line raw string inside a function body. On top of that, the standard library ships a large set of convenience string functions — trim, split, toIntOrNull, padStart, repeat, and more — that cover the everyday string manipulation you'd otherwise reach for regex or manual loops to do.

val name = "Kotlin"
val version = 2.0
println("Hello, $name! Version: ${version}")   // template — no + concatenation needed
println("Sum: ${1 + 2}")                        // any expression is allowed inside ${}

// Raw string — triple-quoted, no escaping needed, spans multiple lines
val json = """
    {
        "name": "$name",
        "ok": true
    }
""".trimIndent()   // strips the common leading whitespace from every line

val sql = """
    |SELECT *
    |FROM users
""".trimMargin()    // strips everything up to and including the '|' marker

// Common stdlib string functions
"  hi  ".trim()                 // "hi"
"a,b,,c".split(",")             // ["a", "b", "", "c"]
"42".toIntOrNull()               // 42 (null instead of throwing on bad input)
"id".padStart(5, '0')            // "000id"
"ab".repeat(3)                   // "ababab"
Q17when expression: exhaustiveness, and expression vs statementMedium

when can be used two ways in Kotlin, and the difference matters because it changes what the compiler requires from you. Used as a statement — where you're just running side effects per branch and nothing consumes a return value — the branches don't need to cover every possible case, and you can leave off else entirely. Used as an expression — where the result is assigned to a variable or returned — Kotlin needs a value out of every possible path, so the compiler forces exhaustiveness and refuses to compile without an else branch, unless the subject's type is a sealed class or an enum whose cases the compiler can already enumerate completely. That last exception is the real payoff: once you're switching over a sealed hierarchy or an enum, the compiler already knows every case exists, so else becomes optional, and adding a new subtype or constant later will break every exhaustive when that doesn't handle it — turning what would be a runtime bug in Java into a compile-time error in Kotlin.

// As a STATEMENT — branches don't need to cover every case
when (httpCode) {
    200 -> println("OK")
    404 -> println("Not found")
    else -> println("Unhandled") // optional here, but good practice
}

// As an EXPRESSION — a value must come out of every path, so the compiler
// forces exhaustiveness
val message: String = when (httpCode) {
    200 -> "OK"
    404 -> "Not found"
    else -> "Unhandled"          // REQUIRED — compile error without it
}

// Exception: when the subject is a sealed type or an enum, the compiler
// already knows every case, so 'else' becomes optional
enum class Status { LOADING, SUCCESS, ERROR }
fun describe(s: Status) = when (s) {           // no else needed — exhaustive
    Status.LOADING -> "Loading"
    Status.SUCCESS -> "Done"
    Status.ERROR -> "Failed"
}
// Adding a new enum constant later breaks the build here until it's handled —
// a safety net a Java switch doesn't give you for free
Add a new subclass to a sealed hierarchy, or a new enum constant, and every exhaustive when referencing it stops compiling until you handle it — this is intentional and one of the biggest real-world wins of sealed types.
Q18Ranges and progressions: 1..10, downTo, step, untilEasy

Ranges give Kotlin a clean, allocation-free way to express "a sequence of values between two bounds" without writing a manual counting loop. 1..10 is an inclusive IntRange, 1 until 10 is the exclusive equivalent that stops one short, downTo walks backwards, and step changes the increment — all four read almost like English once you're used to them. Under the hood, ranges are more than syntax sugar for a for loop: they're real objects backed by the rangeTo() operator function, which is also what makes the in/!in membership checks work, and any type — not just numbers — can support its own range by implementing operator fun rangeTo() itself. The performance detail worth knowing is that when a range like 1..n is used directly as the subject of a for loop, the compiler compiles it down to a plain counting loop with no intermediate collection or boxing at all.

for (i in 1..5) print(i)          // 1 2 3 4 5   — inclusive range
for (i in 1 until 5) print(i)     // 1 2 3 4     — exclusive of the end
for (i in 5 downTo 1) print(i)    // 5 4 3 2 1   — descending
for (i in 1..10 step 2) print(i)  // 1 3 5 7 9   — custom step

val r = 1..10
5 in r      // true — 'in' checks range membership
15 !in r    // true

// '..' is just an operator — rangeTo() — so custom types can support it too
data class Point(val x: Int)
operator fun Point.rangeTo(other: Point) = (x..other.x)
IntRange/LongRange/CharRange compile to a plain counting loop with no boxing when used directly in a for — no intermediate list is ever created.
Q19Named arguments, default parameter values, and vararg with the spread operatorEasy

Named arguments and default parameter values work together to cut down on the constructor and function overloading you'd need in Java. A parameter with a default value can simply be omitted at the call site, and named arguments let a caller skip earlier parameters and specify only the ones after — in any order — which avoids the classic mistake of miscounting positional booleans or ints. vararg lets a function accept a variable number of arguments of the same type, exposed inside the function as a plain array, and Kotlin only allows one vararg parameter per function, conventionally placed last; if a parameter has to follow it, callers are required to pass that one by name. The spread operator, *array, is how you forward an existing array into a vararg parameter instead of passing its elements one at a time.

fun createUser(name: String, age: Int = 18, isAdmin: Boolean = false) { /* ... */ }

createUser("Alice")                       // uses both defaults
createUser("Bob", isAdmin = true)         // named arg — skip 'age', keep its default
createUser(name = "Eve", age = 30)        // order doesn't matter with named args

// vararg — zero or more arguments, exposed as an Array inside the function
fun sum(vararg numbers: Int): Int = numbers.sum()
sum(1, 2, 3)                              // 6
sum()                                     // 0

// spread operator '*' — unpacks an existing array into vararg positions
val nums = intArrayOf(1, 2, 3)
sum(*nums)                                // spreads the array as individual args

// only ONE parameter may be vararg, conventionally placed last; if a param
// must follow it, callers must pass that one by name
fun log(vararg tags: String, message: String) { /* ... */ }
log("net", "debug", message = "started")

Functions & Lambdas

Q20Higher-order functions and lambda syntax — it, multiple params, destructuringEasy

A higher-order function is simply a function that takes another function as a parameter or returns one — map, filter, and forEach on collections are all higher-order functions under the hood, each taking a lambda that describes what to do with an element. When a lambda has exactly one parameter, Kotlin lets you skip naming it and refer to it as the implicit it, which is why { it * it } reads so tersely; multi-parameter lambdas need explicit names like { x, y -> x + y }. Lambda parameters can also be destructured inline — handy when iterating over a Map's entries or a list of Pairs, since (key, value) -> ... is more readable than reaching into entry.key and entry.value manually. And because function types are just regular types in Kotlin, a function can return another function — building simple factories or curried-style behavior, like a multiplier(factor) that returns a fresh (Int) -> Int for each factor.

// A higher-order function: takes a function as a parameter
fun calculate(a: Int, b: Int, op: (Int, Int) -> Int): Int = op(a, b)
calculate(4, 2) { x, y -> x + y }     // named lambda params

// single-parameter lambdas can use the implicit name 'it'
listOf(1, 2, 3).map { it * it }        // [1, 4, 9]

// destructuring directly in a lambda parameter — handy for Pair/Map entries
val pairs = listOf(1 to "a", 2 to "b")
pairs.forEach { (number, letter) -> println("$number=$letter") }

mapOf(1 to "one", 2 to "two").forEach { (key, value) -> println("$key -> $value") }

// a function can also RETURN a function (currying-style)
fun multiplier(factor: Int): (Int) -> Int = { n -> n * factor }
val triple = multiplier(3)
triple(5)   // 15
Q21Local functions and closures — what does a lambda actually capture?Medium

A local function is just a function nested inside another — it can see and use everything in its enclosing scope. A lambda closes over the same way: it captures the variables it references, not just their current values. Unlike Java's "effectively final" restriction, Kotlin lets a lambda capture a var and both read and mutate it — the capture is by reference.

fun createGreeter(greeting: String): () -> Unit {
    fun greet() {                  // local function — sees 'greeting' from the outer scope
        println("$greeting!")
    }
    return ::greet
}

// closures capture VARIABLES, not just values — a captured 'var' can be
// read AND mutated from inside the lambda
fun makeCounter(): () -> Int {
    var count = 0
    return { count++ }              // each call mutates the SAME captured 'count'
}
val counter = makeCounter()
counter() // 0
counter() // 1

// Kotlin's for-in loop binds a FRESH read-only variable each iteration, so —
// unlike classic Java/JS loop-closure bugs — this behaves as expected:
val actions = mutableListOf<() -> Unit>()
for (i in 1..3) {
    actions.add { println(i) }      // each lambda captures its OWN 'i'
}
actions.forEach { it() }            // prints 1, 2, 3 — not 3, 3, 3
Capturing a mutable var that outlives the enclosing function — e.g. inside a callback stored for later — is a common source of subtle bugs once multiple threads are involved: the capture is by reference, so concurrent mutation is a genuine race condition.
Q22Infix functions — the rules, and when to reach for oneEasy

An infix function lets you call a function without the dot and parentheses, so a op b reads like natural language instead of a.op(b) — that's exactly how 1 to "one", 1 until 10, and true xor false all work; they're ordinary infix functions from the standard library, not built-in syntax. To declare one yourself, three rules apply: it has to be a member or extension function, it has to take exactly one parameter, and that parameter can't have a default value or be a vararg — the compiler needs the call to stay unambiguous with nothing left implicit. In practice, infix is worth reaching for when the call genuinely reads as a sentence — a small assertion or configuration DSL is the classic case — but forcing it onto something like list.contains(x) just obscures a normal method call without adding any readability.

infix fun Int.times(str: String) = str.repeat(this)
println(2 times "Go")     // "GoGo" — reads like natural language

// stdlib examples you already use every day:
1 to "one"          // Pair(1, "one") — 'to' is an infix function
1 until 10           // IntRange
true xor false        // Boolean

// Rules — an infix function must:
// 1) be a member or extension function
// 2) take EXACTLY one parameter
// 3) have no default value, and not be vararg
infix fun String.padTo(length: Int) = this.padStart(length)   // OK
// infix fun String.padTo(length: Int, char: Char = ' ') ...  // ERROR: default not allowed
Reach for infix mainly when the call reads naturally as a sentence — 1 to 2 or a custom assertion DSL benefit; a plain list.contains(x)-style call gains nothing from it.
Q23Extension properties vs extension functions — why can't extension properties have backing fields?Medium

An extension property looks like a stored property but must always be computed, because Kotlin never actually adds storage to the receiver's class — it's compiled the same static-dispatch way as an extension function, just accessed without parentheses.

// Extension function
fun String.isPalindrome(): Boolean = this == this.reversed()

// Extension property — MUST be computed, no initializer allowed
val String.lastChar: Char
    get() = this[length - 1]        // required — no backing field exists

// a 'var' extension property needs both accessors, still with no storage
var StringBuilder.lastChar: Char
    get() = this[length - 1]
    set(value) { this.setCharAt(length - 1, value) }

// This does NOT compile — no initializer, and 'field' is unresolved here:
// val String.extra: Int = 0          // ERROR
// val String.extra: Int
//     get() = field                  // ERROR: 'field' is unresolved
If you need real per-instance state, extension properties can't provide it — use an external map keyed by identity, or add a genuine member property to the class instead.

Classes & Object-Oriented Kotlin

Q24Primary vs secondary constructors, and the order of initializationMedium

Kotlin separates the idea of "constructor" from "what happens during construction" more explicitly than Java does. The primary constructor lives right in the class header and mainly just declares and binds parameters — any real setup logic goes into one or more init {} blocks, and Kotlin's rule is that init blocks and property initializers run strictly in the order they're written in the source file, interleaved with each other, not all-properties-then-all-inits or vice versa. A secondary constructor, declared with the constructor keyword, is required to delegate to the primary constructor — directly with this(...) or through another secondary constructor — so the primary constructor's parameter binding and every init block always run first, no matter which constructor the caller actually used, and only then does the secondary constructor's own body execute. This ordering matters most when one property's initializer depends on another one already being set.

class User(val name: String, age: Int) {   // 'age' is just a ctor param — no val/var → not a property
    val ageGroup: String

    init {                                  // init blocks run in the order they appear,
        println("Creating user: $name")     // interleaved with property initializers
        ageGroup = if (age >= 18) "adult" else "minor"
    }

    // A secondary constructor MUST delegate to the primary, directly or transitively
    constructor(name: String) : this(name, age = 0) {
        println("Secondary constructor finished")
    }
}
// Execution order for User("Bob", 20):
// 1. primary constructor params are bound
// 2. property initializers & init blocks run, top to bottom, in source order
// 3. the secondary constructor's own body (if that's the one called)
A class with only a primary constructor and simple assignments doesn't need init {} at all — property initializers alone cover most cases. Reach for init when initialization needs statements, not just a single expression.
Q25Custom getters/setters and the `field` backing identifierMedium

Every var property in Kotlin gets a default getter and setter generated automatically, and field is the compiler's name for the backing storage those default accessors read from and write to. When you write a custom setter and reference field inside it, you're intercepting the assignment — running your own logic, like validation or a side-effect log — while still routing the actual value through the same storage slot the class already had. The important subtlety is that a backing field only gets generated at all if some accessor in the property actually references field; a property that's fully computed from other properties, like a fahrenheit value derived from celsius, needs no storage of its own and none is allocated. This is also the basis of the "backing property" pattern common in ViewModels: keep a private mutable property internally, expose a public read-only property whose getter just returns the private one, and callers get a safe view without any copying.

class Temperature {
    var celsius: Double = 0.0
        set(value) {
            field = value                 // 'field' — the compiler-generated backing field
            println("Set to $value°C")
        }

    val fahrenheit: Double                 // computed — NO backing field generated at all
        get() = celsius * 9 / 5 + 32
}

// Backing property pattern — a read-only public view over mutable private state
class ViewModel {
    private val _items = mutableListOf<String>()   // internal, mutable
    val items: List<String> get() = _items         // public, read-only — cheap, no copy

    fun addItem(item: String) { _items.add(item) }
}
A backing field only exists if you reference field inside a custom accessor (or use the default accessor). A property whose getter never touches field allocates no storage at all.
Q26Nested classes vs inner classes — what does `inner` actually change?Medium

By default, a class declared inside another class in Kotlin behaves like a Java static nested class — it has no connection to any particular instance of the outer class and can't see the outer class's members at all, which is why it can be constructed as Outer.Nested() without ever having an Outer instance around. Adding the inner keyword changes that completely: an inner class instance is only ever created from an outer instance (outer.Inner()), and it holds an implicit reference back to that specific outer instance, which is what lets it read the outer class's properties directly and use the qualified this@Outer syntax when it needs to disambiguate. The trade-off worth knowing for an interview is that this implicit reference is a real, retained object reference — if an inner class instance is stored somewhere long-lived, like a static field or a listener registered with the OS, it can keep the entire outer instance alive longer than intended, which is a classic memory leak pattern on Android. The safe default is to reach for a plain nested class unless you specifically need access to the outer instance.

class Outer(val name: String) {
    val nested = Nested()          // fine — Nested doesn't need an Outer instance

    class Nested {                  // like a Java 'static' nested class — NO link to Outer
        fun greet() = "Nested"      // cannot see 'name' — no implicit outer reference
    }

    inner class Inner {             // holds an implicit reference to the enclosing Outer instance
        fun greet() = "Inner in ${name}"       // CAN access Outer's members directly
        fun outerRef() = this@Outer.name        // explicit qualified 'this' when needed
    }
}

val outer = Outer("A")
val nested = Outer.Nested()          // no outer instance needed — like a static class
val inner = outer.Inner()            // requires an outer instance to construct
Default to a plain nested class unless you specifically need the enclosing instance — an inner class instance holds a hidden reference to its outer object, which can leak memory if the inner instance outlives the outer one (e.g. stored in a static field or long-lived listener).
Q27Interfaces with default implementations and properties — resolving the diamond problemMedium

Kotlin interfaces can carry both default method implementations and abstract properties, closer to Java 8's default methods than to classic interfaces — but that power reintroduces the diamond problem when a class implements two interfaces that both provide a default for the same method signature. Kotlin refuses to silently pick one for you: the implementing class is forced to override the conflicting method itself, and inside that override it can explicitly choose which supertype's implementation to fall back on using the qualified syntax super<InterfaceName>.method(), even calling both if that's the right behavior. Interface properties work similarly but with one restriction: an interface property can declare a custom getter, but it can never hold actual backing state, since there's no instance storage at the interface level — any real state has to live in the implementing class, either as a constructor property or an overridden accessor.

interface Clickable {
    fun click() = println("Clickable clicked")   // default implementation
    val id: String                                // abstract property — no state, no default value
}

interface Focusable {
    fun click() = println("Focusable clicked")    // same signature — a conflict!
}

class Button(override val id: String) : Clickable, Focusable {
    // MUST override — the compiler can't silently pick one default for you
    override fun click() {
        super<Clickable>.click()    // explicitly call ONE specific supertype's implementation
        super<Focusable>.click()
        println("Button clicked")
    }
}
An interface property can declare a getter (val x: Int get() = ...) but never holds real state — implementing classes must supply the actual storage, either as a constructor property or their own custom accessor.
Q28What does a companion object compile to? @JvmStatic and the factory patternMedium

A companion object isn't just Kotlin's version of "static" — it's a genuine singleton the compiler generates as a nested class (named Companion by default) with a single static instance field on the outer class, which is why calling ApiClient.create() from Kotlin looks static but from Java actually compiles to ApiClient.Companion.create() unless you help it along. @JvmStatic on a companion function tells the compiler to also generate a real static method on the outer class itself, so Java callers get the clean ApiClient.createDefault() syntax instead of going through .Companion. The common idiom of pairing a private constructor with a companion factory function exists because a companion object, unlike a constructor, can validate input, return a cached instance, or hide multiple construction paths behind one clean, appropriately-named entry point — none of which a raw public constructor can do.

class ApiClient private constructor(private val baseUrl: String) {

    companion object {                       // exactly one per class; compiles to a nested
        private const val DEFAULT_URL = "https://api.example.com"  // 'ApiClient$Companion' singleton

        fun create(url: String = DEFAULT_URL): ApiClient = ApiClient(url)   // factory function

        @JvmStatic
        fun createDefault(): ApiClient = ApiClient(DEFAULT_URL)
    }
}

val client = ApiClient.create()      // Kotlin call — looks static either way
// Java call without @JvmStatic:  ApiClient.Companion.create();
// Java call WITH @JvmStatic:     ApiClient.createDefault();   // real static method, cleaner interop
The private-constructor-plus-companion-factory combo is idiomatic when you want to validate input, cache instances, or hide multiple construction paths behind one clean entry point.
Q29The three uses of `object`: declaration, expression, and companionEasy

object shows up in three different roles in Kotlin, and they're easy to mix up because they share a keyword but have very different lifetimes. An object declaration — object Foo { } — creates a genuine singleton: exactly one instance exists, created lazily and thread-safely the first time it's referenced, which is the idiomatic replacement for the classic Java singleton-with-double-checked-locking pattern. An object expression — object : SomeInterface { } — is the opposite in one important way: every time that expression executes, it creates a brand-new anonymous instance, similar to an anonymous inner class in Java, and it's free to capture variables from its surrounding scope the way a lambda would. A companion object is really just an object declaration nested inside and tied to a specific class, giving that class one shared holder for factory functions or constants. The distinction worth remembering is that only the first and third are singletons — the object expression is not, and creating one inside a loop or a frequently-called function produces a fresh instance every single time.

// 1) Object DECLARATION — a singleton, created lazily and thread-safely on first access
object AnalyticsTracker {
    fun track(event: String) = println("Tracked: $event")
}
AnalyticsTracker.track("app_open")

// 2) Object EXPRESSION — an anonymous, one-off instance (like a Java anonymous class)
val listener = object : View.OnClickListener {
    override fun onClick(v: View?) { println("Clicked") }
}
// unlike a singleton, a NEW instance is created every time this expression runs,
// and it can freely capture variables from the surrounding scope

// 3) Companion object — one per class, tied to that class (see previous question)
class Config { companion object { const val VERSION = 1 } }
Only object declarations and companion objects are singletons; an object expression creates a fresh instance every time that code runs — a subtle but common source of confusion.
Q30Visibility modifiers — how does Kotlin's `internal` differ from Java's package-private?Easy

Kotlin's visibility modifiers mostly map onto Java's, with one meaningful difference and one gap. public is the default (writing it explicitly is redundant), top-level private scopes to the containing file rather than the containing class, and protected is only usable on class members — Kotlin has no top-level protected since there's no enclosing class to protect access on. The interesting one is internal: it makes a declaration visible everywhere inside the same compiled module — the same Gradle module or published artifact — regardless of which package that code lives in. That's a coarser and more deliberate boundary than Java's package-private, which scopes to a single package folder and can be worked around simply by adding a new class to that package from anywhere; internal is enforced at the module boundary the build system actually creates, so it more reliably hides implementation details from other modules or consumers of a published library.

public class Api            // default — visible everywhere (writing 'public' is redundant)
internal class Impl         // visible anywhere in the SAME MODULE, regardless of package
private class Helper        // top-level 'private' = visible only within this FILE

class Base {
    protected val secret = 42     // visible to Base and subclasses only — no top-level 'protected'
    private fun helper() {}       // visible only inside Base
}

class Derived : Base() {
    fun useSecret() = secret      // OK — protected is visible to subclasses
}
Java's package-private (no modifier) scopes to a folder; Kotlin's internal scopes to an entire compiled module — everything inside one Gradle module or published artifact — which is a coarser, more deliberate boundary than "same package."

Constants, Initialization & Immutability

Q31const val vs val — what qualifies as a compile-time constant?Easy

const val and val both create read-only bindings, but they operate at completely different times. A regular val is evaluated at runtime — once per instance if it's a property, or once when the line executes if it's local — so it can call functions, read other values, or do anything else a normal expression can do. const val is evaluated at compile time: the compiler literally inlines the value into every call site that uses it, which restricts it to String and primitive types initialized directly from literal values, and it can only be declared at the top level or inside an object/companion object — never inside a regular class body, since there'd be no single value shared across differently-constructed instances. The gotcha worth mentioning is a binary-compatibility one: because the value is copied into every consumer at compile time, changing a const val inside a library requires every consumer to recompile to pick up the new value, whereas a function or a regular val doesn't carry that constraint.

const val MAX_RETRIES = 3                 // OK — top-level, primitive, literal value
const val APP_NAME = "MyApp"               // OK — String literal

object Config {
    const val VERSION = 2                  // OK inside an object/companion
}

class Request {
    val timestamp = System.currentTimeMillis()   // OK as val — computed at runtime, once per instance
    // const val timestamp = System.currentTimeMillis()  // ERROR: not a compile-time constant
    // const val id = computeId()                        // ERROR: function calls aren't allowed
}
// const val must ALSO be a top-level/object member — never inside a regular
// class body, since there'd be no single "compile time" value shared by all instances
Because const val values are inlined into every call site at compile time, changing one inside a library requires recompiling every consumer — a plain val (or a function) doesn't carry that binary-compatibility gotcha.
Q32lateinit var vs by lazy — differences, and lazy's thread-safety modesMedium

lateinit var and by lazy solve the same basic problem — a property you can't give a real value to immediately — but for different situations. lateinit lets you declare a non-null var without initializing it right away, on the promise that you'll assign it before anything reads it; break that promise and accessing it throws UninitializedPropertyAccessException, though you can defensively check ::property.isInitialized first. It only works on var, and only on non-null, non-primitive types, since there's no sentinel value for a primitive that could represent "not yet set." by lazy is different in kind: it only applies to val, it computes the value itself the first time it's accessed via the lambda you supply, and it caches that result forever afterward — you never assign to it directly. The thread-safety mode you pass to lazy() matters in concurrent code: SYNCHRONIZED (the default) locks so only one thread ever runs the initializer, PUBLICATION allows multiple threads to race to compute it but guarantees they all end up seeing the same result, and NONE skips locking entirely and is safe only when access is guaranteed single-threaded.

class MainActivity : AppCompatActivity() {
    lateinit var binding: ActivityMainBinding   // must be var, non-null, non-primitive

    override fun onCreate(savedInstanceState: Bundle?) {
        binding = ActivityMainBinding.inflate(layoutInflater)   // must assign before use
    }

    fun useBinding() {
        if (::binding.isInitialized) { /* safe check */ }
        binding.root   // throws UninitializedPropertyAccessException if accessed too early
    }
}

// by lazy — val only, computed once, thread-safety is configurable
val heavy: Bitmap by lazy { decodeLargeBitmap() }                        // SYNCHRONIZED (default)
val cache: Map<String, Int> by lazy(LazyThreadSafetyMode.PUBLICATION) { buildCache() }
val fast: Int by lazy(LazyThreadSafetyMode.NONE) { compute() }           // no locking at all
SYNCHRONIZED locks so only one thread ever runs the initializer; PUBLICATION lets multiple threads race to compute it but guarantees only one result is kept; NONE has no protection at all — safe only when access is guaranteed single-threaded.
Q33require, check, assert, and error — Kotlin's precondition functionsEasy

These four functions are Kotlin's idiomatic way to fail fast with a clear message instead of letting a bug produce garbage output silently, and the distinction between them is really about whose fault the failure is. require() is for bad input — it throws IllegalArgumentException, so it belongs at the top of a function validating what the caller passed in. check() is for bad internal state — it throws IllegalStateException, so it belongs wherever you're asserting an invariant about the object itself, like having enough balance before a withdrawal. error() unconditionally throws IllegalStateException with your message and has a return type of Nothing, which makes it a natural fit for the else branch of an exhaustive when where you want an "impossible" case to fail loudly instead of being silently ignored. assert() is the odd one out — it's only active when the JVM runs with the -ea flag, off by default in production, so it should never be relied on for anything that actually matters; requireNotNull and checkNotNull are the null-checking variants of the first two, and both also smart-cast their result to a non-null type on success.

fun withdraw(amount: Int, balance: Int) {
    require(amount > 0) { "Amount must be positive, was $amount" }     // IllegalArgumentException
    check(balance >= amount) { "Insufficient balance" }                 // IllegalStateException
}

fun process(state: State) = when (state) {
    State.Ready -> "ready"
    State.Done -> "done"
    else -> error("Unexpected state: $state")     // throws IllegalStateException, return type Nothing
}

// requireNotNull / checkNotNull also smart-cast the result to non-null
fun greet(name: String?) {
    val safeName = requireNotNull(name) { "name must not be null" }   // safeName: String
    println(safeName.length)
}

assert(1 + 1 == 2)   // only active with the JVM's -ea flag — disabled by default, don't rely on it in production
Use require for bad arguments (caller's fault), check for bad internal state (your own invariant broke), and error inside an exhaustive when's else branch to make "this can't happen" cases fail loudly instead of silently returning garbage.
Q34Immutability idioms: copy(), preferring val, and defensive copyingMedium

Kotlin encourages immutability through a handful of idioms rather than one hard guarantee. copy() on a data class is the main one: instead of mutating an existing instance, you produce a new instance with just the fields you specify changed, leaving the original completely untouched — which avoids a whole class of bugs where some other part of the code was still holding a reference to the "old" state. Preferring val over var is the other half of the idiom, but it's only half the story: a val holding a MutableList still lets you mutate the list's contents even though you can't reassign the variable itself, so real immutability requires both a val and a read-only collection type. The defensive-copying pattern — exposing a private MutableList as a public List by returning toList() from a getter — closes a related gap: Kotlin's "read-only" collection interfaces are just a compile-time view with no mutating methods exposed, not a genuinely immutable object, so a caller who casts a List back to a MutableList can still mutate the underlying data unless you've actually handed them a separate copy.

data class Settings(val theme: String, val fontSize: Int)

val original = Settings("dark", 14)
val updated = original.copy(fontSize = 16)   // original untouched; only fontSize changes

// Prefer val + read-only collection TYPES — 'val list' still lets you mutate
// the CONTENTS if the declared type is MutableList, so both matter:
class Cart {
    private val _items = mutableListOf<String>()
    val items: List<String>
        get() = _items.toList()      // defensive copy — caller can't cast back and mutate it
}

// Without the copy, this would compile and silently corrupt internal state:
// (cart.items as MutableList).add("hacked")   // works if items just returns the same instance!
Exposing _items typed as List<String> doesn't stop a caller from casting it back to MutableList<String> at runtime — read-only Kotlin collection types are a compile-time view, not real immutability. Only a genuinely separate copy (or a real immutable collection library) is safe against that.

Collections & Functional Operations

Q35List/Set/Map basics: mutable vs read-only, and listOf vs mutableListOf vs arrayListOfEasy

Kotlin's collection interfaces are split into read-only and mutable pairs — List/MutableList, Set/MutableSet, Map/MutableMap — and listOf(), setOf(), and mapOf() all return the read-only version, meaning the compile-time type simply has no add() or remove() exposed on it. mutableListOf() and friends return the mutable interface with those methods available, and arrayListOf() specifically returns a concrete java.util.ArrayList, typed as Kotlin's ArrayList, for cases where you need that exact Java type for interop. The detail that trips people up is that "read-only" describes the interface, not the object underneath it: if a mutable list is assigned to a variable typed as the read-only List, that variable has no way to mutate the list, but the same underlying object can still be changed through whatever reference is actually typed as mutable, and those changes show up through the read-only view too, since both point at the same list in memory.

val readOnly: List<Int> = listOf(1, 2, 3)         // no add()/remove() in the type
val mutable: MutableList<Int> = mutableListOf(1, 2, 3)
mutable.add(4)

val set: Set<Int> = setOf(1, 2, 2, 3)              // duplicates removed -> {1, 2, 3}
val map: Map<String, Int> = mapOf("a" to 1, "b" to 2)

val arrayList: ArrayList<Int> = arrayListOf(1, 2, 3)   // concrete java.util.ArrayList, exposed as ArrayList

// "read-only" is a VIEW, not a guarantee of immutability:
val backing = mutableListOf(1, 2, 3)
val view: List<Int> = backing         // 'view' has no mutating methods...
backing.add(4)                        // ...but changes through 'backing' still show up in 'view'
println(view)                          // [1, 2, 3, 4]
listOf()/mapOf()/setOf() give you read-only interfaces, not truly immutable collections like Java's List.of() or Guava's ImmutableList — the underlying object can still be mutated through a differently-typed reference to the same instance.
Q36map/filter/reduce/fold — how they differ, and fold's initial value vs reduceMedium

map, filter, reduce, and fold are core building blocks of Kotlin's functional collection API, and they differ in what they do to the collection's shape. map transforms every element into something else, one-to-one, so the result is always the same size as the input. filter keeps the type but shrinks the collection down to only the elements matching a predicate. reduce and fold both combine every element down into a single accumulated result, but they differ in where the accumulator starts: reduce seeds it with the collection's first element, which means it throws on an empty collection since there's nothing to seed it with, while fold takes an explicit initial value as its first argument, so it works safely on an empty collection — and because the seed is explicit, its result type doesn't even have to match the element type, letting you fold a list of numbers into a String, for example.

val nums = listOf(1, 2, 3, 4)

nums.map { it * it }              // [1, 4, 9, 16] — same size, transformed elements
nums.filter { it % 2 == 0 }       // [2, 4] — same type, a subset

nums.reduce { acc, n -> acc + n } // 10 — seed = first element (1); throws on an EMPTY list
nums.fold(100) { acc, n -> acc + n }  // 110 — seed is explicit; works fine on an empty list

// fold's result type can differ from the element type — reduce's can't
val joined: String = nums.fold("") { acc, n -> acc + n }   // "1234"

emptyList<Int>().fold(0) { acc, n -> acc + n }   // 0 — safe
// emptyList<Int>().reduce { acc, n -> acc + n } // throws UnsupportedOperationException

nums.reduceOrNull { acc, n -> acc + n }   // null instead of throwing, on an empty list
Q37groupBy, associateBy, partition, chunked, and windowedMedium

These five functions cover the most common ways you need to reorganize a collection instead of just filtering or mapping it element-by-element. groupBy buckets elements by a computed key into a Map<Key, List<T>>, keeping every element that shares a key. associateBy is similar but assumes uniqueness — it produces a Map<Key, T> with one value per key, so if two elements share a key the later one silently overwrites the earlier one. partition splits a collection into exactly two lists based on a boolean predicate, returned as a Pair of matching and non-matching elements, cleaner than calling filter twice with opposite conditions. chunked breaks a collection into fixed-size sublists, with the final chunk possibly shorter if the size doesn't divide evenly, while windowed produces overlapping sliding windows of a given size — its optional step parameter controls how far the window moves each time, letting you do non-overlapping batches or overlapping time-series-style windows with the same function.

data class User(val name: String, val country: String)
val users = listOf(User("A", "US"), User("B", "US"), User("C", "IN"))

users.groupBy { it.country }
// {US=[User(A,US), User(B,US)], IN=[User(C,IN)]}  — Map<Key, List<T>>

users.associateBy { it.name }
// {A=User(A,US), B=User(B,US), C=User(C,IN)}      — Map<Key, T>, last duplicate wins

val (adults, minors) = listOf(20, 15, 30, 10).partition { it >= 18 }
// adults = [20, 30], minors = [15, 10]  — Pair<List<T>, List<T>>

listOf(1, 2, 3, 4, 5).chunked(2)          // [[1,2], [3,4], [5]] — fixed-size chunks, last may be short
listOf(1, 2, 3, 4, 5).windowed(3)          // [[1,2,3], [2,3,4], [3,4,5]] — sliding window
listOf(1, 2, 3, 4, 5).windowed(3, step = 2) // [[1,2,3], [3,4,5]]
Q38Array vs List in Kotlin — why arrays are less idiomatic, and primitive arraysMedium

Array in Kotlin maps directly onto the JVM's array type, and that has real consequences that make it less idiomatic than List for everyday code. arrayOf() for a type like Int actually boxes every element into an Integer object, since Array<T> is generic and generics can't hold primitives directly — getting a genuinely unboxed array of primitives requires the dedicated IntArray, DoubleArray, and similar types, which compile straight to a real int[] under the hood. Array<T> is also invariant, unlike List<out T>, so an Array<Int> can't be used where an Array<Any> is expected even though the equivalent is fine for List — a direct consequence of arrays being mutable by index while List is read-only by default. The footgun most worth knowing is that arrays don't override equals() or toString(), so == between two arrays is reference comparison even when their contents are identical — contentEquals() and contentToString() are the structural equivalents you actually want. In practice, Array is mainly reached for when interoperating with Java, implementing vararg parameters, or specifically avoiding boxing overhead with a primitive array type in performance-sensitive numeric code.

val arr = arrayOf(1, 2, 3)          // Array<Int> — boxes each Int into an Integer object!
val intArr = intArrayOf(1, 2, 3)    // IntArray — a real unboxed int[] under the hood, no boxing

arr[0] = 10                          // mutable by index — but SIZE is fixed, no add()/remove()

// Array<T> is invariant, unlike List<out T>:
// val objs: Array<Any> = arr        // ERROR — Array<Int> is not a subtype of Array<Any>
val objs: List<Any> = listOf(1, 2, 3)  // OK — List is declared 'out T'

// == on arrays is REFERENCE equality (arrays don't override equals())
intArrayOf(1, 2) == intArrayOf(1, 2)             // false!
intArrayOf(1, 2).contentEquals(intArrayOf(1, 2)) // true — structural comparison

// Prefer List/MutableList for everyday code; reach for Array mainly for
// Java interop, vararg parameters, or IntArray/DoubleArray/... to avoid
// boxing overhead in performance-sensitive numeric code
Forgetting contentEquals (or contentToString() for printing) is one of the most common Kotlin footguns — arrays silently fall back to identity comparison and the default toString().
Q39Comparable vs Comparator — compareBy and thenByMedium

Comparable and Comparator both define an ordering, but they answer different questions about where that ordering should live. A class implements Comparable<T> itself when there's one obvious, intrinsic "natural" order for it — implementing compareTo() bakes that ordering into the type, so calling sorted() on a list of that type just works with no extra arguments. A Comparator is an external, swappable strategy object instead — useful when there either isn't one natural order, or when you need a different one in some particular context without touching the class's own code. Kotlin's compareBy and thenBy make building one read almost like a sentence: compareBy { it.name }.thenBy { it.age } sorts primarily by name and breaks ties by age, and sortedWith() is the function that applies a Comparator instead of the type's own compareTo(). The rule of thumb is: implement Comparable for the one "default" ordering a type should have, and build a Comparator for every situational ordering beyond that.

data class Person(val name: String, val age: Int) : Comparable<Person> {
    override fun compareTo(other: Person): Int = age.compareTo(other.age)   // natural order = by age
}

val people = listOf(Person("Bob", 30), Person("Ana", 25))
people.sorted()                    // uses Comparable.compareTo — sorted by age

// Comparator — an external, swappable ordering strategy, no need to touch the class
val byNameThenAge = compareBy<Person> { it.name }.thenBy { it.age }
people.sortedWith(byNameThenAge)    // Ana(25) before Bob(30) — sorted by name, ties broken by age

val byAgeDesc = compareByDescending<Person> { it.age }
people.sortedWith(byAgeDesc)
Implement Comparable when there's one obvious "natural" ordering for the type; reach for a Comparator (often built with compareBy/thenBy) whenever you need a different or situational ordering without touching the class itself.

Generics & Type System Deep Dive

Q40Type erasure and reified generics — why does `reified` require `inline`?Hard

The JVM erases generic type parameters at runtime — List<String> and List<Int> are the exact same class once compiled, so a normal function has no way to check value is T or call T::class. An inline function sidesteps this by physically pasting its body — and the real type argument used at each call site — directly into the caller, so the compiler can substitute the concrete type in place of T before erasure even happens. That's why reified is only legal on an inline function: without inlining, the compiled bytecode has already erased T by the time it runs, and there's nothing left to substitute.

// Normal generics: erased at runtime — this does NOT compile
fun <T> isOfType(value: Any): Boolean = value is T   // ERROR: cannot check for instance of erased type T

// Reified — only allowed on an inline function, since the compiler substitutes
// the ACTUAL type argument at each call site during inlining
inline fun <reified T> isOfType(value: Any): Boolean = value is T
isOfType<String>("hi")   // true — 'T' literally becomes 'String' at this call site

inline fun <reified T> Gson.fromJson(json: String): T = this.fromJson(json, T::class.java)
val user: User = gson.fromJson(jsonString)   // clean API, no TypeToken/Class parameter needed

// Real stdlib use: filterIsInstance relies on reified + inline
val mixed: List<Any> = listOf(1, "a", 2, "b")
val strings: List<String> = mixed.filterIsInstance<String>()   // ["a", "b"]
Without inline, the compiled function only ever sees the erased T — there's nothing left at runtime for reified to substitute. That's why it's a compile error, not just bad style.
Q41Star projection (*) vs Any? in genericsMedium

Star projection and Any? look similar but answer genuinely different questions about a generic type. List<*> means "a list of some specific type, I just don't know which one at compile time" — the compiler still knows there is one real, consistent element type, it just can't name it, so it lets you safely read elements out (each one is at least Any?) but refuses to let you write anything in, since it can't verify a new value matches whatever that hidden type turns out to be; even list.add(null) is rejected because the "in" position for a star-projected type becomes Nothing, which nothing except Nothing itself can satisfy. List<Any?>, by contrast, is a genuine declaration that the list holds a real mix of any type, by design — so both reading and writing are fully allowed, because Any? really is the declared, agreed-upon element type rather than a stand-in for an unknown one. The interview-relevant distinction is that MutableList<*> is read-mostly by necessity, while MutableList<Any?> is fully read-write by design — they look like they mean the same thing but they don't.

fun printAll(list: List<*>) {                 // "a List of SOME type, I don't know which"
    for (item in list) println(item)          // safe to read — every item is at least Any?
}
printAll(listOf(1, 2, 3))
printAll(listOf("a", "b"))

fun addItem(list: MutableList<*>) {
    // list.add("x")     // ERROR — compiler can't prove "x" matches the list's real, unknown type
    // list.add(null)    // ERROR too — not even null is allowed; the 'in' position becomes Nothing
    val first = list[0]  // OK to read — comes out typed as Any?
}

// List<Any?> is a DIFFERENT thing — a list DECLARED to genuinely hold any
// mix of types, so both read and write are allowed:
fun addAnything(list: MutableList<Any?>) {
    list.add("x")    // OK — Any? really is the declared element type
    list.add(42)
    list.add(null)
}
List<*> means "a specific-but-unknown type" (read-safe only); List<Any?> means "genuinely any type, mixed together, by design" (fully read-write). They look similar but answer different questions.
Q42Type aliases — what they are (and aren't)Easy

A typealias is purely a compile-time renaming — it gives an existing type a different name to make signatures more readable, but it introduces zero new type safety, since the alias and the underlying type are completely interchangeable everywhere. That makes it a great tool for shortening a deeply nested generic type like Map<String, List<Order>>, or naming a function type like (View) -> Unit so a parameter list reads clearly, but it does nothing to stop a plain String from being passed wherever a UserId typealias is expected, because to the compiler they're literally the same type. That's the key contrast with @JvmInline value class (see the value-class question): a value class introduces a real, distinct type that the compiler will reject a mismatched String for, at the cost of it being an actual class declaration rather than free — so the choice comes down to whether you want readability alone (typealias) or genuine compile-time protection against mixing up two conceptually different values that happen to share an underlying type (value class).

typealias UserId = String                       // just another name for String
typealias ClickHandler = (View) -> Unit         // shortens a function type signature
typealias UserMap = Map<String, List<Order>>    // shortens a deeply nested generic type

fun onClick(handler: ClickHandler) { /* ... */ }
fun findUser(id: UserId): User? = /* ... */

// NO extra type safety — a UserId and a plain String are 100% interchangeable
val id: UserId = "abc123"
val raw: String = id              // compiles fine — they're literally the same type
findUser("just a raw string")     // compiles fine too — the alias doesn't stop this

// Compare to @JvmInline value class, which DOES introduce a real, distinct type:
// findUser(rawString) would be a compile ERROR if UserId were a value class instead

Q43How do Kotlin DSL builders work? Lambda with receiverHard

A lambda-with-receiver — a function type written as T.() -> Unit — executes its body as if it were an extension function on T: inside the block, this is the receiver, so its members are callable without a qualifier. Nesting these is exactly how type-safe HTML/Gradle-style builders scope which functions are callable at each level.

class Html {
    private val children = mutableListOf<String>()
    fun body(block: Body.() -> Unit) {           // parameter is a lambda WITH RECEIVER Body
        val body = Body()
        body.block()                              // invoked as an extension — 'this' inside block() is Body
        children.add(body.render())
    }
}
class Body {
    private val tags = mutableListOf<String>()
    fun p(text: String) { tags.add("<p>$text</p>") }
    fun render() = tags.joinToString("")
}

fun html(block: Html.() -> Unit): Html = Html().apply(block)

val page = html {
    body {              // 'this' here is Html — body() is called without a receiver prefix
        p("Hello")       // 'this' here is Body — p() resolves against Body, not Html
        p("World")
    }
}

// apply() itself is just a tiny lambda-with-receiver function:
inline fun <T> T.apply(block: T.() -> Unit): T { block(); return this }
The type-safety comes from scoping: inside the body { } block, only Body's members are callable directly, so the compiler catches a misplaced call at the wrong level — the whole trick behind Kotlin's @DslMarker-guarded builders.

Q45Enum classes with abstract members and interfacesMedium

An enum class in Kotlin can declare an abstract member and have each constant supply its own implementation in a per-constant body, which turns the enum itself into a small polymorphic dispatch table instead of something you'd normally pair with an external when block. Each constant like ADD or MULTIPLY effectively becomes its own anonymous subclass of the enum, so calling apply() on Calculator.ADD dispatches straight to that constant's own override with no branching logic anywhere else in the codebase — and because the compiler requires every constant to implement the abstract member, adding a new operation later forces you to fill in its behavior right there, rather than risk forgetting to update a when statement scattered somewhere else. Enums still carry their usual built-in members too — ordinal for declaration order, name for the constant's identifier, and valueOf() to look one up by string, throwing if it isn't found — and since Kotlin 1.9, entries is the preferred way to iterate all constants, since it's a cached List rather than values(), which allocates a brand-new array on every single call.

interface Operation { fun apply(a: Int, b: Int): Int }

enum class Calculator(private val symbol: String) : Operation {
    ADD("+") { override fun apply(a: Int, b: Int) = a + b },
    SUBTRACT("-") { override fun apply(a: Int, b: Int) = a - b },
    MULTIPLY("*") { override fun apply(a: Int, b: Int) = a * b };   // ';' required after the last constant

    override fun toString() = symbol
}

Calculator.ADD.apply(2, 3)        // 5 — no when/if needed, dispatch is per-constant
println(Calculator.MULTIPLY)      // "*"

Calculator.ADD.ordinal    // 0 — declaration order
Calculator.ADD.name       // "ADD"
Calculator.valueOf("ADD") // Calculator.ADD — throws IllegalArgumentException if not found

// Kotlin 1.9+: prefer 'entries' over 'values()' — entries is a cached List,
// values() allocates a brand-new array on every single call
for (op in Calculator.entries) println(op)
Per-constant bodies are the idiomatic replacement for a when(type) { ... } dispatch table scattered across the codebase — adding a new enum constant forces you to implement the abstract member right there, so nothing is silently missed.
Q46Java interop annotations: @JvmOverloads, @JvmStatic, @JvmField, @ThrowsMedium

These four annotations exist purely to smooth over places where a Kotlin feature has no direct Java equivalent. @JvmOverloads is for default parameter values: Kotlin itself compiles a function with defaults down to a single method requiring every argument, so without the annotation, Java callers — who have no concept of default arguments — would be forced to pass all of them; the annotation makes the compiler generate one overload per suffix of default parameters, restoring the convenience Kotlin callers already had. @JvmStatic, applied inside a companion object, generates a genuinely static method on the outer class so Java callers get Api.create() instead of having to go through Api.Companion.create(). @JvmField exposes a property as a plain public field rather than through a generated getter/setter pair, which matters for frameworks that expect direct field access. @Throws is there because Kotlin has no checked exceptions at all — nothing forces you to declare or catch anything — but adding @Throws(IOException::class) tells the Kotlin compiler to still emit the Java throws declaration in the bytecode, so Java callers are properly required to handle it the way Java's checked-exception system expects.

class Api {
    @JvmOverloads
    fun request(url: String, timeout: Int = 30, retries: Int = 3) { /* ... */ }
    // generates 3 Java overloads: request(url), request(url,timeout), request(url,timeout,retries)

    companion object {
        @JvmStatic fun create(): Api = Api()      // real static method for Java
    }
}

class Config {
    @JvmField val maxSize = 100    // exposed as a plain public field in Java — no getMaxSize() generated
}

class FileReaderKt {
    @Throws(IOException::class)     // Kotlin has no checked exceptions, but this annotation still
    fun readFile(path: String) {    // forces Java callers to catch/declare IOException
        File(path).readText()
    }
}
Without @JvmOverloads, a Kotlin function with default parameter values compiles to exactly ONE method requiring every parameter — Java has no concept of default arguments, so callers from Java must pass all of them unless you add the annotation.
Q47try-catch-finally as an expression, and why Kotlin has no checked exceptionsEasy

In Kotlin, try/catch/finally is an expression, not just a statement — the value of the whole construct is whatever the last line of the branch that actually ran evaluates to, which lets you write val number = try { input.toInt() } catch (e: NumberFormatException) { -1 } and assign the result directly instead of declaring a var above the block and mutating it inside each branch. The finally block runs regardless of which path was taken, but purely for side effects — its own value never becomes the result of the expression. That was a deliberate design choice by the Kotlin team, based on the observation that in real Java codebases checked exceptions mostly produced empty catch (Exception e) {} blocks or a blanket throws Exception rather than genuinely safer code — @Throws exists only as an escape hatch for when Java callers specifically still need that declaration.

Q48The sequence { } builder — generating lazy sequences with yieldMedium

The sequence { } builder is Kotlin's tool for generating a lazy, potentially infinite stream of values using ordinary imperative code — a while loop and a yield() call — instead of building an eager collection up front. yield() suspends the generator at that point and hands control back to whatever is consuming the sequence, so a naturalNumbers sequence built around while(true) { yield(n); n++ } never actually runs forever in practice, because functions like take(5) or first { ... } only pull as many values out as they need and the generator body simply never advances past that point. yieldAll() lets you splice an existing list, range, or another sequence into the middle of the generation logic, useful for building a combined sequence out of several sources without eagerly concatenating them first. // Generates values lazily, on demand — nothing is computed until consumed

    while (true) {
        yield(n)          // suspends generation here until the next value is requested
        n++
    }
}

naturalNumbers.take(5).toList()          // [1, 2, 3, 4, 5] — only 5 values ever computed
naturalNumbers.first { it % 7 == 0 }     // 7 — stops generating as soon as it's found

val combined = sequence {
    yieldAll(listOf(1, 2, 3))
    yield(4)
    yieldAll(5..7)
