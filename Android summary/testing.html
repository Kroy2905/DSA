🧪 Testing — Interview Questions

Testing is a first-class citizen at Google. Know unit testing, integration testing, UI testing, and TDD. Expect to write tests during the interview.

Unit Testing

Q1How do you unit test a ViewModel with coroutines and Flow?Hard 
// Dependencies:
// testImplementation("org.jetbrains.kotlinx:kotlinx-coroutines-test:1.7.3")
// testImplementation("io.mockk:mockk:1.13.5")
// testImplementation("app.cash.turbine:turbine:1.0.0")

class UserViewModelTest {

    // Rule to replace Dispatchers.Main in tests
    @get:Rule
    val mainDispatcherRule = MainDispatcherRule()

    private val userRepository = mockk<UserRepository>()
    private lateinit var viewModel: UserViewModel

    @Before
    fun setUp() { viewModel = UserViewModel(userRepository) }

    @Test
    fun `loadUser emits loading then success`() = runTest {
        // Arrange
        val user = User("1", "Alice")
        coEvery { userRepository.getUser("1") } returns user

        // Act + Assert with Turbine
        viewModel.uiState.test {
            viewModel.loadUser("1")

            val loading = awaitItem()
            assertTrue(loading.isLoading)

            val success = awaitItem()
            assertFalse(success.isLoading)
            assertEquals(user, success.user)

            cancelAndIgnoreRemainingEvents()
        }
    }

    @Test
    fun `loadUser emits error on network failure`() = runTest {
        coEvery { userRepository.getUser("1") } throws IOException("Network error")
        viewModel.uiState.test {
            viewModel.loadUser("1")
            skipItems(1) // skip loading state
            val error = awaitItem()
            assertNotNull(error.errorMessage)
            cancelAndIgnoreRemainingEvents()
        }
    }
}

// MainDispatcherRule — replaces Dispatchers.Main in tests
class MainDispatcherRule(private val dispatcher: TestCoroutineDispatcher = UnconfinedTestDispatcher()) : TestWatcher() {
    override fun starting(d: Description?) = Dispatchers.setMain(dispatcher)
    override fun finished(d: Description?) = Dispatchers.resetMain()
}
Q2How do you unit test a UseCase and Repository?Medium 
// UseCase test — pure Kotlin, no Android dependency
class GetUserUseCaseTest {
    private val repository = mockk<UserRepository>()
    private val useCase = GetUserUseCase(repository)

    @Test
    fun `returns user when repository succeeds`() = runTest {
        val expected = User("1", "Alice")
        coEvery { repository.getUser("1") } returns expected
        val result = useCase.invoke("1")
        assertEquals(expected, result)
        coVerify(exactly = 1) { repository.getUser("1") }
    }
}

// Repository test — mock both data sources
class UserRepositoryTest {
    private val remoteSource = mockk<UserRemoteDataSource>()
    private val localSource = mockk<UserLocalDataSource>(relaxed = true)
    private val repository = UserRepositoryImpl(remoteSource, localSource)

    @Test
    fun `getUser returns local cache if available`() = runTest {
        val cached = User("1", "Alice")
        coEvery { localSource.getUser("1") } returns cached
        val result = repository.getUser("1")
        assertEquals(cached, result)
        coVerify(exactly = 0) { remoteSource.fetchUser(any()) } // network NOT called
    }
}

// MockK essentials
mockk<MyClass>()            // strict mock — every call must be stubbed
mockk<MyClass>(relaxed = true) // relaxed — unstubbed calls return defaults
coEvery { suspend_fun() } returns value // stub a suspend function
coEvery { fun() } throws IOException() // throw from mock
coVerify(exactly = 1) { fun() }        // verify called exactly once
verify(exactly = 0) { fun() }          // verify never called

class LoginScreenTest {

    @get:Rule
    val composeTestRule = createComposeRule()

    @Test
    fun `login button disabled when email empty`() {
        composeTestRule.setContent {

    @Test

        composeTestRule.setContent { LoginScreen(onLogin = {}, onForgotPassword = {}) }

        // Interact: type in text field
        composeTestRule.onNodeWithTag("email_field").performTextInput("notanemail")
        composeTestRule.onNodeWithTag("login_button").performClick()

        // Assert: error visible
        composeTestRule.onNodeWithText("Invalid email").assertIsDisplayed()

    @Test

        composeTestRule.setContent {

        composeTestRule.onNodeWithTag("password_field").performTextInput("password")
        composeTestRule.onNodeWithTag("login_button").performClick()
        assertTrue(loginCalled)
    }
}

TDD & Best Practices

Q5What is the testing pyramid and how do you apply it in Android?Medium

Unit Tests (70%)

ViewModels, UseCases, Repositories, Mappers, Utils. Run on JVM, fast (milliseconds). Use MockK for mocking, Turbine for flows.

Integration Tests (20%)

Room DAO tests (in-memory DB), Repository with real data sources, API contract tests. Slower, run on emulator/device.

E2E UI Tests (10%)

Critical user flows only (login, checkout, signup). Espresso or Compose UI tests. Slowest, most brittle.

// In-memory Room DB for integration tests
class UserDaoTest {
    private lateinit var db: AppDatabase
    private lateinit var dao: UserDao

    @Before
    fun setUp() {
        // In-memory: no files on disk, perfect for tests
        db = Room.inMemoryDatabaseBuilder(ApplicationProvider.getApplicationContext(), AppDatabase::class.java)
            .allowMainThreadQueries() // test only!
            .build()
        dao = db.userDao()
    }

    @After fun tearDown() = db.close()

    @Test
    fun insertAndRetrieveUser() = runTest {
        val user = UserEntity("1", "Alice", "alice@test.com", 0L)
        dao.insertAll(listOf(user))
        dao.getUserById("1").first().let {
            assertEquals("Alice", it?.name)
        }
    }
}
Q6What makes code testable? Common anti-patterns that hurt testability.Medium

Good practices for testability:

  • Constructor injection: All dependencies passed in, not created internally
  • Program to interfaces: UserRepository interface, not UserRepositoryImpl
  • Inject Dispatchers: class Repo(val dispatcher: CoroutineDispatcher = Dispatchers.IO) — inject UnconfinedTestDispatcher in tests
  • Pure functions: No side effects, easy to verify output from input
  • Avoid static methods and singletons: They're global state — impossible to replace in tests

Anti-patterns that kill testability:

// BAD: creates dependencies internally
class BadViewModel : ViewModel() {
    private val repo = UserRepositoryImpl() // hardcoded — can't mock
    private val analytics = FirebaseAnalytics.getInstance(context) // static
}

// BAD: Dispatchers.IO hardcoded
suspend fun loadData() = withContext(Dispatchers.IO) { repo.fetch() }

// GOOD: injectable dispatcher
class GoodViewModel(
    private val repo: UserRepository,          // interface
    private val analytics: Analytics,           // interface
    private val dispatcher: CoroutineDispatcher = Dispatchers.IO // injectable
) : ViewModel()

Test Doubles

Q7Fakes vs Mocks vs Stubs vs Spies — what's the precise difference, and why prefer Fakes for repositories?Medium

Dummy

Passed around only to satisfy a parameter or constructor signature — never actually used during the test. Rare in idiomatic Kotlin (default params/nullability avoid most of these) but common in Java-interop tests.

Stub

Returns canned, hardcoded answers to calls made during the test. Has no real logic and doesn't verify anything itself — it just feeds the system under test fixed data. coEvery { repo.getUser(any()) } returns fakeUser is a stub.

Mock

A stub that additionally records how it was called so the test can verify interactions — call count, arguments, order. coVerify(exactly = 1) { repo.deleteUser("1") }. This is what MockK/Mockito generate for you.

Spy

Wraps a real object and delegates to it by default, while letting you observe calls or override one or two methods. Useful when you want genuine behavior for most of a class but need to stub/verify a single method.

Fake

A lightweight but fully working implementation of the interface — e.g. an in-memory FakeUserRepository backed by a MutableMap instead of a real database or network call. It behaves like the production implementation, just without I/O or latency.

Why many Android teams reach for hand-written Fakes over MockK-generated mocks at the repository layer:

  • Fakes catch more real bugs. A mock only returns whatever you told it to return for the exact arguments you stubbed — if your code accidentally passes the wrong id, a lazily-stubbed mock (or a relaxed mock) will happily hand back the "right" value anyway and the test stays green. A fake actually looks the id up in its in-memory store, so a wrong id naturally returns null/throws, exposing the bug.
  • Refactor-resistant. Mocks bake every call shape into the test itself (coEvery { repo.getUser("1") }), so renaming a parameter, splitting a method, or reordering calls breaks dozens of unrelated tests. A fake's public contract barely changes across refactors, so tests built on it keep passing.
  • Don't over-specify interactions. coVerify(exactly = 1) asserts on how the code called its dependency, not on the outcome. Add a harmless second call and mock-based tests break even though behavior is unchanged. Fakes push you toward asserting on state/output, which is what you actually care about.
  • Reusable across the whole suite. One FakeUserRepository can back ViewModel tests, UseCase tests, and integration-style tests, while every mock has to be re-stubbed per test method.
  • Tradeoff: fakes cost more upfront to write and maintain, and a buggy fake can mask a bug a real backend would surface — so a fake's behavior should mirror the real implementation's contract closely (some teams verify this once with a shared "contract test" run against both the fake and the real impl).
class FakeUserRepository : UserRepository {
    private val users = mutableMapOf<String, User>()
    fun addUser(user: User) { users[user.id] = user }
    override suspend fun getUser(id: String): User? = users[id]
}

@Test
fun `returns null for an id that was never added`() = runTest {
    val repo = FakeUserRepository()
    // No stubbing needed — a mock would happily return a canned user
    // for ANY id unless you remembered to stub this exact case
    assertNull(repo.getUser("missing-id"))
}

Testing Coroutines & Flow

Q8How do you test Kotlin Flow with Turbine? What are common pitfalls?Medium

Turbine (app.cash.turbine:turbine) wraps a Flow in a test-friendly collector DSL: flow.test { ... } launches a coroutine that collects the flow and gives you suspend functions — awaitItem(), awaitComplete(), awaitError() — to assert on emissions one at a time, in order, without manually managing a Job or collector. Cold flows (flowOf, a plain flow { }) run to completion and should end with awaitComplete(); hot flows (StateFlow, SharedFlow) never finish on their own and must be released with cancelAndIgnoreRemainingEvents() instead.

@Test
fun `flow emits then completes`() = runTest {
    flowOf(1, 2, 3).test {
        assertEquals(1, awaitItem())
        assertEquals(2, awaitItem())
        assertEquals(3, awaitItem())
        awaitComplete()
    }
}

@Test
fun `StateFlow never completes on its own`() = runTest {
    val state = MutableStateFlow(0)
    state.test {
        assertEquals(0, awaitItem()) // initial value replayed immediately
        state.value = 1
        assertEquals(1, awaitItem())
        cancelAndIgnoreRemainingEvents() // a hot flow never calls awaitComplete()
    }
}

Common pitfalls:

  • Forgetting a flow never completes: StateFlow and SharedFlow are hot and infinite — calling awaitComplete() on one hangs the test until Turbine's default timeout, then fails. End the block with cancelAndIgnoreRemainingEvents() (or let test { }'s implicit cancellation at the end of the lambda handle it) instead.
  • Skipping expectNoEvents(): without it, an unexpected extra emission your code shouldn't have produced simply sits unconsumed and the test still passes — expectNoEvents() is the assertion that nothing is pending.
  • Not draining every emitted item: Turbine fails the test if the flow finishes (or the block ends) with unconsumed items still in the buffer, unless you explicitly acknowledge them with cancelAndIgnoreRemainingEvents() or skipItems(n) — a common "test hangs/fails for no reason" complaint that's actually Turbine correctly telling you the assertions don't match the real emission count.
  • Real delays inside the flow: a delay() inside the collected flow combined with runTest's virtual-time scheduler can behave unexpectedly if dispatchers aren't wired consistently — prefer injecting a TestDispatcher everywhere so Turbine and runTest share the same virtual clock instead of racing against real time.

Screenshot / Snapshot Testing

Q9What is screenshot/snapshot testing (Paparazzi, Shot)? What does it catch that unit tests can't, and what are the tradeoffs?Hard

Screenshot testing renders a Composable or View to a bitmap and diffs it, pixel-by-pixel (with some tolerance), against a previously-approved "golden" image. Paparazzi does this entirely on the JVM using Android's layoutlib renderer — no emulator or physical device needed, so it runs as part of the regular unit-test task in a second or two. Shot (and Compose's own screenshot testing via screenshotTest source sets) instead captures real screenshots from an emulator/device and compares them, which is slower but exercises the actual rendering pipeline end-to-end.

@get:Rule
val paparazzi = Paparazzi(deviceConfig = DeviceConfig.PIXEL_5)

@Test
fun loginScreen_defaultState() {
    paparazzi.snapshot { LoginScreen(onLogin = {}, onForgotPassword = {}) }
}

// ./gradlew recordPaparazziDebug  -> approve new/changed goldens
// ./gradlew verifyPaparazziDebug  -> fails the build if render != golden

What it catches that assertion-based unit tests can't: unit tests verify state and logic ("is isLoading true"), not pixels — they'd happily pass while a margin is wrong, text is clipped, a color token regressed, dark theme contrast is broken, or an RTL layout mirrors incorrectly. Screenshot tests catch exactly these purely-visual regressions, and they catch them for every screen state (loading/error/empty/RTL/large font) cheaply, without a human eyeballing each build.

Benefits

  • Fast, deterministic, runs on every CI build (Paparazzi)
  • Catches visual regressions no assertion would
  • Golden images double as living, reviewable UI documentation in PR diffs

Tradeoffs

  • Golden maintenance: every intentional UI change requires regenerating and re-reviewing goldens — easy to rubber-stamp without truly checking
  • Cross-machine flakiness: font rendering, anti-aliasing, and pixel density can differ subtly across CI runners/OS versions, causing false failures unless fonts/rendering are pinned to one environment
  • Storage/repo bloat from binary golden images over time

Flaky Tests

Q10What are the most common causes of flaky Espresso/Compose UI tests, and how do you fix them properly?Hard
  • Animations left enabled: window/transition/animator duration scales default to 1x on emulators; Espresso can intermittently time out mid-animation or read a view's position/state before a transition finishes. Fix at the environment level, not per-test.
  • Async work Espresso doesn't know about: Espresso's idling is based on the main thread's message queue and registered AppCompat/RecyclerView idling — it has no idea a network call, a coroutine launched on Dispatchers.IO, or a Handler.postDelayed is still in flight. The test proceeds to assert before the async work finishes, and pass/fail depends on how fast the network/CI happened to be that run — the definition of flaky.
  • Thread.sleep() band-aids: "fixing" the above by sleeping a fixed duration is worse than the disease — too short and it's still flaky, too long and every run wastes real wall-clock time across the whole suite for no better guarantee.
  • Compose's built-in idling not covering off-recomposition work: ComposeTestRule automatically waits for recomposition/animation frames, but a coroutine launched in viewModelScope that updates state after a real network round trip is invisible to it — the same class of bug as Espresso, just inside Compose.
  • Test order / shared mutable state: tests that depend on a previous test's side effects (a static singleton, a real shared database file) pass or fail depending on run order — a different flavor of flakiness, not timing-related but often confused for it.
// BAD — guesses how long async work takes
onView(withId(R.id.loadButton)).perform(click())
Thread.sleep(2000) // too short = flaky, too long = slow suite
onView(withId(R.id.userName)).check(matches(isDisplayed()))

// GOOD — Compose: poll a deterministic clock instead of guessing
composeTestRule.mainClock.autoAdvance = false
composeTestRule.onNodeWithTag("load_button").performClick()
composeTestRule.waitForIdle() // waits until actually idle, not a fixed duration
Rule of thumb: if a test needs a sleep to pass reliably, it's not actually synchronized with the thing it's testing — replace the sleep with a mechanism the test framework can poll (IdlingResource, Compose's idling, or a fake/test dispatcher that runs synchronously) rather than a duration you hope is long enough.

CI/CD Testing Strategy

Q11How would you structure the testing strategy in CI for a real Android app?Medium

Unit tests — every commit

  • Pure JVM, no emulator — runs in a plain Gradle/CI container
  • Seconds to a couple of minutes even for a large module
  • Deterministic — near-zero infra-caused flakiness
  • Required check — blocks merge on failure

Instrumented tests — subset / nightly

  • Needs a real device/emulator or a device farm (Firebase Test Lab, AWS Device Farm)
  • Minutes per run, plus device-boot and queue time
  • Subject to emulator timing, API-level/OEM differences
  • Often non-blocking — reported as a signal, triaged separately
// every push/PR — required, blocks merge
./gradlew testDebugUnitTests

// nightly — informational, not a merge gate
firebase test:android run --type instrumentation \
  --device model=Pixel6,version=34 --app app-debug.apk
Why gate merges only on the fast unit-test suite: instrumented failures are frequently caused by environment flakiness — device-farm queueing, emulator timing, an animation race — rather than by the PR's actual change. Making them a hard merge gate trains engineers to reflexively hit "re-run" instead of trusting CI, and adds minutes-to-tens-of-minutes to every merge. Treating instrumented results as a monitored signal (dashboard + alert + human triage) keeps the PR feedback loop fast while still surfacing real regressions. Teams that do want instrumented tests in the merge path usually gate only on a small, curated smoke suite (login, checkout — the handful of flows that would be a P0 if broken) run against a single stable device profile, and push the full instrumented matrix to nightly.
