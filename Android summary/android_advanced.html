Custom Views & Drawing

Q1Explain the View drawing lifecycle: measure → layout → drawHard

Every View goes through three phases before it appears on screen:

class CustomProgressBar(context: Context, attrs: AttributeSet? = null) : View(context, attrs) {

    private var progress = 0f
    private val paint = Paint(Paint.ANTI_ALIAS_FLAG)
    private val rectF = RectF()

    // PHASE 1: MEASURE — How big should this view be?
    override fun onMeasure(widthMeasureSpec: Int, heightMeasureSpec: Int) {
        val desiredW = 300; val desiredH = 50
        // Reconcile our desired size with parent's constraints
        val w = resolveSize(desiredW, widthMeasureSpec)
        val h = resolveSize(desiredH, heightMeasureSpec)
        setMeasuredDimension(w, h) // MUST call this
    }

    // PHASE 2: LAYOUT — Where should children be placed? (for ViewGroups)
    // For leaf views: onLayout() is usually empty
    override fun onLayout(changed: Boolean, l: Int, t: Int, r: Int, b: Int) {
        rectF.set(0f, 0f, width.toFloat(), height.toFloat())
    }

    // PHASE 3: DRAW — Paint pixels on canvas
    override fun onDraw(canvas: Canvas) {
        // Background track
        paint.color = 0xFFE0E0E0.toInt()
        canvas.drawRoundRect(rectF, 25f, 25f, paint)
        // Progress fill
        paint.color = 0xFF6200EE.toInt()
        val progressRect = RectF(rectF.left, rectF.top, rectF.right * progress, rectF.bottom)
        canvas.drawRoundRect(progressRect, 25f, 25f, paint)
    }

    fun setProgress(value: Float) {
        progress = value.coerceIn(0f, 1f)
        invalidate() // schedules onDraw() — use for appearance changes
        // requestLayout() — use when size changes too
    }
}

MeasureSpec modes:

  • EXACTLY: Parent says "you must be exactly this size" (e.g. match_parent, fixed dp)
  • AT_MOST: Parent says "you can be up to this size" (wrap_content)
  • UNSPECIFIED: Parent doesn't care (e.g. ScrollView child, ListView)
💡 Never allocate objects in onDraw() — it causes GC during animation. Pre-allocate Paint, Path, RectF in init or constructor.
Q2What is the difference between invalidate() and requestLayout()?Medium
  • invalidate(): Only triggers draw phase. Use when appearance changes but size doesn't (progress, color, text content in fixed-size view). Cheaper.
  • requestLayout(): Triggers measure + layout + draw. Use when view's size or position changes (adding/removing children, text that changes view size). More expensive — triggers full traversal from root.
  • postInvalidate(): Thread-safe version of invalidate() — use from background threads.
// Rule of thumb:
// Content changed, same size → invalidate()
// Size might change → requestLayout()
// Size AND content changed → requestLayout() alone is enough (includes draw)

// Batching: Android batches invalidate() calls in one frame
// Multiple invalidate() calls before next frame = only ONE draw pass
Q3How do you create a custom ViewGroup (e.g. a simple FlowLayout)?Hard 
class FlowLayout(context: Context, attrs: AttributeSet? = null) : ViewGroup(context, attrs) {

    override fun onMeasure(widthSpec: Int, heightSpec: Int) {
        val maxWidth = MeasureSpec.getSize(widthSpec)
        var currentX = 0; var currentY = 0; var rowHeight = 0
        for (i in 0 until childCount) {
            val child = getChildAt(i)
            measureChild(child, widthSpec, heightSpec) // let child measure itself
            if (currentX + child.measuredWidth > maxWidth) { // wrap to next line
                currentX = 0; currentY += rowHeight; rowHeight = 0
            }
            currentX += child.measuredWidth
            rowHeight = maxOf(rowHeight, child.measuredHeight)
        }
        setMeasuredDimension(maxWidth, currentY + rowHeight)
    }

    override fun onLayout(changed: Boolean, l: Int, t: Int, r: Int, b: Int) {
        var currentX = 0; var currentY = 0; var rowHeight = 0
        for (i in 0 until childCount) {
            val child = getChildAt(i)
            if (currentX + child.measuredWidth > width) {
                currentX = 0; currentY += rowHeight; rowHeight = 0
            }
            child.layout(currentX, currentY, currentX + child.measuredWidth, currentY + child.measuredHeight)
            currentX += child.measuredWidth
            rowHeight = maxOf(rowHeight, child.measuredHeight)
        }
    }
}

RecyclerView Internals

Q4How does RecyclerView recycling work internally? What are the different caches?Hard — Google Favorite

RecyclerView has a 4-level caching system for ViewHolders:

  • Scrap cache (mAttachedScrap / mChangedScrap): ViewHolders currently in layout but temporarily detached during animation/relayout. Reused without rebinding. Instant reuse.
  • Cache (mCachedViews): Recently scrolled-off views. Default size = 2. Returned to exact same position — NO rebind needed. Like a "just in case" buffer for scroll-back.
  • RecycledViewPool (mRecyclerPool): ViewHolders keyed by viewType. Shared across multiple RecyclerViews. Requires rebind when reused (onBindViewHolder called). Default size = 5 per type.
  • ViewCacheExtension: Custom cache layer. Rarely used.
// Optimization: share pool across multiple RecyclerViews (e.g. ViewPager tabs)
val pool = RecyclerView.RecycledViewPool()
pool.setMaxRecycledViews(VIEW_TYPE_POST, 20) // increase pool size
recyclerView1.setRecycledViewPool(pool)
recyclerView2.setRecycledViewPool(pool)

// Increase mCachedViews size for heavy-scroll screens
recyclerView.setItemViewCacheSize(20) // avoid rebinding on slight scroll-back

// DiffUtil: calculate minimal diff, animate only changed items
class PostDiffCallback : DiffUtil.ItemCallback<Post>() {
    override fun areItemsTheSame(old: Post, new: Post) = old.id == new.id
    override fun areContentsTheSame(old: Post, new: Post) = old == new
    override fun getChangePayload(old: Post, new: Post): Any? {
        // Return only what changed — avoids full rebind (flicker)
        return if (old.likes != new.likes) PAYLOAD_LIKES else null
    }
}
✓ Use stable IDs (setHasStableIds(true)) if your items have unique IDs — RecyclerView uses them for better animation decisions.

// ConcatAdapter: combine multiple adapters into one RecyclerView
// NEVER nest RecyclerViews — ruins recycling, breaks scroll

val headerAdapter = HeaderAdapter()
val storiesAdapter = StoriesAdapter()   // horizontal scroll row
val postsAdapter = PostsAdapter()       // main feed
val loadingAdapter = LoadingAdapter()  // footer loading spinner

// Merge all into single RecyclerView
val concatConfig = ConcatAdapter.Config.Builder()
    .setIsolateViewTypes(false) // share ViewHolder types across adapters
    .build()
recyclerView.adapter = ConcatAdapter(concatConfig, headerAdapter, storiesAdapter, postsAdapter, loadingAdapter)

// Update only the section that changed:
postsAdapter.submitList(newPosts)  // headerAdapter untouched
💡 ConcatAdapter was introduced in RecyclerView 1.2.0. Each sub-adapter manages its own data and animations independently.

Performance & Memory

Q6How do you diagnose and fix jank (dropped frames) in Android?Hard

Jank = frames that take longer than 16ms (60fps) or 8.3ms (120fps) to render.

Diagnosis tools:

  • Android Profiler → CPU: Record trace, look for long frames on main thread
  • Systrace / Perfetto: Frame timeline, identify slow phases (measure, layout, draw, animate)
  • GPU Rendering bars: Developer options → "Profile GPU rendering" — bars above green line = jank
  • StrictMode: Catches disk/network I/O on main thread in dev builds

Common causes and fixes:

  • Heavy onDraw(): Move object allocation out, pre-compute values. Never call invalidate() in a loop.
  • Deep view hierarchy: Flatten with ConstraintLayout. Use merge and include tags.
  • Overdraw: Remove unnecessary background paints. Check with "Show overdraw areas" in dev options.
  • RecyclerView bind too slow: Move heavy computation off bind, cache formatted strings.
  • Image decode on main thread: Always use Coil/Glide which decode on background thread.
// StrictMode setup in Application.onCreate() for debug builds
if (BuildConfig.DEBUG) {
    StrictMode.setThreadPolicy(
        StrictMode.ThreadPolicy.Builder()
            .detectAll()
            .penaltyLog()
            .build()
    )
}
Q7What is overdraw and how do you reduce it?Medium

Overdraw = a pixel drawn multiple times in a single frame. 1x overdraw = drawn twice. Colors in GPU overdraw visualization: blue (1x), green (2x), pink (3x), red (4x+).

  • Remove unnecessary backgrounds on ViewGroups (if parent already paints the background)
  • Don't set a Window background if your content fills the screen: window.setBackgroundDrawable(null)
  • Use clipRect() in custom drawing to skip drawing outside visible bounds
  • Use quickReject() to skip drawing entirely when outside clip bounds
// In theme: remove default window background if content fills screen
<style name="Theme.App">
    <item name="android:windowBackground">@null</item>
</style>

// clipRect in custom draw — only draw visible portion
override fun onDraw(canvas: Canvas) {
    for (card in cards) {
        canvas.save()
        canvas.clipRect(card.left, card.top, card.right, card.bottom)
        card.draw(canvas)
        canvas.restore()
    }
}

WorkManager & Background Work

Q8When to use WorkManager vs Coroutines vs Service? How does WorkManager work?Hard

Coroutines (viewModelScope)

In-scope async work. Tied to ViewModel/Activity lifecycle. Cancelled when scope is cancelled. Best for: UI operations, network calls while user is in the screen.

WorkManager

Guaranteed execution even after app restart/kill. Survives device reboot. Supports constraints (WiFi, charging). Best for: sync, upload, cache cleanup — anything that MUST complete.

// WorkManager with coroutines
class SyncWorker(context: Context, params: WorkerParameters) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result {
        return try {
            val userId = inputData.getString("USER_ID") ?: return Result.failure()
            repository.sync(userId)
            Result.success()
        } catch (e: Exception) {
            if (runAttemptCount < 3) Result.retry() else Result.failure()
        }
    }
}

// Schedule with constraints
val syncRequest = PeriodicWorkRequestBuilder<SyncWorker>(15, TimeUnit.MINUTES)
    .setConstraints(Constraints.Builder()
        .setRequiredNetworkType(NetworkType.UNMETERED) // WiFi only
        .setRequiresBatteryNotLow(true)
        .build())
    .setInputData(workDataOf("USER_ID" to userId))
    .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 10, TimeUnit.SECONDS)
    .build()

WorkManager.getInstance(context)
    .enqueueUniquePeriodicWork("sync", ExistingPeriodicWorkPolicy.KEEP, syncRequest)

Animations

Q9What are the different animation APIs in Android?Medium 
// 1. Property Animator (API 11+) — animates actual object properties
ObjectAnimator.ofFloat(view, "translationX", 0f, 200f).apply {
    duration = 300
    interpolator = DecelerateInterpolator()
    start()
}

// 2. ValueAnimator — animate a value, apply manually
ValueAnimator.ofFloat(0f, 1f).apply {
    duration = 500
    addUpdateListener { view.alpha = it.animatedValue as Float }
    start()
}

// 3. AnimatorSet — chain/combine animations
AnimatorSet().apply {
    play(fadeIn).before(slideUp)  // sequence
    play(fadeIn).with(scaleUp)   // parallel
    start()
}

// 4. Transition API — animate between two states of a ViewGroup
TransitionManager.beginDelayedTransition(rootLayout, AutoTransition())
view.visibility = View.VISIBLE // Android animates the change automatically

// 5. MotionLayout (declarative, XML-driven)
// Define start/end ConstraintSets + keyframes in MotionScene XML
motionLayout.transitionToEnd() // or bind to drag gesture

// 6. Compose Animation (modern approach)
val alpha by animateFloatAsState(targetValue = if (visible) 1f else 0f)
✓ For Google interviews: understand that all View Property Animators operate on the View's rendering properties (alpha, translationX, scaleX, rotation) — they don't trigger layout. This is why they're faster than animating margin/width.
