Custom Views & Drawing

Q1Explain the View drawing lifecycle: measure → layout → drawHard

Android splits rendering a View into three distinct passes because a parent and its children need to negotiate size before anyone can be positioned or painted: measure figures out how big a view wants to be given the constraints handed down by its parent, layout assigns each view its final position and size, and draw actually paints pixels onto the Canvas. This is why a ViewGroup's own measurement can't be finalized until it has measured all its children first — sizes resolve bottom-up before positions resolve top-down in layout. Interviewers ask this because it underpins almost every custom-view performance question: understanding that invalidate() only re-triggers draw while requestLayout() re-triggers all three phases is what separates "it works" from "it works and doesn't waste a full traversal on every frame." Here's a minimal custom view that implements all three phases explicitly:

class CustomProgressBar(context: Context, attrs: AttributeSet? = null) : View(context, attrs) {

    private var progress = 0f
    private val paint = Paint(Paint.ANTI_ALIAS_FLAG)
    private val rectF = RectF()

    // PHASE 1: MEASURE — How big should this view be?
    override fun onMeasure(widthMeasureSpec: Int, heightMeasureSpec: Int) {
        val desiredW = 300; val desiredH = 50
        // Reconcile our desired size with parent's constraints
        val w = resolveSize(desiredW, widthMeasureSpec)
        val h = resolveSize(desiredH, heightMeasureSpec)
        setMeasuredDimension(w, h) // MUST call this
    }

    // PHASE 2: LAYOUT — Where should children be placed? (for ViewGroups)
    // For leaf views: onLayout() is usually empty
    override fun onLayout(changed: Boolean, l: Int, t: Int, r: Int, b: Int) {
        rectF.set(0f, 0f, width.toFloat(), height.toFloat())
    }

    // PHASE 3: DRAW — Paint pixels on canvas
    override fun onDraw(canvas: Canvas) {
        // Background track
        paint.color = 0xFFE0E0E0.toInt()
        canvas.drawRoundRect(rectF, 25f, 25f, paint)
        // Progress fill
        paint.color = 0xFF6200EE.toInt()
        val progressRect = RectF(rectF.left, rectF.top, rectF.right * progress, rectF.bottom)
        canvas.drawRoundRect(progressRect, 25f, 25f, paint)
    }

    fun setProgress(value: Float) {
        progress = value.coerceIn(0f, 1f)
        invalidate() // schedules onDraw() — use for appearance changes
        // requestLayout() — use when size changes too
    }
}

MeasureSpec modes:

  • EXACTLY: Parent says "you must be exactly this size" (e.g. match_parent, fixed dp)
  • AT_MOST: Parent says "you can be up to this size" (wrap_content)
  • UNSPECIFIED: Parent doesn't care (e.g. ScrollView child, ListView)
💡 Never allocate objects in onDraw() — it causes GC during animation. Pre-allocate Paint, Path, RectF in init or constructor.
Q2What is the difference between invalidate() and requestLayout()?Medium

invalidate() and requestLayout() are the two ways a custom view tells the framework something changed, and picking the wrong one is a classic source of either jank or invisible bugs. The distinction maps directly onto the three-phase pipeline from the previous question: invalidate() only schedules the draw phase, so it's cheap and correct when a view's appearance changes but its size and position don't. requestLayout() re-runs measure and layout for the affected subtree up to the root — necessary whenever the view's size could change, but wasteful if called defensively when invalidate() alone would have done the job. Interviewers ask this to check whether you reason about the cost of each call rather than just sprinkling both everywhere to be safe.

  • invalidate(): Only triggers draw phase. Use when appearance changes but size doesn't (progress, color, text content in fixed-size view). Cheaper.
  • requestLayout(): Triggers measure + layout + draw. Use when view's size or position changes (adding/removing children, text that changes view size). More expensive — triggers full traversal from root.
  • postInvalidate(): Thread-safe version of invalidate() — use from background threads.

// Content changed, same size → invalidate()
// Size might change → requestLayout()
// Size AND content changed → requestLayout() alone is enough (includes draw)

Q3How do you create a custom ViewGroup (e.g. a simple FlowLayout)?Hard

Building a custom ViewGroup means implementing onMeasure() and onLayout() yourself, because unlike a plain View, a ViewGroup is also responsible for measuring and positioning its children, not just painting itself. A FlowLayout is a good example because it needs genuine layout logic: children should wrap onto a new row once they no longer fit the available width, the same way text wraps. The pattern is always the same two-pass structure — walk the children once in onMeasure(), calling measureChild() on each to find out how much space they want and using that to compute the ViewGroup's own size, then walk them again in onLayout() calling child.layout() with the actual coordinates decided during that first pass. Interviewers are checking for exactly this separation: candidates who try to position children inside onMeasure() run into bugs because final positions aren't settled until layout.

class FlowLayout(context: Context, attrs: AttributeSet? = null) : ViewGroup(context, attrs) {

    override fun onMeasure(widthSpec: Int, heightSpec: Int) {
        val maxWidth = MeasureSpec.getSize(widthSpec)
        var currentX = 0; var currentY = 0; var rowHeight = 0
        for (i in 0 until childCount) {
            val child = getChildAt(i)
            measureChild(child, widthSpec, heightSpec) // let child measure itself
            if (currentX + child.measuredWidth > maxWidth) { // wrap to next line
                currentX = 0; currentY += rowHeight; rowHeight = 0
            }
            currentX += child.measuredWidth
            rowHeight = maxOf(rowHeight, child.measuredHeight)
        }
        setMeasuredDimension(maxWidth, currentY + rowHeight)
    }

    override fun onLayout(changed: Boolean, l: Int, t: Int, r: Int, b: Int) {
        var currentX = 0; var currentY = 0; var rowHeight = 0
        for (i in 0 until childCount) {
            val child = getChildAt(i)
            if (currentX + child.measuredWidth > width) {
                currentX = 0; currentY += rowHeight; rowHeight = 0
            }
            child.layout(currentX, currentY, currentX + child.measuredWidth, currentY + child.measuredHeight)
            currentX += child.measuredWidth
            rowHeight = maxOf(rowHeight, child.measuredHeight)
        }
    }
}

RecyclerView Internals

Q4How does RecyclerView recycling work internally? What are the different caches?Hard — Google Favorite

RecyclerView's performance advantage over the old ListView comes almost entirely from how aggressively it avoids re-inflating and re-binding views, and that's implemented as a four-level cache that a ViewHolder falls through as it scrolls off-screen. The tiers are ordered from cheapest to most expensive to reuse: the earlier a ViewHolder is found, the less work is needed before it can be shown again, ranging from instant reuse with no rebind at all down to a full onBindViewHolder() call. This is a favorite Google interview question because it tests whether you see recycling as a real, tunable performance mechanism rather than a black box — knowing which tier a view lands in explains why scrolling back up feels instant while scrolling into genuinely new content always costs a bind.

  • Scrap cache (mAttachedScrap / mChangedScrap): ViewHolders currently in layout but temporarily detached during animation/relayout. Reused without rebinding. Instant reuse.
  • Cache (mCachedViews): Recently scrolled-off views. Default size = 2. Returned to exact same position — NO rebind needed. Like a "just in case" buffer for scroll-back.
  • RecycledViewPool (mRecyclerPool): ViewHolders keyed by viewType. Shared across multiple RecyclerViews. Requires rebind when reused (onBindViewHolder called). Default size = 5 per type.
  • ViewCacheExtension: Custom cache layer. Rarely used.
// Optimization: share pool across multiple RecyclerViews (e.g. ViewPager tabs)
val pool = RecyclerView.RecycledViewPool()
pool.setMaxRecycledViews(VIEW_TYPE_POST, 20) // increase pool size
recyclerView1.setRecycledViewPool(pool)
recyclerView2.setRecycledViewPool(pool)

// Increase mCachedViews size for heavy-scroll screens
recyclerView.setItemViewCacheSize(20) // avoid rebinding on slight scroll-back

// DiffUtil: calculate minimal diff, animate only changed items
class PostDiffCallback : DiffUtil.ItemCallback<Post>() {
    override fun areItemsTheSame(old: Post, new: Post) = old.id == new.id
    override fun areContentsTheSame(old: Post, new: Post) = old == new
    override fun getChangePayload(old: Post, new: Post): Any? {
        // Return only what changed — avoids full rebind (flicker)
        return if (old.likes != new.likes) PAYLOAD_LIKES else null
    }
}
✓ Use stable IDs (setHasStableIds(true)) if your items have unique IDs — RecyclerView uses them for better animation decisions.
Q5What is ConcatAdapter and when would you use it over nested RecyclerViews?Medium

ConcatAdapter solves a problem that used to be handled by nesting RecyclerViews inside each other or hacking multiple view types into one monolithic adapter: showing several logically distinct sections — a header, a horizontally-scrolling row, a main feed, a loading footer — in one scrollable list. Nesting RecyclerViews is an anti-pattern because the outer RecyclerView can't recycle across the inner ones, nested scrolling is janky, and you lose a single unified scroll position. ConcatAdapter instead lets each section keep its own independent Adapter — with its own DiffUtil, its own data updates, its own view types — and just concatenates them into one adapter that RecyclerView treats as a single flat list. That's the real reason to reach for it over nesting: updating the posts section doesn't touch the header adapter at all, and recycling still works correctly across every section boundary.

// ConcatAdapter: combine multiple adapters into one RecyclerView
// NEVER nest RecyclerViews — ruins recycling, breaks scroll

val headerAdapter = HeaderAdapter()
val storiesAdapter = StoriesAdapter()   // horizontal scroll row
val postsAdapter = PostsAdapter()       // main feed
val loadingAdapter = LoadingAdapter()  // footer loading spinner

// Merge all into single RecyclerView
val concatConfig = ConcatAdapter.Config.Builder()
    .setIsolateViewTypes(false) // share ViewHolder types across adapters
    .build()
recyclerView.adapter = ConcatAdapter(concatConfig, headerAdapter, storiesAdapter, postsAdapter, loadingAdapter)

// Update only the section that changed:
postsAdapter.submitList(newPosts)  // headerAdapter untouched
💡 ConcatAdapter was introduced in RecyclerView 1.2.0. Each sub-adapter manages its own data and animations independently.

Performance & Memory

Q6How do you diagnose and fix jank (dropped frames) in Android?Hard

Jank is what the user actually perceives when a frame misses its deadline: the display refreshes on a fixed schedule (16.6ms per frame at 60fps, 8.3ms at 120fps), and if the app hasn't handed over a new frame in time, the previous frame is shown again, which reads as a visible stutter. Diagnosing it means figuring out which phase of the frame pipeline — input, animation, measure/layout, draw, sync, GPU rendering — is blowing the budget, because the fix is completely different depending on the answer; a slow onDraw() is fixed differently than a deep view hierarchy or a main-thread image decode. Interviewers ask this because it's one of the most common real debugging tasks on the job — knowing the tools (Profiler, Perfetto/Systrace, GPU rendering bars, StrictMode) and the usual culprits signals you've actually chased jank down in a real app rather than just memorized the frame-budget number.

Diagnosis tools:

  • Android Profiler → CPU: Record trace, look for long frames on main thread
  • Systrace / Perfetto: Frame timeline, identify slow phases (measure, layout, draw, animate)
  • GPU Rendering bars: Developer options → "Profile GPU rendering" — bars above green line = jank
  • StrictMode: Catches disk/network I/O on main thread in dev builds

Common causes and fixes:

  • Heavy onDraw(): Move object allocation out, pre-compute values. Never call invalidate() in a loop.
  • Deep view hierarchy: Flatten with ConstraintLayout. Use merge and include tags.
  • Overdraw: Remove unnecessary background paints. Check with "Show overdraw areas" in dev options.
  • RecyclerView bind too slow: Move heavy computation off bind, cache formatted strings.
  • Image decode on main thread: Always use Coil/Glide which decode on background thread.
// StrictMode setup in Application.onCreate() for debug builds
if (BuildConfig.DEBUG) {
    StrictMode.setThreadPolicy(
        StrictMode.ThreadPolicy.Builder()
            .detectAll()
            .penaltyLog()
            .build()
    )
}
Q7What is overdraw and how do you reduce it?Medium

Overdraw = a pixel drawn multiple times in a single frame. 1x overdraw = drawn twice. Colors in GPU overdraw visualization: blue (1x), green (2x), pink (3x), red (4x+).

  • Remove unnecessary backgrounds on ViewGroups (if parent already paints the background)
  • Don't set a Window background if your content fills the screen: window.setBackgroundDrawable(null)
  • Use clipRect() in custom drawing to skip drawing outside visible bounds
  • Use quickReject() to skip drawing entirely when outside clip bounds
// In theme: remove default window background if content fills screen
<style name="Theme.App">
    <item name="android:windowBackground">@null</item>
</style>

// clipRect in custom draw — only draw visible portion
override fun onDraw(canvas: Canvas) {
    for (card in cards) {
        canvas.save()
        canvas.clipRect(card.left, card.top, card.right, card.bottom)
        card.draw(canvas)
        canvas.restore()
    }
}

WorkManager & Background Work

Q8When to use WorkManager vs Coroutines vs Service? How does WorkManager work?Hard

The right tool here depends entirely on what guarantee you need about the work actually completing. A coroutine scoped to a ViewModel or Activity is the simplest option but is explicitly tied to that component's lifecycle — if the user leaves the screen or the process dies, the work is gone, which is fine for a network call feeding the current UI but wrong for anything that must finish regardless. WorkManager exists for the opposite case: it persists the work request to disk, survives process death and even device reboot, and can wait on constraints like being on WiFi or charging before running, which is why it's the right choice for sync, uploads, or cleanup that absolutely has to happen eventually. A plain foreground Service sits in between — useful when work must start immediately and stay visible via a notification, but without WorkManager's built-in persistence, retry, and constraint handling.

Coroutines (viewModelScope)

In-scope async work. Tied to ViewModel/Activity lifecycle. Cancelled when scope is cancelled. Best for: UI operations, network calls while user is in the screen.

WorkManager

Guaranteed execution even after app restart/kill. Survives device reboot. Supports constraints (WiFi, charging). Best for: sync, upload, cache cleanup — anything that MUST complete.

// WorkManager with coroutines
class SyncWorker(context: Context, params: WorkerParameters) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result {
        return try {
            val userId = inputData.getString("USER_ID") ?: return Result.failure()
            repository.sync(userId)
            Result.success()
        } catch (e: Exception) {
            if (runAttemptCount < 3) Result.retry() else Result.failure()
        }
    }
}

// Schedule with constraints
val syncRequest = PeriodicWorkRequestBuilder<SyncWorker>(15, TimeUnit.MINUTES)
    .setConstraints(Constraints.Builder()
        .setRequiredNetworkType(NetworkType.UNMETERED) // WiFi only
        .setRequiresBatteryNotLow(true)
        .build())
    .setInputData(workDataOf("USER_ID" to userId))
    .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 10, TimeUnit.SECONDS)
    .build()

WorkManager.getInstance(context)
    .enqueueUniquePeriodicWork("sync", ExistingPeriodicWorkPolicy.KEEP, syncRequest)

Animations

Q9What are the different animation APIs in Android?Medium

Android has accumulated several animation APIs over the years, and knowing which one to reach for signals that you understand the tradeoffs rather than just copying whichever one you saw in a tutorial. ObjectAnimator and ValueAnimator are both built on the property animation system from API 11: ObjectAnimator directly mutates a named property on a target object (translationX, alpha, scaleX) frame by frame, while ValueAnimator just produces the interpolated values and leaves you to apply them yourself, which matters when you're not animating a simple object property at all. AnimatorSet composes multiple animators together — sequenced or in parallel — for coordinated multi-step effects, while the Transition API and MotionLayout work a level higher, animating between two declared states of a layout rather than individual properties. In Compose, the state-driven approach (animateFloatAsState and friends) replaces most of this entirely, since an animation there is just a function of state rather than an imperative object you start and stop.

// 1. Property Animator (API 11+) — animates actual object properties
ObjectAnimator.ofFloat(view, "translationX", 0f, 200f).apply {
    duration = 300
    interpolator = DecelerateInterpolator()
    start()
}

// 2. ValueAnimator — animate a value, apply manually
ValueAnimator.ofFloat(0f, 1f).apply {
    duration = 500
    addUpdateListener { view.alpha = it.animatedValue as Float }
    start()
}

// 3. AnimatorSet — chain/combine animations
AnimatorSet().apply {
    play(fadeIn).before(slideUp)  // sequence
    play(fadeIn).with(scaleUp)   // parallel
    start()
}

// 4. Transition API — animate between two states of a ViewGroup
TransitionManager.beginDelayedTransition(rootLayout, AutoTransition())
view.visibility = View.VISIBLE // Android animates the change automatically

// 5. MotionLayout (declarative, XML-driven)
// Define start/end ConstraintSets + keyframes in MotionScene XML
motionLayout.transitionToEnd() // or bind to drag gesture

// 6. Compose Animation (modern approach)
val alpha by animateFloatAsState(targetValue = if (visible) 1f else 0f)
✓ For Google interviews: understand that all View Property Animators operate on the View's rendering properties (alpha, translationX, scaleX, rotation) — they don't trigger layout. This is why they're faster than animating margin/width.

App Startup & Initialization

Q10What are the different app startup types (cold/warm/hot) and how do you optimize them?Hard

The three startup types differ in how much state the system has to rebuild — that's the whole story, and it's what determines the cost:

  • Cold start: The app's process doesn't exist yet. The system creates the process, instantiates the Application object (attachBaseContext → onCreate, plus ContentProviders and App Startup initializers), starts the main thread Looper, then creates and inflates the launching Activity before the first frame is drawn. Everything is built from scratch — the most expensive path.
  • Warm start: The process is still alive (the system only evicted the Activity, or the user backgrounded and returned), so Application creation is skipped — but Activity onCreate() still runs and re-inflates views. Cheaper than cold, still noticeable.
  • Hot start: Both process and Activity are alive — the system just brings it to the foreground (onRestart → onStart → onResume). No object creation, no inflation at all. This is what most "reopen the app" launches actually are.

Optimization techniques: Baseline Profiles ship a list of hot classes/methods in the APK so ART ahead-of-time compiles them at install time instead of interpreting them on the first few runs — generated via the Macrobenchmark library recording a real user journey. The App Startup library (androidx.startup) fixes a subtler cost: every library that needs init-time setup traditionally registers its own ContentProvider, and each one adds process-creation overhead even if never queried — App Startup lets each library define an Initializer<T> with explicit dependencies, all running behind a single consolidated ContentProvider. Finally, lazy initialization defers anything not needed for the first frame — by lazy singletons, SDK init pushed past reportFullyDrawn(), or handed off to WorkManager entirely.

class LoggerInitializer : Initializer<Logger> {
    override fun create(context: Context) = Logger.init(context)
    // one ContentProvider for ALL initializers, not one per library
    override fun dependencies() = listOf(WorkManagerInitializer::class.java)
}

// Signal "fully drawn" for cold-start measurement + to gate lazy init after
view.viewTreeObserver.addOnDrawListener { activity.reportFullyDrawn() }
💡 Measure with adb shell am start -W com.app/.MainActivity — it reports TotalTime directly. For CI regression tracking, use Macrobenchmark's StartupTimingMetric.

Bitmap & Image Memory

Q11How do you manage Bitmap memory efficiently — inSampleSize, inBitmap pooling, and hardware bitmaps?Hard

A decoded Bitmap costs width × height × bytesPerPixel — a 4000×3000 photo at ARGB_8888 is ~46MB, an easy OOM if decoded naively just to show a 100dp thumbnail. Three techniques attack this at different points in the pipeline:

  • inSampleSize downsampling: Decode at reduced resolution before the pixel buffer is allocated. First decode with inJustDecodeBounds = true to read width/height from headers only (no pixel allocation), compute a power-of-two sample size that fits the target size, then decode for real.
  • Bitmap pooling / inBitmap reuse: Reuse the pixel buffer of an already-decoded, no-longer-needed Bitmap via BitmapFactory.Options.inBitmap instead of allocating fresh each time — avoids GC churn from constantly alloc'ing/freeing large byte arrays. Glide and Coil both do this automatically via an internal BitmapPool.
  • Hardware bitmaps: On API 26+, Bitmap.Config.HARDWARE decodes straight into GPU-accessible graphics memory — the pixel data never touches the Java/native heap at all. Ideal for images that are only ever drawn (immutable, never read pixel-by-pixel or drawn on a software Canvas).
// 1. Read bounds only (no pixel alloc), then pick a power-of-two sample size
val opts = BitmapFactory.Options().apply { inJustDecodeBounds = true }
BitmapFactory.decodeResource(res, id, opts)
opts.inSampleSize = calculateSampleSize(opts.outWidth, opts.outHeight, reqW, reqH)
opts.inJustDecodeBounds = false
val thumb = BitmapFactory.decodeResource(res, id, opts) // small alloc, not full-size

// 2. Reuse an existing buffer instead of a fresh allocation
opts.inBitmap = pool.getReusableBitmap(opts)

// 3. Decode straight into GPU memory — never touches the Java heap
opts.inPreferredConfig = Bitmap.Config.HARDWARE
⚠ Hardware bitmaps can't be read with getPixels() or drawn on a software Canvas — they're a "decode once, draw many times" optimization, not a general-purpose Bitmap replacement.

Lists, Diffing & Paging Views

Q12How does DiffUtil compute its diff, why do stable IDs matter, and how does ListAdapter differ from calling DiffUtil directly?Hard

How the diff is computed: DiffUtil.calculateDiff() is conceptually based on Eugene Myers' O(N+D²) diff algorithm (the same family behind Unix diff/Git) — it finds the shortest edit script that turns the old list into the new one, i.e. the minimal set of insertions/deletions (a move is really a deletion + insertion at a different index), instead of comparing every old item against every new item pairwise. This is what lets RecyclerView run a targeted, minimal set of item animations.

Why stable IDs matter: areItemsTheSame() tells the algorithm "this is the same logical entity, just possibly changed or moved" versus "this is new." Compare by a stable unique ID (a DB primary key), not object equality or list position — otherwise DiffUtil can't distinguish a moved item from a remove+add pair, producing wrong animations and unnecessary rebinds. areContentsTheSame() only runs once items are matched, and decides if a rebind is needed at all.

ListAdapter vs manual calculateDiff: calling DiffUtil.calculateDiff() directly is synchronous on whatever thread you call it from — for large lists that O(N+D²) work must be pushed off the main thread yourself, then dispatched back via dispatchUpdatesTo(adapter). ListAdapter<T,VH> wraps AsyncListDiffer, which runs the diff on a background executor automatically and posts the result to the main thread for you — you just call submitList().

class PostDiffCallback : DiffUtil.ItemCallback<Post>() {
    // stable id — NOT position, NOT object equality
    override fun areItemsTheSame(old: Post, new: Post) = old.id == new.id
    override fun areContentsTheSame(old: Post, new: Post) = old == new
}

class PostAdapter : ListAdapter<Post, PostAdapter.VH>(PostDiffCallback()) {
    override fun onBindViewHolder(holder: VH, position: Int) = holder.bind(getItem(position))
}

// diffs on a background executor automatically, dispatches result to main thread
adapter.submitList(newPosts.toList()) // new instance — never mutate in place
Q13ViewPager2 vs the old ViewPager vs a plain RecyclerView — what's actually different under the hood?Medium

The key fact: ViewPager2 is built on top of RecyclerView internally — it hosts a RecyclerView with a LinearLayoutManager and a snap-helper-style paging behavior wired underneath its public API. That single detail is why it gets a whole set of capabilities for free that the old ViewPager never had: RTL support (from the LayoutManager's reverseLayout handling), vertical orientation (just orientation = ORIENTATION_VERTICAL), DiffUtil-based updates (because the adapter is a normal RecyclerView.Adapter, you can use ListAdapter instead of blunt notifyDataSetChanged()), and standard ViewHolder recycling through the same scrap/cache/pool tiers instead of ViewPager's own ad-hoc instantiateItem/destroyItem lifecycle.

The old ViewPager was a bespoke ViewGroup driven by PagerAdapter (or FragmentPagerAdapter/FragmentStatePagerAdapter) — no RTL, no vertical paging, no DiffUtil; refreshing content required the POSITION_NONE trick to force a full recreate.

class OnboardingAdapter(fa: FragmentActivity) : FragmentStateAdapter(fa) {
    override fun getItemCount() = pages.size
    override fun createFragment(position: Int) = pages[position]
}
viewPager2.adapter = OnboardingAdapter(this)
viewPager2.orientation = ViewPager2.ORIENTATION_VERTICAL // free, thanks to LinearLayoutManager underneath
💡 Reach for a plain RecyclerView + PagerSnapHelper instead of ViewPager2 when you need to peek adjacent pages, custom snap positions (start/center, not just full-page), variable page widths, or mixed view types in one list — ViewPager2 assumes each page fills the whole viewport on snap.

Performance Diagnostics Toolchain

Q14Perfetto, Layout Inspector, and StrictMode — what does each one actually catch, and when do you reach for which?Medium

These three tools sit at different points in the development cycle and answer different questions:

Perfetto / Systrace

System-wide trace: CPU scheduling per thread, SurfaceFlinger's frame timeline, RenderThread activity. Answers "why was this specific frame slow" — pinpoints which phase (input, animation, traversal, draw, sync, GPU) ate the budget. Use once you already know jank exists and need the root cause.

Layout Inspector

Live view hierarchy attached to a running app, no rebuild needed (API 29+): resolved dimensions, constraints, a 3D exploded view of the stack. Answers "why does this screen have too many/overlapping views" — the tool for hunting deep hierarchies and overdraw sources.

StrictMode

In-process policy checks (thread + VM policy) that fire the instant a violation happens in a debug build. Answers "catch this before it's a perf bug at all" — disk/network on main thread, leaked Closeables, leaked Activity/Fragment references.

// Custom Perfetto trace section — shows up as a named block in the timeline
Trace.beginSection("loadFeed")
try { /* expensive work */ } finally { Trace.endSection() }

// StrictMode — fires the instant a violation happens, debug builds only
if (BuildConfig.DEBUG) {
    StrictMode.setThreadPolicy(StrictMode.ThreadPolicy.Builder()
        .detectNetwork().detectDiskReads().penaltyLog().build())
    StrictMode.setVmPolicy(StrictMode.VmPolicy.Builder()
        .detectLeakedClosableObjects().penaltyLog().build())
}
✓ Default flow: StrictMode always on in debug (catches issues as you code) → Layout Inspector when a screen feels heavy → Perfetto when jank is reproducible and you need the exact culprit phase. For CI regression tracking, Macrobenchmark's FrameTimingMetric asserts frame timing automatically, backed by the same Perfetto data.
