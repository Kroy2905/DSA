🏛 Architecture — Interview Questions

MVVM, MVI, Clean Architecture, Repository pattern, ViewModel, State management — Google expects you to justify every architectural decision.

Architecture Patterns

Q1Compare MVVM, MVP, and MVI — when would you choose each?Hard

MVVM, MVP, and MVI all exist to pull business/presentation logic out of the Activity or Fragment so the View stays dumb and the logic stays testable, but they differ in how tightly the View is coupled to that logic and how state travels between them. Interviewers ask this to see whether you can justify an architectural choice with real trade-offs instead of just reciting three acronyms — there's no single "correct" answer, only the one that fits the screen's complexity and how much determinism the team needs. MVVM keeps the View and ViewModel decoupled through observable state (LiveData/StateFlow) and is Google's default recommendation because it maps cleanly onto Jetpack. MVP gives a Presenter a direct reference to a View interface — simple to reason about, but the two are now bidirectionally coupled, which makes the View harder to fake in tests. MVI goes further than either by funneling every change through one immutable state object and a strict Intent → Model → View loop, trading extra boilerplate for a fully deterministic, replayable UI — worth it on screens with many interacting states, overkill for a simple form.

MVVM

View observes ViewModel state. ViewModel doesn't know about View. Uses LiveData/StateFlow. Default recommendation for Android (Google). Best for: most apps, especially with Jetpack.

MVP

Presenter has direct reference to View interface. Bidirectional — tight coupling. Good: simple screens, legacy codebases. Bad: boilerplate, hard to test without mocking View.

MVI

Unidirectional: Intent → Model → View. Single immutable state, one-way data flow, deterministic. Best for: complex UIs, screens with many states, real-time updates. Harder to set up.

// MVVM — ViewModel exposes state, View observes
class LoginViewModel : ViewModel() {
    private val _uiState = MutableStateFlow(LoginUiState())
    val uiState: StateFlow<LoginUiState> = _uiState.asStateFlow()

    fun login(email: String, password: String) {
        _uiState.update { it.copy(isLoading = true) }
        viewModelScope.launch {
            val result = repository.login(email, password)
            _uiState.update { it.copy(isLoading = false, user = result) }
        }
    }
}

// MVI — Single sealed intent, reducer pattern
sealed class LoginIntent {
    data class Login(val email: String, val password: String) : LoginIntent()
    object Logout : LoginIntent()
}
fun processIntent(intent: LoginIntent) { /* reduces state */ }
Q2Explain Clean Architecture in Android — layers, dependencies, why each existsHard

Clean Architecture organizes an app into concentric layers — Presentation, Domain, and Data — governed by one strict rule: dependencies only ever point inward, and the innermost layer, Domain, doesn't know the outer layers exist at all. Interviewers ask this to check that you understand why the layers exist, not just their names: the payoff is that business logic in Domain is plain Kotlin with zero Android, Room, or Retrofit imports, so it can be unit-tested in milliseconds and reused no matter how the UI is built or where the data comes from. Presentation (Activity/Fragment/Compose plus ViewModel) depends inward on Domain to run use cases; Data (Room, Retrofit/Ktor) also depends inward on Domain, but only to implement the repository interface that Domain declares — Domain itself depends on nothing. Concretely: Entities and UseCases and a Repository interface live in Domain, a RepositoryImpl that actually talks to Room/Retrofit lives in Data, and the ViewModel calls the UseCase — never the repository or a data source directly — which is what keeps the dependency arrow pointing the right way.

// Dependency rule: outer layers depend on inner, never inward
// Presentation → Domain ← Data

// DOMAIN LAYER (pure Kotlin, no Android dependencies)
data class User(val id: String, val name: String) // Entity

interface UserRepository { // Repository interface
    suspend fun getUser(id: String): User
}

class GetUserUseCase(private val repo: UserRepository) { // UseCase
    suspend operator fun invoke(id: String): User = repo.getUser(id)
}

// DATA LAYER (implements domain interfaces)
class UserRepositoryImpl(
    private val api: UserApi,    // remote data source
    private val dao: UserDao     // local data source
) : UserRepository {
    override suspend fun getUser(id: String): User {
        return dao.getUser(id) ?: api.fetchUser(id).also { dao.insert(it) }
    }
}

// PRESENTATION LAYER (MVVM with ViewModel)
class UserViewModel(private val getUser: GetUserUseCase) : ViewModel() {
    fun loadUser(id: String) = viewModelScope.launch {
        val user = getUser(id) // calls UseCase, not repository directly
    }
}

Why UseCases? Single responsibility — each use case does ONE thing. Reusable across ViewModels. Easy to unit test (pure Kotlin, no Android). Encapsulates business logic away from UI.

✓ Testability is the killer benefit: domain layer has zero Android imports — test with plain JUnit, no mocking framework needed.
Q3Why does ViewModel survive configuration changes? How is it implemented?Hard

When a configuration change occurs (rotation, language change), Android calls onDestroy() and recreates the Activity. But before destroying, it calls onRetainNonConfigurationInstance() internally and saves the ViewModelStore.

The ViewModelStore is a HashMap kept alive by the Activity's NonConfigurationInstances. The new Activity receives the same ViewModelStore, so ViewModelProvider.get() returns the existing ViewModel instead of creating a new one.

// Under the hood (simplified)
class ViewModelStore {
    private val map = HashMap<String, ViewModel>()
    fun put(key: String, vm: ViewModel) = map.put(key, vm)
    fun get(key: String) = map[key]
    fun clear() = map.values.forEach { it.onCleared() }
    // clear() called when user FINISHES the activity (not on rotation)
}

// ViewModelProvider uses the store:
val viewModel = ViewModelProvider(this)[MyViewModel::class.java]
// First call: creates new ViewModel, stores it
// After rotation: returns SAME ViewModel from store

ViewModel's onCleared() is called only when the Activity is truly finishing (user pressed back, finish() called) — not on rotation.

Q4LiveData vs StateFlow vs SharedFlow — which to use when and why?Hard

LiveData, StateFlow, and SharedFlow are all ways to expose observable state or events from a ViewModel to the UI, but they differ in lifecycle-awareness, threading, and — the detail that actually matters day to day — whether they replay their last value to a subscriber that joins late. Interviewers ask this because picking the wrong one is a real, recurring bug source: back a one-time event with something that replays, and it fires again after every rotation; back continuous UI state with something that doesn't replay, and a screen redrawn after a config change shows nothing until the next update arrives. LiveData is the original Android-lifecycle-aware holder — safe by default, but confined to the main thread with limited operators, which is why newer code favors Kotlin Flow. StateFlow is hot and always holds a value, replaying it to every new collector, which makes it the natural fit for continuous UI state. SharedFlow is also hot but has no required initial value and configurable replay, so with replay = 0 it's the right tool for one-shot events like navigation or a toast that shouldn't repeat.

LiveData

Lifecycle-aware. Auto-disposes. Only on main thread. Limited operators. Good for: UI state in legacy code with Views. Bad: no backpressure, can't do complex transformations.

StateFlow

Hot, always has value, replays last to new subscribers. Requires CoroutineScope. Works on any thread. Good for: UI state in MVVM (replaces LiveData). Must collect with lifecycle awareness.

SharedFlow

Hot, no initial value, configurable replay. Good for: one-time events (navigation, toasts), events that shouldn't be replayed to late subscribers.

class MyViewModel : ViewModel() {
    // StateFlow for UI state — replays last state to new observers
    private val _uiState = MutableStateFlow(UiState())
    val uiState = _uiState.asStateFlow()

    // SharedFlow for events — don't replay old navigation events
    private val _events = MutableSharedFlow<UiEvent>()
    val events = _events.asSharedFlow()

    fun onLoginSuccess() {
        _events.tryEmit(UiEvent.NavigateToHome) // one-time event
    }
}

// In Fragment — collect with lifecycle awareness
viewLifecycleOwner.lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        // Suspends when STOPPED, resumes when STARTED
        viewModel.uiState.collect { state -> renderUi(state) }
    }
}
⚠ Never use lifecycleScope.launch { flow.collect {} } directly — it doesn't auto-cancel when app is backgrounded. Always use repeatOnLifecycle(STARTED) or flowWithLifecycle.
Q5What is the Repository pattern? What problem does it solve?Medium

Repository is an abstraction layer between data sources and the rest of the app. It decides where data comes from (network, cache, database) — the ViewModel doesn't care.

class UserRepository(
    private val remoteSource: UserRemoteDataSource,
    private val localSource: UserLocalDataSource
) {
    fun getUsers(): Flow<List<User>> = flow {
        // 1. Emit cached data immediately
        val cached = localSource.getUsers()
        if (cached.isNotEmpty()) emit(cached)

        // 2. Fetch fresh data
        val fresh = remoteSource.fetchUsers()

        // 3. Cache and emit fresh data
        localSource.insertAll(fresh)
        emit(fresh)
    }
}

// ViewModel just asks repository — doesn't know about network/DB
class UsersViewModel(private val repo: UserRepository) : ViewModel() {
    val users = repo.getUsers().stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), emptyList())
}

Benefits: Single source of truth · Easy to switch data sources · Testable (mock the repository) · Consistent data strategy across app

Q6How do you handle one-time events (navigation, toasts) in MVVM to avoid issues on rotation?Hard

StateFlow and LiveData are both built to replay their current value to any new subscriber, which is exactly right for state — a rotated screen needs its data back — but wrong for a one-time event like "navigate to this screen" or "show this toast": if the event is stored the same way as state, the new subscriber created after rotation receives it again and the navigation or toast fires a second time for something the user already saw. The fix is to use a stream that only delivers to whoever is actively listening at the moment of emission, so a fresh subscriber after rotation simply gets nothing. There are a few ways to build that:

// Option 1: SharedFlow with replay=0 (won't replay to new subscribers)
private val _events = MutableSharedFlow<UiEvent>(replay = 0)
val events: SharedFlow<UiEvent> = _events.asSharedFlow()

// Option 2: Channel (delivers to one consumer, drops if nobody listening)
private val _events = Channel<UiEvent>(Channel.BUFFERED)
val events: Flow<UiEvent> = _events.receiveAsFlow()

// Option 3: Wrapper class (old approach, works with LiveData)
class Event<T>(private val content: T) {
    private var hasBeenHandled = false
    fun getContentIfNotHandled() = if (!hasBeenHandled) { hasBeenHandled = true; content } else null
}

// Google's current recommendation: use sealed class + Channel
sealed class UiEvent {
    data class NavigateTo(val route: String) : UiEvent()
    data class ShowToast(val message: String) : UiEvent()
    object Logout : UiEvent()
}
Q7What is Unidirectional Data Flow (UDF), and how does it apply beyond MVI?Hard

UDF is the principle that events flow up, state flows down, through exactly one channel each. The View sends events upward to whatever owns the logic; that owner is the only place allowed to produce a new state; the new state flows back down for the View to render. The View never mutates state itself — it's a pure function of whatever state it's handed. MVI is just one formalized, type-enforced implementation of this — the principle itself is bigger and applies to any architecture.

Contrast this with two-way data binding (e.g. XML's android:text="@={viewModel.text}"), where the View can write directly into the bound property. Now there are two writers to the same value, and when a bug report says "this field shows the wrong value," you can't answer by reading one function — you have to trace every binding that could have written to it, in what order, on what thread.

Two-way binding

Multiple writers to the same state. Changes can originate from the View directly. No single place to log a state change — you trace backward through bindings.

Unidirectional (UDF)

Exactly one writer. Every change is the result of a named event — trivially loggable, and testable with plain Kotlin, no live View needed.

Note that MVVM with StateFlow already follows UDF, with no formal reducer required — the loop has the same shape:

class CounterViewModel : ViewModel() {
    private val _uiState = MutableStateFlow(CounterState())
    val uiState: StateFlow<CounterState> = _uiState.asStateFlow() // read-only — event UP, state DOWN

    fun onIncrementClicked() {                         // event from View
        _uiState.update { it.copy(count = it.count + 1) } // single mutation point
    }
}

MVI makes this explicit with a sealed Intent instead of arbitrary function calls, and a pure reduce(state, intent) instead of scattered .update{} calls (see Q10) — but the underlying shape, events up / state down / single source of truth, is identical.

✓ UDF is not "use StateFlow." You can violate it while using StateFlow — e.g. exposing a mutable flow publicly so the View writes to it directly. The type doesn't guarantee the principle; discipline does.
Q8Why modularize an app into feature/core Gradle modules? What does it actually buy you?Medium

A multi-module project splits :app into many smaller modules, usually of two kinds: feature modules (:feature:login, :feature:checkout — one per user-facing flow, owns its UI + ViewModel) and core modules (:core:network, :core:database, :core:designsystem — shared, low-level, no feature logic).

Build time: with one giant :app module, any code change forces Gradle to recompile the whole app. With modules, Gradle's incremental build only recompiles the module that changed plus whatever depends on it — untouched modules are pulled straight from cache — and independent modules compile in parallel across cores. On a large app this is the difference between a multi-minute and a multi-second incremental build.

Enforced boundaries: boundaries kept only by convention (a lint rule, a wiki page) get violated under deadline pressure. Module visibility makes the violation a compile error, not a code-review nitpick:

// :feature:login/build.gradle.kts
dependencies {
    implementation(project(":core:network"))   // no dependency on :feature:profile
}

// inside :feature:login source — this is a compile error, not a warning:
import com.app.feature.profile.ProfileViewModel // ✗ unresolved reference

Using implementation (not api) also keeps a dependency off the classpath of whatever depends on this module, so :app can't reach into :core:network transitively through :feature:login either.

⚠ If two features both need each other, that's a cycle waiting to happen. Fix by extracting the shared piece into a :core module both depend on downward — never add a direct feature→feature dependency.
Q9Walk through Dependency Inversion Principle (DIP) concretely in an Android data layerHard

DIP (the "D" in SOLID) says high-level modules shouldn't depend on low-level modules — both should depend on an abstraction. In Android this is exactly the domain/data split: the interface (UserRepository) lives in the domain module and describes only what is needed; the implementation lives in data and is the only place that imports Room or Retrofit types.

Without DIP, the "natural" arrow would be domain → data (business logic needs data, so it seems like it should depend on it). DIP flips that: data depends on domain by implementing domain's interface, so domain has zero compile-time dependency on Room/Retrofit at all — its build.gradle.kts doesn't even list those artifacts.

// DOMAIN — pure Kotlin, no Room/Retrofit imports
interface UserRepository { suspend fun getUser(id: String): User }

// DATA — the only module that knows about Retrofit
class RetrofitUserRepository(private val api: UserApi) : UserRepository {
    override suspend fun getUser(id: String) = api.fetchUser(id).toDomain()
}

// TEST — a fake with the same contract, no framework at all
class FakeUserRepository : UserRepository {
    val users = mutableMapOf<String, User>()
    override suspend fun getUser(id: String) = users.getValue(id)
}

Why this specifically enables painless swaps: GetUserUseCase and the ViewModel depend only on the UserRepository interface, so tests hand them FakeUserRepository above with zero mocking framework — the class under test literally cannot tell the difference. The same reasoning covers a Retrofit→Ktor migration: only the impl class changes; domain and presentation never recompile differently, because they only ever referenced the interface, whose contract never moved.

✓ The key word is inversion. The intuitive direction (domain needs data, so domain→data) gets flipped (data→domain) by having data implement an interface domain owns — that's what keeps domain a stable, framework-free core.
Q10What is the reducer pattern, and why is it easier to test than imperative state updates?Hard

In MVI-style architectures, every state transition for a screen is described by one pure reducer function: (State, Action) -> State. "Pure" means: no network calls, no logging, no navigation, no mutation of anything outside its own return value — given the same inputs it always returns the same output, synchronously.

sealed class CounterAction { object Increment : CounterAction(); object Reset : CounterAction() }

fun reduce(state: CounterState, action: CounterAction): CounterState = when (action) {
    is CounterAction.Increment -> state.copy(count = state.count + 1)
    is CounterAction.Reset -> CounterState()
    // sealed class → compiler error if a new Action isn't handled here
}

Why this is trivially testable: a test just calls reduce(givenState, someAction) and asserts on the return value — no runTest, no TestDispatcher, no mocked repository, no coroutine at all, because the function has no dependencies to fake.

Scattered .update{} calls

Transition logic lives inside N different ViewModel functions, interleaved with suspend calls and side effects. Knowing every state the screen can reach means reading the whole ViewModel. Testing one transition means calling the full function and mocking its dependencies.

Centralized reduce()

Every transition lives in one exhaustive when block. Reading reduce() top to bottom is the full state machine of the screen — and it's the one place a logging/replay middleware needs to wrap to get a complete audit trail.

Q11In a reducer-based (MVI) screen, how do you separate one-time side effects from continuous state?Hard

A reducer-driven screen needs two separate streams, and conflating them is the most common MVI bug:

  • State — continuous, always has a current value, must be re-deliverable (rotation needs the latest state again to redraw). Modeled with StateFlow.
  • Effect — navigate away, show a Snackbar, trigger haptics. Must be consumed exactly once. If it lived in State, a rotation would re-collect it and fire the navigation/Snackbar again — the same bug covered in Q6, now framed for MVI.

The fix reuses the Q6 primitives (Channel or a zero-replay SharedFlow), wired specifically so the pure reduce() never itself emits an effect (that would make it impure and break Q10's testability). The orchestrating process(intent) calls reduce() for state, and separately — outside the reducer — decides whether to also send an effect:

private val _state = MutableStateFlow(CheckoutState())
val state: StateFlow<CheckoutState> = _state.asStateFlow()        // replayed on rotation

private val _effect = Channel<CheckoutEffect>(Channel.BUFFERED)
val effect: Flow<CheckoutEffect> = _effect.receiveAsFlow()      // consumed once, never replayed

fun process(intent: CheckoutIntent) {
    _state.update { reduce(it, intent) }                    // pure — state only
    if (intent is CheckoutIntent.SubmitOrder) {
        _effect.trySend(CheckoutEffect.NavigateToConfirmation) // side effect, outside reduce()
    }
}
↔ See Q6 for the full Channel vs SharedFlow(replay=0) vs legacy Event-wrapper comparison — the same options apply here; MVI just adds the rule that the pure reduce() is never the one emitting them.
