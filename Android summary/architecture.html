🏛 Architecture — Interview Questions

MVVM, MVI, Clean Architecture, Repository pattern, ViewModel, State management — Google expects you to justify every architectural decision.

Architecture Patterns

Q1Compare MVVM, MVP, and MVI — when would you choose each?Hard

MVVM

View observes ViewModel state. ViewModel doesn't know about View. Uses LiveData/StateFlow. Default recommendation for Android (Google). Best for: most apps, especially with Jetpack.

MVP

Presenter has direct reference to View interface. Bidirectional — tight coupling. Good: simple screens, legacy codebases. Bad: boilerplate, hard to test without mocking View.

MVI

Unidirectional: Intent → Model → View. Single immutable state, one-way data flow, deterministic. Best for: complex UIs, screens with many states, real-time updates. Harder to set up.

// MVVM — ViewModel exposes state, View observes
class LoginViewModel : ViewModel() {
    private val _uiState = MutableStateFlow(LoginUiState())
    val uiState: StateFlow<LoginUiState> = _uiState.asStateFlow()

    fun login(email: String, password: String) {
        _uiState.update { it.copy(isLoading = true) }
        viewModelScope.launch {
            val result = repository.login(email, password)
            _uiState.update { it.copy(isLoading = false, user = result) }
        }
    }
}

// MVI — Single sealed intent, reducer pattern
sealed class LoginIntent {
    data class Login(val email: String, val password: String) : LoginIntent()
    object Logout : LoginIntent()
}
fun processIntent(intent: LoginIntent) { /* reduces state */ }
Q2Explain Clean Architecture in Android — layers, dependencies, why each existsHard 
// Dependency rule: outer layers depend on inner, never inward
// Presentation → Domain ← Data

// DOMAIN LAYER (pure Kotlin, no Android dependencies)
data class User(val id: String, val name: String) // Entity

interface UserRepository { // Repository interface
    suspend fun getUser(id: String): User
}

class GetUserUseCase(private val repo: UserRepository) { // UseCase
    suspend operator fun invoke(id: String): User = repo.getUser(id)
}

// DATA LAYER (implements domain interfaces)
class UserRepositoryImpl(
    private val api: UserApi,    // remote data source
    private val dao: UserDao     // local data source
) : UserRepository {
    override suspend fun getUser(id: String): User {
        return dao.getUser(id) ?: api.fetchUser(id).also { dao.insert(it) }
    }
}

// PRESENTATION LAYER (MVVM with ViewModel)
class UserViewModel(private val getUser: GetUserUseCase) : ViewModel() {
    fun loadUser(id: String) = viewModelScope.launch {
        val user = getUser(id) // calls UseCase, not repository directly
    }
}

Why UseCases? Single responsibility — each use case does ONE thing. Reusable across ViewModels. Easy to unit test (pure Kotlin, no Android). Encapsulates business logic away from UI.

✓ Testability is the killer benefit: domain layer has zero Android imports — test with plain JUnit, no mocking framework needed.
Q3Why does ViewModel survive configuration changes? How is it implemented?Hard

When a configuration change occurs (rotation, language change), Android calls onDestroy() and recreates the Activity. But before destroying, it calls onRetainNonConfigurationInstance() internally and saves the ViewModelStore.

The ViewModelStore is a HashMap kept alive by the Activity's NonConfigurationInstances. The new Activity receives the same ViewModelStore, so ViewModelProvider.get() returns the existing ViewModel instead of creating a new one.

// Under the hood (simplified)
class ViewModelStore {
    private val map = HashMap<String, ViewModel>()
    fun put(key: String, vm: ViewModel) = map.put(key, vm)
    fun get(key: String) = map[key]
    fun clear() = map.values.forEach { it.onCleared() }
    // clear() called when user FINISHES the activity (not on rotation)
}

// ViewModelProvider uses the store:
val viewModel = ViewModelProvider(this)[MyViewModel::class.java]
// First call: creates new ViewModel, stores it
// After rotation: returns SAME ViewModel from store

ViewModel's onCleared() is called only when the Activity is truly finishing (user pressed back, finish() called) — not on rotation.

Q4LiveData vs StateFlow vs SharedFlow — which to use when and why?Hard

LiveData

Lifecycle-aware. Auto-disposes. Only on main thread. Limited operators. Good for: UI state in legacy code with Views. Bad: no backpressure, can't do complex transformations.

StateFlow

Hot, always has value, replays last to new subscribers. Requires CoroutineScope. Works on any thread. Good for: UI state in MVVM (replaces LiveData). Must collect with lifecycle awareness.

SharedFlow

Hot, no initial value, configurable replay. Good for: one-time events (navigation, toasts), events that shouldn't be replayed to late subscribers.

class MyViewModel : ViewModel() {
    // StateFlow for UI state — replays last state to new observers
    private val _uiState = MutableStateFlow(UiState())
    val uiState = _uiState.asStateFlow()

    // SharedFlow for events — don't replay old navigation events
    private val _events = MutableSharedFlow<UiEvent>()
    val events = _events.asSharedFlow()

    fun onLoginSuccess() {
        _events.tryEmit(UiEvent.NavigateToHome) // one-time event
    }
}

// In Fragment — collect with lifecycle awareness
viewLifecycleOwner.lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        // Suspends when STOPPED, resumes when STARTED
        viewModel.uiState.collect { state -> renderUi(state) }
    }
}
⚠ Never use lifecycleScope.launch { flow.collect {} } directly — it doesn't auto-cancel when app is backgrounded. Always use repeatOnLifecycle(STARTED) or flowWithLifecycle.
Q5What is the Repository pattern? What problem does it solve?Medium

Repository is an abstraction layer between data sources and the rest of the app. It decides where data comes from (network, cache, database) — the ViewModel doesn't care.

class UserRepository(
    private val remoteSource: UserRemoteDataSource,
    private val localSource: UserLocalDataSource
) {
    fun getUsers(): Flow<List<User>> = flow {
        // 1. Emit cached data immediately
        val cached = localSource.getUsers()
        if (cached.isNotEmpty()) emit(cached)

        // 2. Fetch fresh data
        val fresh = remoteSource.fetchUsers()

        // 3. Cache and emit fresh data
        localSource.insertAll(fresh)
        emit(fresh)
    }
}

// ViewModel just asks repository — doesn't know about network/DB
class UsersViewModel(private val repo: UserRepository) : ViewModel() {
    val users = repo.getUsers().stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), emptyList())
}

Benefits: Single source of truth · Easy to switch data sources · Testable (mock the repository) · Consistent data strategy across app

Q6How do you handle one-time events (navigation, toasts) in MVVM to avoid issues on rotation?Hard

This is a known problem: if you use StateFlow/LiveData for events and the user rotates, the event gets replayed. Solutions:

// Option 1: SharedFlow with replay=0 (won't replay to new subscribers)
private val _events = MutableSharedFlow<UiEvent>(replay = 0)
val events: SharedFlow<UiEvent> = _events.asSharedFlow()

// Option 2: Channel (delivers to one consumer, drops if nobody listening)
private val _events = Channel<UiEvent>(Channel.BUFFERED)
val events: Flow<UiEvent> = _events.receiveAsFlow()

// Option 3: Wrapper class (old approach, works with LiveData)
class Event<T>(private val content: T) {
    private var hasBeenHandled = false
    fun getContentIfNotHandled() = if (!hasBeenHandled) { hasBeenHandled = true; content } else null
}

// Google's current recommendation: use sealed class + Channel
sealed class UiEvent {
    data class NavigateTo(val route: String) : UiEvent()
    data class ShowToast(val message: String) : UiEvent()
    object Logout : UiEvent()
}
