💉 Dependency Injection — Interview Questions

Hilt is Google's recommended DI framework. Know why DI exists, how Hilt works, and the Dagger 2 concepts underneath it.

Why Dependency Injection?

Q1What is Dependency Injection and why do we need it?Easy

DI = providing a class with its dependencies instead of the class creating them itself. Turns val repo = UserRepositoryImpl() inside a class into receiving it from outside.

// WITHOUT DI: tightly coupled, impossible to test
class UserViewModel {
    private val repo = UserRepositoryImpl(// creates its own — can't swap for test
        RetrofitClient.create(UserApi::class.java),
        AppDatabase.getInstance(context).userDao()
    )
}

// WITH DI: loosely coupled, fully testable
class UserViewModel(private val repo: UserRepository) : ViewModel() {
    // repo is an interface — test can inject MockUserRepository
}

// Benefits:
// 1. Testability: inject mocks/fakes instead of real implementations
// 2. Flexibility: swap implementations (prod vs debug vs test)
// 3. Single responsibility: class doesn't manage lifecycle of its dependencies
// 4. Reusability: dependencies shared across classes (Singleton pattern managed for you)

Hilt (Google's Recommended DI)

Q2Explain Hilt setup and all its core annotationsHard 
// 1. Application — entry point
@HiltAndroidApp
class MyApp : Application()

// 2. Android class — inject into Activities, Fragments, Services, etc.
@AndroidEntryPoint
class MainActivity : AppCompatActivity() {
    @Inject lateinit var analytics: Analytics // field injection
}

// 3. ViewModel
@HiltViewModel
class UserViewModel @Inject constructor(
    private val repo: UserRepository  // constructor injection
) : ViewModel()

// 4. Module — tells Hilt HOW to provide types it can't figure out itself
@Module
@InstallIn(SingletonComponent::class) // available app-wide as Singleton
object NetworkModule {

    @Provides
    @Singleton  // only one instance created
    fun provideRetrofit(): Retrofit = Retrofit.Builder()
        .baseUrl(BuildConfig.API_URL)
        .addConverterFactory(GsonConverterFactory.create())
        .build()

    @Provides
    @Singleton
    fun provideUserApi(retrofit: Retrofit): UserApi =  // Hilt provides retrofit
        retrofit.create(UserApi::class.java)
}

// 5. Binds — tell Hilt which implementation to use for an interface
@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {
    @Binds
    @Singleton
    abstract fun bindUserRepository(impl: UserRepositoryImpl): UserRepository
    // @Provides (object): use for 3rd-party classes (Retrofit, Room)
    // @Binds (abstract): use for your own interface→impl mappings (more efficient)
}
Q3Explain Hilt components and scopes — which scope for each use case?Hard

Hilt has a hierarchy of Components, each with its own scope and lifetime:

Component Hierarchy

  • SingletonComponent (Application)
  • ActivityRetainedComponent (ViewModel scope)
  • ActivityComponent (Activity)
  • FragmentComponent (Fragment)
  • ViewComponent (View)
  • ServiceComponent (Service)

Scope Annotations

  • @Singleton — one per app
  • @ActivityRetainedScoped — survives rotation
  • @ActivityScoped — one per Activity
  • @FragmentScoped — one per Fragment
  • @ViewScoped — one per View
// @Singleton: shared database, shared network client
@Singleton class UserRepository @Inject constructor(…)

// @ActivityScoped: analytics tied to one Activity session
@ActivityScoped class ScreenAnalytics @Inject constructor(…)

// @ViewModelScoped (ActivityRetainedScoped internally)
// Use for objects that should survive rotation but not be singletons
@ViewModelScoped class SearchManager @Inject constructor(…)

// Rule: a scoped object can only inject objects of same or broader scope
// @FragmentScoped can inject @Singleton, @ActivityScoped, @FragmentScoped
// @FragmentScoped CANNOT inject @ViewModelScoped (narrower)

// Qualifiers: when you have multiple bindings of same type
@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class AuthInterceptorOkHttpClient

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class PlainOkHttpClient

@Provides @AuthInterceptorOkHttpClient
fun provideAuthClient(interceptor: AuthInterceptor) = OkHttpClient.Builder().addInterceptor(interceptor).build()

@Provides @PlainOkHttpClient
fun providePlainClient() = OkHttpClient.Builder().build()

Dagger 2 (Hilt is built on it)

Q4Explain core Dagger 2 concepts: @Component, @Module, @Inject, @ProvidesHard 
// @Inject on constructor: Dagger knows how to create this class
class UserRepository @Inject constructor(
    private val api: UserApi,   // Dagger provides these
    private val dao: UserDao
)

// @Module: provides things Dagger can't create via @Inject
@Module
class NetworkModule {
    @Provides // Dagger calls this to get an OkHttpClient
    fun provideOkHttpClient(): OkHttpClient = OkHttpClient.Builder().build()
}

// @Component: the bridge — connects modules to injection targets
// Dagger generates AppComponent_Impl at compile time
@Component(modules = [NetworkModule::class, DatabaseModule::class])
interface AppComponent {
    fun inject(activity: MainActivity)  // allows injection into MainActivity
    fun userRepository(): UserRepository  // expose to sub-components
}

// Hilt removes the need to write Components manually — it generates them
// This is Hilt's main advantage over raw Dagger 2

Koin (Lightweight Alternative)

Q5How does Koin work and how does it compare to Hilt/Dagger?Medium 
// Koin: service locator + DI without code generation
// Resolved at RUNTIME (not compile time like Dagger/Hilt)

val appModule = module {
    single { OkHttpClient.Builder().build() }   // singleton
    single { Retrofit.Builder().client(get()).build() } // get() resolves OkHttpClient
    factory { UserRepositoryImpl(get(), get()) } // new instance each time
    viewModel { UserViewModel(get()) }
}

// In Application.onCreate():
startKoin {
    androidContext(this@MyApp)
    modules(appModule)
}

// In Fragment/Activity:
val viewModel: UserViewModel by viewModel()
val repo: UserRepository by inject()

Koin Pros

No annotation processing. Faster build times. Kotlin DSL. Easy to learn. Good for small-medium projects.

Koin Cons

Runtime failures (errors discovered at runtime, not compile time). No scope hierarchy. Slightly slower at runtime due to reflection.

💡 Google recommendation: Hilt for new projects (compile-time safety, works well with Jetpack). Koin is fine for smaller teams or projects prioritizing build speed.
Q6How do you test with Hilt? How do you replace modules in tests?Hard 
// Replace module in tests with @TestInstallIn
@Module
@TestInstallIn(components = [SingletonComponent::class], replaces = [NetworkModule::class])
object FakeNetworkModule {
    @Provides
    fun provideFakeUserApi(): UserApi = FakeUserApi() // fake impl for tests
}

// HiltAndroidTest for instrumented tests
@HiltAndroidTest
class UserViewModelTest {
    @get:Rule
    val hiltRule = HiltAndroidRule(this)

    @Inject
    lateinit var viewModel: UserViewModel

    @Before
    fun setUp() { hiltRule.inject() }
}

// For unit tests (no Android): just inject via constructor manually
class UserViewModelUnitTest {
    private val fakeRepo = mockk<UserRepository>()
    private val viewModel = UserViewModel(fakeRepo) // no Hilt needed!
}
✓ Pure constructor injection (no @HiltViewModel needed) is the best approach for unit-testable ViewModels — Hilt just wires the real app, tests inject directly.
