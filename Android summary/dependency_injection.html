💉 Dependency Injection — Interview Questions

Hilt is Google's recommended DI framework. Know why DI exists, how Hilt works, and the Dagger 2 concepts underneath it.

Why Dependency Injection?

Q1What is Dependency Injection and why do we need it?Easy

DI = providing a class with its dependencies instead of the class creating them itself. Turns val repo = UserRepositoryImpl() inside a class into receiving it from outside.

// WITHOUT DI: tightly coupled, impossible to test
class UserViewModel {
    private val repo = UserRepositoryImpl(// creates its own — can't swap for test
        RetrofitClient.create(UserApi::class.java),
        AppDatabase.getInstance(context).userDao()
    )
}

// WITH DI: loosely coupled, fully testable
class UserViewModel(private val repo: UserRepository) : ViewModel() {
    // repo is an interface — test can inject MockUserRepository
}

// Benefits:
// 1. Testability: inject mocks/fakes instead of real implementations
// 2. Flexibility: swap implementations (prod vs debug vs test)
// 3. Single responsibility: class doesn't manage lifecycle of its dependencies
// 4. Reusability: dependencies shared across classes (Singleton pattern managed for you)

Hilt (Google's Recommended DI)

Q2Explain Hilt setup and all its core annotationsHard 
// 1. Application — entry point
@HiltAndroidApp
class MyApp : Application()

// 2. Android class — inject into Activities, Fragments, Services, etc.
@AndroidEntryPoint
class MainActivity : AppCompatActivity() {
    @Inject lateinit var analytics: Analytics // field injection
}

// 3. ViewModel
@HiltViewModel
class UserViewModel @Inject constructor(
    private val repo: UserRepository  // constructor injection
) : ViewModel()

// 4. Module — tells Hilt HOW to provide types it can't figure out itself
@Module
@InstallIn(SingletonComponent::class) // available app-wide as Singleton
object NetworkModule {

    @Provides
    @Singleton  // only one instance created
    fun provideRetrofit(): Retrofit = Retrofit.Builder()
        .baseUrl(BuildConfig.API_URL)
        .addConverterFactory(GsonConverterFactory.create())
        .build()

    @Provides
    @Singleton
    fun provideUserApi(retrofit: Retrofit): UserApi =  // Hilt provides retrofit
        retrofit.create(UserApi::class.java)
}

// 5. Binds — tell Hilt which implementation to use for an interface
@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {
    @Binds
    @Singleton
    abstract fun bindUserRepository(impl: UserRepositoryImpl): UserRepository
    // @Provides (object): use for 3rd-party classes (Retrofit, Room)
    // @Binds (abstract): use for your own interface→impl mappings (more efficient)
}
Q3Explain Hilt components and scopes — which scope for each use case?Hard

Hilt has a hierarchy of Components, each with its own scope and lifetime:

Component Hierarchy

  • SingletonComponent (Application)
  • ActivityRetainedComponent (ViewModel scope)
  • ActivityComponent (Activity)
  • FragmentComponent (Fragment)
  • ViewComponent (View)
  • ServiceComponent (Service)

Scope Annotations

  • @Singleton — one per app
  • @ActivityRetainedScoped — survives rotation
  • @ActivityScoped — one per Activity
  • @FragmentScoped — one per Fragment
  • @ViewScoped — one per View
// @Singleton: shared database, shared network client
@Singleton class UserRepository @Inject constructor(…)

// @ActivityScoped: analytics tied to one Activity session
@ActivityScoped class ScreenAnalytics @Inject constructor(…)

// @ViewModelScoped (ActivityRetainedScoped internally)
// Use for objects that should survive rotation but not be singletons
@ViewModelScoped class SearchManager @Inject constructor(…)

// Rule: a scoped object can only inject objects of same or broader scope
// @FragmentScoped can inject @Singleton, @ActivityScoped, @FragmentScoped
// @FragmentScoped CANNOT inject @ViewModelScoped (narrower)

// Qualifiers: when you have multiple bindings of same type
@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class AuthInterceptorOkHttpClient

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class PlainOkHttpClient

@Provides @AuthInterceptorOkHttpClient
fun provideAuthClient(interceptor: AuthInterceptor) = OkHttpClient.Builder().addInterceptor(interceptor).build()

@Provides @PlainOkHttpClient
fun providePlainClient() = OkHttpClient.Builder().build()

Dagger 2 (Hilt is built on it)

Q4Explain core Dagger 2 concepts: @Component, @Module, @Inject, @ProvidesHard 
// @Inject on constructor: Dagger knows how to create this class
class UserRepository @Inject constructor(
    private val api: UserApi,   // Dagger provides these
    private val dao: UserDao
)

// @Module: provides things Dagger can't create via @Inject
@Module
class NetworkModule {
    @Provides // Dagger calls this to get an OkHttpClient
    fun provideOkHttpClient(): OkHttpClient = OkHttpClient.Builder().build()
}

// @Component: the bridge — connects modules to injection targets
// Dagger generates AppComponent_Impl at compile time
@Component(modules = [NetworkModule::class, DatabaseModule::class])
interface AppComponent {
    fun inject(activity: MainActivity)  // allows injection into MainActivity
    fun userRepository(): UserRepository  // expose to sub-components
}

// Hilt removes the need to write Components manually — it generates them
// This is Hilt's main advantage over raw Dagger 2

Koin (Lightweight Alternative)

Q5How does Koin work and how does it compare to Hilt/Dagger?Medium 
// Koin: service locator + DI without code generation
// Resolved at RUNTIME (not compile time like Dagger/Hilt)

val appModule = module {
    single { OkHttpClient.Builder().build() }   // singleton
    single { Retrofit.Builder().client(get()).build() } // get() resolves OkHttpClient
    factory { UserRepositoryImpl(get(), get()) } // new instance each time
    viewModel { UserViewModel(get()) }
}

// In Application.onCreate():
startKoin {
    androidContext(this@MyApp)
    modules(appModule)
}

// In Fragment/Activity:
val viewModel: UserViewModel by viewModel()
val repo: UserRepository by inject()

Koin Pros

No annotation processing. Faster build times. Kotlin DSL. Easy to learn. Good for small-medium projects.

Koin Cons

Runtime failures (errors discovered at runtime, not compile time). No scope hierarchy. Slightly slower at runtime due to reflection.

💡 Google recommendation: Hilt for new projects (compile-time safety, works well with Jetpack). Koin is fine for smaller teams or projects prioritizing build speed.
Q6How do you test with Hilt? How do you replace modules in tests?Hard 
// Replace module in tests with @TestInstallIn
@Module
@TestInstallIn(components = [SingletonComponent::class], replaces = [NetworkModule::class])
object FakeNetworkModule {
    @Provides
    fun provideFakeUserApi(): UserApi = FakeUserApi() // fake impl for tests
}

// HiltAndroidTest for instrumented tests
@HiltAndroidTest
class UserViewModelTest {
    @get:Rule
    val hiltRule = HiltAndroidRule(this)

    @Inject
    lateinit var viewModel: UserViewModel

    @Before
    fun setUp() { hiltRule.inject() }
}

// For unit tests (no Android): just inject via constructor manually
class UserViewModelUnitTest {
    private val fakeRepo = mockk<UserRepository>()
    private val viewModel = UserViewModel(fakeRepo) // no Hilt needed!
}
✓ Pure constructor injection (no @HiltViewModel needed) is the best approach for unit-testable ViewModels — Hilt just wires the real app, tests inject directly.

Advanced Hilt Patterns

Q7How do multibinding (@IntoSet / @IntoMap) work, and when would you use them?Hard

Multibinding lets several separate @Binds/@Provides methods contribute to one collection instead of one implementation winning — Dagger merges them into a Set<T> or Map<K, T> that you inject as a whole. This is the standard shape for plugin-style architectures: a set of analytics trackers that should all fire on every event, or a map of feature-flag handlers looked up by key at runtime — new implementations register themselves in their own module without ever touching the consumer's code.

interface AnalyticsTracker { fun track(event: String) }

@Module @InstallIn(SingletonComponent::class)
abstract class AnalyticsModule {
    @Binds @IntoSet
    abstract fun bindFirebase(impl: FirebaseTracker): AnalyticsTracker

    @Binds @IntoSet
    abstract fun bindMixpanel(impl: MixpanelTracker): AnalyticsTracker
}

// Hilt now provides Set<AnalyticsTracker> containing BOTH implementations
class CompositeAnalytics @Inject constructor(
    private val trackers: Set<@JvmSuppressWildcards AnalyticsTracker>
) {
    fun trackEvent(event: String) = trackers.forEach { it.track(event) }
}

// @IntoMap works the same way but keyed: @Binds @IntoMap @StringKey("dark_mode") ...
// injected as Map<String, FeatureFlagHandler> and looked up by flag name at runtime

Built-in map keys

@StringKey, @IntKey, @LongKey, @ClassKey ship with Dagger; define a custom @MapKey for typed/enum keys.

Two gotchas

Kotlin's Set<out T> covariance needs @JvmSuppressWildcards to match Dagger's generated signature. An empty contribution set is also a compile error unless a @Multibinds declaration says empty is valid.

✓ Use case: a dynamic feature module or SDK contributes its own @IntoSet/@IntoMap binding without ever touching the core app's code — fully open for extension, closed for modification.
Q8What is assisted injection (@AssistedInject / @AssistedFactory) and when do you need it?Hard

Assisted injection solves the case where a class needs both Dagger-provided dependencies and a runtime value that isn't known until after the graph is built — e.g. an item ID only available once the user taps something. Without it, you'd either lose Dagger's dependency resolution by new-ing the class manually, or smuggle the runtime value in through a mutable field set after construction (reintroducing the same unsafe-ordering problem field injection has).

@AssistedFactory
interface ItemDetailsFetcherFactory {
    fun create(itemId: String): ItemDetailsFetcher
}

class ItemDetailsFetcher @AssistedInject constructor(
    @Assisted private val itemId: String,   // runtime-only
    private val api: ItemApi,                 // from the Dagger graph
    private val cache: ItemCache
) {
    suspend fun fetch(): Item = cache.get(itemId) ?: api.fetchItem(itemId)
}

// Consumer only ever holds the FACTORY — fully graph-provided, no reflection
class ItemViewModel @Inject constructor(
    private val fetcherFactory: ItemDetailsFetcherFactory
) : ViewModel() {
    fun fetcherFor(itemId: String): ItemDetailsFetcher = fetcherFactory.create(itemId)
}
💡 Dagger generates ItemDetailsFetcherFactory_Impl whose create(itemId) body is roughly new ItemDetailsFetcher(itemId, apiProvider.get(), cacheProvider.get()) — the assisted param passes straight through, the rest come from Providers captured when the factory was injected.

Rule of thumb: constructor needs a call-time value mixed with regular Dagger deps → @AssistedInject. All deps known up front → a plain @Inject constructor. No Dagger deps at all → just a regular factory, no annotations needed.

Q9What is @EntryPoint and when do you need EntryPointAccessors instead of normal injection?Medium

Hilt only knows how to inject into a fixed list of Android classes: Application, Activity, Fragment, View, Service, BroadcastReceiver (via @AndroidEntryPoint). ContentProvider is notably absent — it can be instantiated before Application.onCreate() runs, so Hilt can't guarantee the component graph is attached yet, and generates no base class for it. The same problem hits any class instantiated outside Hilt's control: a raw (non-@HiltWorker) Worker built by a third-party factory, or a class a library constructs via reflection. For these, @EntryPoint + EntryPointAccessors reach into the graph manually instead of relying on Hilt to push dependencies in.

@EntryPoint
@InstallIn(SingletonComponent::class)
interface ProviderEntryPoint {
    fun userRepository(): UserRepository
}

class MyContentProvider : ContentProvider() {
    override fun onCreate(): Boolean {
        val entryPoint = EntryPointAccessors.fromApplication(
            context!!.applicationContext, ProviderEntryPoint::class.java
        )
        val repo = entryPoint.userRepository()  // resolved straight from SingletonComponent
        return true
    }
}
💡 There's a matching accessor per component scope — fromApplication(), fromActivity(), fromFragment(), fromView(), fromService() — pick the one matching your @EntryPoint's @InstallIn target or you get a runtime IllegalStateException. Prefer @HiltWorker/HiltWorkerFactory for Workers when you control the setup — @EntryPoint is the escape hatch for when you don't.
Q10Field injection vs constructor injection — why prefer constructor injection, and when is field injection unavoidable?Medium

Constructor injection makes dependencies part of the object's required shape — you cannot construct the object without them, the compiler enforces it, and tests can just call the constructor with fakes (no Hilt, no reflection). Field injection is the fallback for classes the Android framework instantiates itself via a required no-arg constructor (reflection) — you can't add constructor parameters to something the OS creates, so Hilt can only assign a lateinit field after the object already exists.

// Constructor injection: impossible to create UserRepository without a UserApi
class UserRepository @Inject constructor(private val api: UserApi)
val repo = UserRepository(FakeUserApi()) // testable with zero Hilt

// Field injection: Hilt_MainActivity.onCreate() injects BEFORE your onCreate() body runs
@AndroidEntryPoint
class MainActivity : AppCompatActivity() {
    @Inject lateinit var analytics: Analytics // unset until Hilt's superclass injects it

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState) // safe to use analytics only after this line
        analytics.logScreenView("main")
    }
}
⚠ Reading a lateinit @Inject field from a property initializer or init {} block crashes with UninitializedPropertyAccessException — those run before onAttach()/the generated inject() call. Field injection is unavoidable for OS-instantiated classes, but it trades away the compile-time safety constructor injection gives everything else.
Q11What scoping bugs should you watch for, and how do Singleton→Activity leaks happen if Dagger checks scopes at compile time?Hard

Dagger/Hilt does catch the classic mistake — injecting a narrower-scoped dependency into a wider-scoped one — at compile time, because it can see every binding that flows through a constructor or @Provides/@Binds method. What it cannot see is a plain mutable field or setter assigned after both objects already exist — that's exactly how a @Singleton ends up holding a strong reference to an Activity long after that Activity should have been garbage-collected.

// Compile-time error: Dagger sees this — narrower scope injected into wider scope
@Singleton
class GlobalCache @Inject constructor(
    private val screenAnalytics: ScreenAnalytics // @ActivityScoped — narrower than GlobalCache!
) // error: ScreenAnalytics cannot be provided in SingletonComponent

// Compiles FINE but leaks: the reference never goes through the constructor graph
@Singleton
class SessionManager @Inject constructor() {
    var callback: SessionCallback? = null // plain var — invisible to scope checking
}

override fun onStart() { sessionManager.callback = this }  // LEAK if never cleared
override fun onStop()  { sessionManager.callback = null } // MUST null it out here
⚠ Dagger's scope check only protects bindings that flow through the graph (constructor params, @Provides/@Binds returns) — not a field assigned after the fact. Fixes: pair every manual back-reference with the lifecycle callback that clears it, wrap it in a WeakReference, or better — have the Singleton expose a SharedFlow/Channel the Activity collects from instead of registering a stored callback. LeakCanary catches this pattern in debug builds if it slips through review.
