⚡ Coroutines & Flow — Interview Questions

The most tested modern Android topic at senior level interviews. Know every nuance of structured concurrency and reactive streams.

Coroutines Fundamentals

Q1What is a coroutine? How is it different from a thread?Medium

A coroutine is a suspendable computation — lightweight, cooperative multitasking. Unlike threads:

  • Coroutines are cheap: You can run 100,000 coroutines on a device. 100,000 threads would crash it.
  • Coroutines suspend, not block: When a coroutine calls a suspend function, it releases the thread for other work. A thread blocks and does nothing while waiting.
  • Coroutines are cooperative: They yield control explicitly at suspension points. Threads are preemptive — OS can switch them at any time.
// Thread: blocks an OS thread while sleeping
Thread { Thread.sleep(1000); println("done") }.start()

// Coroutine: suspends, frees the thread for other work
launch { delay(1000); println("done") }

// 100,000 concurrent coroutines — works fine
repeat(100_000) {
    launch { delay(5000); print(".") }
}
Q2Explain all Coroutine Dispatchers and when to use eachHard

A dispatcher decides which thread or thread pool a coroutine's code actually runs on — the coroutine itself doesn't own a thread, it just gets scheduled onto whatever pool its context points to. This matters because picking the wrong one is a real, common bug: run a network call on Dispatchers.Main and you freeze the UI and risk an ANR; run heavy CPU work there and you get the same freeze even though nothing is "waiting." Kotlin ships four built-in dispatchers, each backed by a differently sized pool tuned for a specific kind of work: Main for touching views, Default for CPU-bound computation sized to the number of cores, IO for blocking I/O with a much larger pool since those threads spend most of their time waiting, and Unconfined for the rare case where you don't care what thread you resume on. The follow-up interviewers usually want is that you inject the dispatcher into your classes rather than hardcode Dispatchers.IO, so tests can swap in a deterministic test dispatcher.

// Dispatchers.Main — UI thread. For UI updates, ViewModel work
launch(Dispatchers.Main) { textView.text = "Hello" }

// Dispatchers.IO — Optimized for I/O blocking operations
// Thread pool size: max(64, CPU cores). Good for: network, file, database
withContext(Dispatchers.IO) { api.fetchData() }

// Dispatchers.Default — CPU-intensive work. Pool size = CPU cores
// Good for: sorting large lists, JSON parsing, image processing
withContext(Dispatchers.Default) { bigList.sortedBy { it.name } }

// Dispatchers.Unconfined — Starts in current thread, resumes in whatever
// thread the suspension was resumed on. Rarely used. Only in tests.

// Custom dispatcher for tests (inject it for testability)
class Repository(private val dispatcher: CoroutineDispatcher = Dispatchers.IO) {
    suspend fun fetch() = withContext(dispatcher) { api.getData() }
}
// In tests: Repository(UnconfinedTestDispatcher())

// Combine dispatchers
launch(Dispatchers.IO + CoroutineName("fetch-data")) { /* ... */ }
💡 Avoid hardcoding Dispatchers in production code — inject them for testability. Use StandardTestDispatcher or UnconfinedTestDispatcher in tests.
Q3What is structured concurrency? Explain Job, SupervisorJob, and cancellationHard

Structured concurrency guarantees: a parent scope only completes when all its children complete. No coroutines can "escape" and run uncontrolled.

// Job: default parent-child relationship
// If child fails → parent CANCELS ALL siblings
val job = Job()
val scope = CoroutineScope(Dispatchers.IO + job)

scope.launch { task1() } // if this throws → task2 gets cancelled
scope.launch { task2() }

job.cancel() // cancels all children

// SupervisorJob: child failure doesn't affect siblings
val supervisor = SupervisorJob()
val scope = CoroutineScope(Dispatchers.IO + supervisor)

scope.launch { taskThatFails() } // fails, but task2 keeps running
scope.launch { task2() }

// viewModelScope uses SupervisorJob internally
// lifecycleScope uses SupervisorJob internally

// Cancellation is cooperative — must check isActive or use cancellable suspend fns
launch {
    repeat(1000) { i ->
        if (!isActive) return@launch // check for cancellation
        doWork(i)
    }
}

// ensureActive() throws CancellationException if cancelled
launch {
    for (item in items) {
        ensureActive() // throws if cancelled
        processItem(item)
    }
}
⚠ CancellationException must never be caught without re-throwing. It's how coroutines cooperate with cancellation.
Q4What is the difference between launch and async? When to use each?Medium

launch and async are the two basic coroutine builders, and the distinction is really about what you get back and why you'd want it. launch starts a coroutine and hands you a Job — it's fire-and-forget, the right choice when you don't need a return value, just something you can cancel later. async starts a coroutine and hands you a Deferred<T>, a promise-like handle you call await() on to suspend until the computed value is ready, which is what makes it the tool for running independent pieces of work concurrently and combining their results afterward. The classic mistake is calling async { ... }.await() immediately — that forces the work to run sequentially anyway and throws away the entire reason to reach for async instead of a plain suspend function; the correct pattern is to launch every async call first and only await them once they're all in flight.

// launch: fire and forget. Returns Job, not a result
val job: Job = viewModelScope.launch {
    repository.saveData(data) // don't need the result
}
job.cancel() // can cancel

// async: returns Deferred<T>. await() to get result
val deferred: Deferred<User> = viewModelScope.async {
    repository.getUser(id) // returns a value
}
val user: User = deferred.await() // suspends until result ready

// Parallel execution with async
val userDeferred = async { api.getUser(id) }
val postsDeferred = async { api.getPosts(id) }
// Both run in parallel, await both:
val user = userDeferred.await()
val posts = postsDeferred.await()

// Sequential (wrong way to use async):
val user = async { api.getUser() }.await() // defeats the purpose!
// Better: just use withContext or a suspend fun directly

Flow — Cold & Hot Streams

Q5Flow vs StateFlow vs SharedFlow — differences with real use casesHard

Flow, StateFlow, and SharedFlow sit on a spectrum from cold to hot, and picking the right one comes down to what kind of data you're actually modeling. A plain Flow is cold — the code inside the builder doesn't run at all until something calls collect(), and it starts over from scratch for every new collector, which is exactly right for a one-shot or repeatable operation like a network request or a sensor read. StateFlow and SharedFlow are hot instead — they run independently of whether anyone is listening and broadcast the same emission to every collector at once; StateFlow on top of that always holds a current value, skips emitting duplicates, and immediately replays its latest value to any new subscriber, which is precisely the contract you want for UI state. SharedFlow drops the "always has a value" guarantee and instead gives you configurable replay and buffering, making it the better fit for one-off events like a navigation command or a snackbar that a late subscriber shouldn't automatically receive unless you explicitly configure replay.

// FLOW (cold): executes only when collected, each collector gets fresh emission
fun getTemperature(): Flow<Int> = flow {
    while (true) {
        emit(sensor.read()) // Starts fresh for EACH collector
        delay(1000)
    }
}

// STATEFLOW (hot): always active, always has value, replays LAST value
// Perfect for UI state
val uiState = MutableStateFlow(UiState.Loading)
uiState.update { UiState.Success(data) }
// New subscriber immediately gets UiState.Success — even if emitted seconds ago
// StateFlow.value always accessible
// Doesn't emit if value is same (distinct until changed)

// SHAREDFLOW (hot): configurable replay, no initial value
// Perfect for events/effects
val events = MutableSharedFlow<Event>(
    replay = 0,              // 0 = don't replay to new subscribers
    extraBufferCapacity = 10 // buffer 10 events if no subscriber
)
events.tryEmit(Event.Navigate) // non-suspending emit (if buffer available)

// Converting cold Flow to hot StateFlow
val hotUsers = repository.getUsers() // cold Flow
    .stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5_000), // stops 5s after last subscriber
        initialValue = emptyList()
    )

SharingStarted options:

  • WhileSubscribed(5000): Upstream active while subscribers exist, 5s grace period after last unsubscribes. Recommended for ViewModels.
  • Eagerly: Upstream starts immediately, never stops
  • Lazily: Upstream starts on first subscriber, never stops
Q6Explain Flow exception handling and how it differs from coroutine exception handlingHard

Flow's error handling looks different from a plain try/catch because a Flow is a pipeline, not a single suspending call, and exceptions only ever propagate downstream — never sideways or back upstream. The catch operator only intercepts exceptions thrown by the code above it in the chain (the flow builder or earlier operators); it cannot catch something thrown inside the terminal collect block, because by the time collect runs, the value has already passed through catch successfully. That's why onCompletion exists alongside it — it always fires when the flow finishes, whether normally or with an exception, so it's the right place for cleanup like hiding a spinner regardless of outcome. Coroutine builders use a completely separate mechanism: launch reports an uncaught exception to a CoroutineExceptionHandler (or crashes the app if none is installed), while async instead stores the exception on its Deferred and only rethrows it when you call await() — so a failing async that's never awaited won't reach the handler at all.

// Flow: exceptions must be handled with catch operator
flow {
    emit(api.getData()) // can throw
}
.catch { e -> emit(Result.Error(e)) } // catches upstream exceptions
.collect { /* handles Result */ }

// catch only catches UPSTREAM exceptions, not in collect {}
flow { emit(1) }
    .catch { e -> println("caught: $e") }
    .collect {
        throw RuntimeException("in collect") // NOT caught by catch!
    }

// onCompletion: called when flow completes normally OR with exception
flow { emit(data) }
    .onCompletion { cause ->
        if (cause != null) handleError(cause)
        hideLoading()
    }
    .collect { handleData(it) }

// Coroutine exception handler (for launch, not async)
val handler = CoroutineExceptionHandler { _, exception ->
    println("Caught: $exception")
}
launch(handler) {
    throw RuntimeException("oops") // caught by handler
}
// async: exception stored in Deferred, thrown on .await()
val deferred = async { throw RuntimeException() }
try { deferred.await() } catch (e: Exception) { handleError(e) }
Q7What are the key Flow operators and when do you use each?Hard

Flow's operators echo Kotlin's collection functions like map and filter, but because a Flow emits asynchronously over time rather than all at once, the operators worth knowing well are the ones with no collection equivalent — the ones that manage timing, concurrency, and backpressure. The flattening operators — flatMapConcat, flatMapMerge, and flatMapLatest — handle the case where your transform itself returns another Flow, and they differ in whether the inner flows run one after another, all at once, or get cancelled the moment a newer value arrives; flatMapLatest is the standard choice for search-as-you-type since it automatically drops a stale in-flight request when the user keeps typing. combine and zip both merge multiple flows but with different pairing rules — combine re-emits whenever any source updates, while zip waits until every source has produced a value before emitting a pair. buffer and conflate both exist to deal with a collector that's slower than its producer: buffer queues up emissions so the producer never has to wait, while conflate throws away all but the most recent value when the collector falls behind — usually the right call for UI state that can change faster than the screen can redraw.

// Transforming
.map { it * 2 }           // transform each emission
.filter { it > 0 }        // only emit if predicate true
.transform { emit(it); emit(it * 2) } // emit 0..N items per input

// Flattening (when your lambda returns a Flow)
.flatMapConcat { userId -> getUserProfile(userId) } // sequential
.flatMapMerge { userId -> getUserProfile(userId) }  // concurrent
.flatMapLatest { query -> searchApi(query) }        // cancels previous if new arrives

// Combining
combine(flow1, flow2) { a, b -> a + b }  // emits when EITHER changes
zip(flow1, flow2) { a, b -> Pair(a, b) }  // pairs up, waits for both

// Buffering / debouncing (for search-as-you-type)
searchQueryFlow
    .debounce(300)          // wait 300ms after last emission
    .distinctUntilChanged()  // don't emit if same as last
    .flatMapLatest { query -> searchRepository.search(query) }
    .collect { results -> showResults(results) }

// Buffer / conflate for backpressure
.buffer(64)    // buffer 64 items to smooth out bursts
.conflate()   // skip intermediate emissions, process latest only

// Lifecycle-aware collection in Fragment
viewLifecycleOwner.lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.state.collect { render(it) }
    }
}

Testing & Advanced Patterns

Q8coroutineScope{} vs supervisorScope{} vs a stored CoroutineScope — why do they fail differently?Hard

coroutineScope{} and supervisorScope{} are suspend functions, not objects. They borrow the calling coroutine's context, create a fresh child Job, and suspend the caller until every coroutine launched inside completes — so an exception thrown inside can be rethrown straight back to the caller. A stored CoroutineScope (like viewModelScope) is a long-lived object instead: scope.launch{} returns immediately and is decoupled from whoever called it.

The two builders also differ in failure semantics. coroutineScope{} keeps a regular Job's all-or-nothing rule: one child failing cancels every sibling launched in that block, and the exception propagates out — use it when the whole group is meaningless if any one piece fails (e.g. two calls that feed one combined result). supervisorScope{} installs a SupervisorJob instead: a failing child does not cancel its siblings, so independent, best-effort pieces of work can fail on their own. This is exactly why viewModelScope/lifecycleScope are built on SupervisorJob — one crashing launch{} must never take down every other coroutine owned by that ViewModel.

// coroutineScope: all-or-nothing — one failure cancels every sibling
suspend fun loadDashboard() = coroutineScope {
    val user  = async { api.getUser() }   // if this throws...
    val posts = async { api.getPosts() }  // ...this gets cancelled too
    Dashboard(user.await(), posts.await())
}

// supervisorScope: isolated — a failing child doesn't touch its siblings
suspend fun loadWidgets() = supervisorScope {
    val weather = async { fetchWeather() }  // may fail on its own
    val stocks  = async { fetchStocks() }   // keeps running either way
    listOf(weather, stocks).map { runCatching { it.await() } }
}
Q9How does callbackFlow bridge a callback API into Flow? How is a Channel different from a Flow?Hard

callbackFlow{} is the standard way to wrap a callback-based API (location updates, a SDK listener, a BroadcastReceiver) as a Flow. Inside the block you register the callback and push values out with trySend() (non-suspending, safe to call from any thread). awaitClose {} is mandatory — it suspends until the collecting coroutine is cancelled or the flow completes, and is the one guaranteed place to unregister the listener, so you never leak it.

Under the hood callbackFlow is backed by a Channel, and that surfaces the key conceptual difference: a Channel is hot — it exists independently of collectors, and every value sent to it is delivered to exactly one receiver (competing consumers), never broadcast to all of them. A Flow is cold — nothing runs until collect() is called, and each collector gets its own independent run of the block. That's why you build a Flow on top of a Channel rather than exposing the Channel directly: it gives you automatic cleanup via awaitClose{} plus the whole standard operator toolkit (map, filter, flowOn…).

fun locationUpdates(client: FusedLocationProviderClient) = callbackFlow {
    val cb = object : LocationCallback() {
        override fun onLocationResult(r: LocationResult) { trySend(r.lastLocation) }
    }
    client.requestLocationUpdates(request, cb, Looper.getMainLooper())
    awaitClose { client.removeLocationUpdates(cb) }  // fires on cancel — no leak
}

// Channel: each value goes to exactly ONE receiver, never both
val channel = Channel<Int>()
launch { repeat(3) { channel.send(it) } }
launch { for (v in channel) log("A: $v") }  // competes with B
Q10How do you test coroutines? Why runTest instead of runBlocking, and Standard vs Unconfined TestDispatcher?Medium

runTest{} is the entry point from kotlinx-coroutines-test: it runs the test body on a TestScope backed by a TestDispatcher with a virtual clock, so calls to delay() fast-forward instead of actually waiting. runBlocking has no virtual clock — a real delay(5000) really waits 5 real seconds — and it gives you no control over when coroutines launched on an unrelated scope (like viewModelScope, which defaults to Dispatchers.Main) actually run; on the JVM there is no real Main thread, so those coroutines would need Dispatchers.setMain(testDispatcher) just to execute at all.

StandardTestDispatcher (the default) queues launched coroutines instead of running them — you must call advanceUntilIdle() (or runCurrent()) to pump the queue. This mirrors production behavior more faithfully and lets you assert an intermediate state (e.g. still Loading) before the work has run. UnconfinedTestDispatcher runs everything eagerly up to the first suspension point, so you often skip advanceUntilIdle() — convenient, but it can mask real dispatch-ordering bugs your app would actually have in production.

@Test
fun loadUser_emitsLoadingThenSuccess() = runTest {
    Dispatchers.setMain(StandardTestDispatcher(testScheduler))
    val vm = UserViewModel(fakeRepo)

    vm.loadUser()                                 // launch{} — just QUEUED, not run yet
    assertEquals(UiState.Loading, vm.state.value)   // nothing executed yet

    advanceUntilIdle()                             // pump the queue to completion
    assertEquals(UiState.Success(fakeUser), vm.state.value)
}
Q11Why doesn't cancel() always stop a coroutine? What's the CancellationException swallow bug?Hard

Cancellation in coroutines is cooperative, not preemptive. Calling job.cancel() only flips the Job to a "Cancelling" state — it throws a CancellationException the next time the coroutine hits a suspension point that checks for it (delay, yield, most suspend calls). A tight CPU-bound loop with no suspend call inside never hits that check, so cancel() silently has no effect until you add one — either check isActive yourself, or call ensureActive() to throw immediately.

The second, subtler bug: CancellationException is a normal Exception subtype, so a broad catch (e: Exception) around a suspending call (like collecting a Flow) will silently swallow it too. That breaks structured concurrency — the exception is what tells the Job machinery "this coroutine is actually done cancelling," so swallowing it lets a coroutine keep running work the rest of the app already assumes is dead (e.g. writing to a UI/state after the screen navigated away). The fix is to always rethrow it, or catch it first and narrower exceptions after.

val job = launch(Dispatchers.Default) {
    var i = 0
    while (i < 1_000_000_000) { i++ }    // no suspension point — cancel() does NOTHING
}
job.cancel()   // job silently keeps running to completion

// the swallow bug — also eats CancellationException:
try { flow.collect {} } catch (e: Exception) { logError(e) }

// fix — rethrow cancellation, handle everything else:
try { flow.collect {} }
catch (e: CancellationException) { throw e }
catch (e: Exception) { logError(e) }
Q12What do stateIn/shareIn do? Explain the SharingStarted strategies and why WhileSubscribed(5000) is the default choiceHard

stateIn converts a cold Flow into a hot StateFlow (needs an initialValue, always has a current value); shareIn converts a cold Flow into a hot SharedFlow (configurable replay, no current-value concept — better for event streams). Both multicast a single upstream execution to every collector. Without one, a Room DAO's Flow<List<User>> collected from two different screens sets up two separate live DB queries; wrapped in stateIn, both screens share the same one.

SharingStarted controls when that shared upstream starts/stops: Eagerly starts immediately and never stops (wastes resources with zero subscribers), Lazily starts on first subscriber but also never stops, and WhileSubscribed(timeoutMs) starts on first subscriber and stops timeoutMs after the last one leaves. A config change (rotation) unsubscribes and immediately resubscribes within milliseconds — WhileSubscribed(5000)'s 5-second grace window survives that gap without restarting an expensive DB observer or GPS listener, while still releasing it once the user actually navigates away. That's why it's the standard ViewModel default.

class UserViewModel(dao: UserDao) : ViewModel() {
    val users: StateFlow<List<User>> = dao.getAllUsersFlow()  // cold Flow
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), emptyList())
}
// shareIn: same idea for event-like flows with no "current value"
val events: SharedFlow<Event> = source.shareIn(scope, SharingStarted.WhileSubscribed(5_000), replay = 1)
