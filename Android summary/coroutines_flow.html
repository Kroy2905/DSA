⚡ Coroutines & Flow — Interview Questions

The most tested modern Android topic at senior level interviews. Know every nuance of structured concurrency and reactive streams.

Coroutines Fundamentals

Q1What is a coroutine? How is it different from a thread?Medium

A coroutine is a suspendable computation — lightweight, cooperative multitasking. Unlike threads:

  • Coroutines are cheap: You can run 100,000 coroutines on a device. 100,000 threads would crash it.
  • Coroutines suspend, not block: When a coroutine calls a suspend function, it releases the thread for other work. A thread blocks and does nothing while waiting.
  • Coroutines are cooperative: They yield control explicitly at suspension points. Threads are preemptive — OS can switch them at any time.
// Thread: blocks an OS thread while sleeping
Thread { Thread.sleep(1000); println("done") }.start()

// Coroutine: suspends, frees the thread for other work
launch { delay(1000); println("done") }

// 100,000 concurrent coroutines — works fine
repeat(100_000) {
    launch { delay(5000); print(".") }
}
Q2Explain all Coroutine Dispatchers and when to use eachHard 
// Dispatchers.Main — UI thread. For UI updates, ViewModel work
launch(Dispatchers.Main) { textView.text = "Hello" }

// Dispatchers.IO — Optimized for I/O blocking operations
// Thread pool size: max(64, CPU cores). Good for: network, file, database
withContext(Dispatchers.IO) { api.fetchData() }

// Dispatchers.Default — CPU-intensive work. Pool size = CPU cores
// Good for: sorting large lists, JSON parsing, image processing
withContext(Dispatchers.Default) { bigList.sortedBy { it.name } }

// Dispatchers.Unconfined — Starts in current thread, resumes in whatever
// thread the suspension was resumed on. Rarely used. Only in tests.

// Custom dispatcher for tests (inject it for testability)
class Repository(private val dispatcher: CoroutineDispatcher = Dispatchers.IO) {
    suspend fun fetch() = withContext(dispatcher) { api.getData() }
}
// In tests: Repository(UnconfinedTestDispatcher())

// Combine dispatchers
launch(Dispatchers.IO + CoroutineName("fetch-data")) { /* ... */ }
💡 Avoid hardcoding Dispatchers in production code — inject them for testability. Use StandardTestDispatcher or UnconfinedTestDispatcher in tests.
Q3What is structured concurrency? Explain Job, SupervisorJob, and cancellationHard

Structured concurrency guarantees: a parent scope only completes when all its children complete. No coroutines can "escape" and run uncontrolled.

// Job: default parent-child relationship
// If child fails → parent CANCELS ALL siblings
val job = Job()
val scope = CoroutineScope(Dispatchers.IO + job)

scope.launch { task1() } // if this throws → task2 gets cancelled
scope.launch { task2() }

job.cancel() // cancels all children

// SupervisorJob: child failure doesn't affect siblings
val supervisor = SupervisorJob()
val scope = CoroutineScope(Dispatchers.IO + supervisor)

scope.launch { taskThatFails() } // fails, but task2 keeps running
scope.launch { task2() }

// viewModelScope uses SupervisorJob internally
// lifecycleScope uses SupervisorJob internally

// Cancellation is cooperative — must check isActive or use cancellable suspend fns
launch {
    repeat(1000) { i ->
        if (!isActive) return@launch // check for cancellation
        doWork(i)
    }
}

// ensureActive() throws CancellationException if cancelled
launch {
    for (item in items) {
        ensureActive() // throws if cancelled
        processItem(item)
    }
}
⚠ CancellationException must never be caught without re-throwing. It's how coroutines cooperate with cancellation.
Q4What is the difference between launch and async? When to use each?Medium 
// launch: fire and forget. Returns Job, not a result
val job: Job = viewModelScope.launch {
    repository.saveData(data) // don't need the result
}
job.cancel() // can cancel

// async: returns Deferred<T>. await() to get result
val deferred: Deferred<User> = viewModelScope.async {
    repository.getUser(id) // returns a value
}
val user: User = deferred.await() // suspends until result ready

// Parallel execution with async
val userDeferred = async { api.getUser(id) }
val postsDeferred = async { api.getPosts(id) }
// Both run in parallel, await both:
val user = userDeferred.await()
val posts = postsDeferred.await()

// Sequential (wrong way to use async):
val user = async { api.getUser() }.await() // defeats the purpose!
// Better: just use withContext or a suspend fun directly

Flow — Cold & Hot Streams

Q5Flow vs StateFlow vs SharedFlow — differences with real use casesHard 
// FLOW (cold): executes only when collected, each collector gets fresh emission
fun getTemperature(): Flow<Int> = flow {
    while (true) {
        emit(sensor.read()) // Starts fresh for EACH collector
        delay(1000)
    }
}

// STATEFLOW (hot): always active, always has value, replays LAST value
// Perfect for UI state
val uiState = MutableStateFlow(UiState.Loading)
uiState.update { UiState.Success(data) }
// New subscriber immediately gets UiState.Success — even if emitted seconds ago
// StateFlow.value always accessible
// Doesn't emit if value is same (distinct until changed)

// SHAREDFLOW (hot): configurable replay, no initial value
// Perfect for events/effects
val events = MutableSharedFlow<Event>(
    replay = 0,              // 0 = don't replay to new subscribers
    extraBufferCapacity = 10 // buffer 10 events if no subscriber
)
events.tryEmit(Event.Navigate) // non-suspending emit (if buffer available)

// Converting cold Flow to hot StateFlow
val hotUsers = repository.getUsers() // cold Flow
    .stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5_000), // stops 5s after last subscriber
        initialValue = emptyList()
    )

SharingStarted options:

  • WhileSubscribed(5000): Upstream active while subscribers exist, 5s grace period after last unsubscribes. Recommended for ViewModels.
  • Eagerly: Upstream starts immediately, never stops
  • Lazily: Upstream starts on first subscriber, never stops
Q6Explain Flow exception handling and how it differs from coroutine exception handlingHard 
// Flow: exceptions must be handled with catch operator
flow {
    emit(api.getData()) // can throw
}
.catch { e -> emit(Result.Error(e)) } // catches upstream exceptions
.collect { /* handles Result */ }

// catch only catches UPSTREAM exceptions, not in collect {}
flow { emit(1) }
    .catch { e -> println("caught: $e") }
    .collect {
        throw RuntimeException("in collect") // NOT caught by catch!
    }

// onCompletion: called when flow completes normally OR with exception
flow { emit(data) }
    .onCompletion { cause ->
        if (cause != null) handleError(cause)
        hideLoading()
    }
    .collect { handleData(it) }

// Coroutine exception handler (for launch, not async)
val handler = CoroutineExceptionHandler { _, exception ->
    println("Caught: $exception")
}
launch(handler) {
    throw RuntimeException("oops") // caught by handler
}
// async: exception stored in Deferred, thrown on .await()
val deferred = async { throw RuntimeException() }
try { deferred.await() } catch (e: Exception) { handleError(e) }
Q7What are the key Flow operators and when do you use each?Hard 
// Transforming
.map { it * 2 }           // transform each emission
.filter { it > 0 }        // only emit if predicate true
.transform { emit(it); emit(it * 2) } // emit 0..N items per input

// Flattening (when your lambda returns a Flow)
.flatMapConcat { userId -> getUserProfile(userId) } // sequential
.flatMapMerge { userId -> getUserProfile(userId) }  // concurrent
.flatMapLatest { query -> searchApi(query) }        // cancels previous if new arrives

// Combining
combine(flow1, flow2) { a, b -> a + b }  // emits when EITHER changes
zip(flow1, flow2) { a, b -> Pair(a, b) }  // pairs up, waits for both

// Buffering / debouncing (for search-as-you-type)
searchQueryFlow
    .debounce(300)          // wait 300ms after last emission
    .distinctUntilChanged()  // don't emit if same as last
    .flatMapLatest { query -> searchRepository.search(query) }
    .collect { results -> showResults(results) }

// Buffer / conflate for backpressure
.buffer(64)    // buffer 64 items to smooth out bursts
.conflate()   // skip intermediate emissions, process latest only

// Lifecycle-aware collection in Fragment
viewLifecycleOwner.lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.state.collect { render(it) }
    }
}
