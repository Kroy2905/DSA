🎨 Jetpack Compose — Interview Questions

Compose is now standard Android. Google expects deep knowledge of recomposition, state, side effects, and how it differs from the View system.

Recomposition & State

Q1What is recomposition? What triggers it and how can you optimize it?Hard — Must Know

Recomposition = Compose re-executing a Composable function because its inputs (state/parameters) changed. Compose uses smart recomposition — only re-runs functions whose inputs actually changed, not the entire tree.

// Triggers recomposition:
// 1. State read inside the composable changes
// 2. Parameters passed to composable change

@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }
    // Clicking triggers recomposition of Counter() only
    Button(onClick = { count++ }) { Text("Count: $count") }
}

// OPTIMIZATION 1: Stable types avoid unnecessary recomposition
// Compose considers a type "stable" if:
// - All public properties are immutable (val), OR
// - Annotated with @Stable/@Immutable
@Immutable // tells Compose: this never changes internally
data class UserUiState(val name: String, val age: Int)

// OPTIMIZATION 2: derivedStateOf — avoid recomposing when derived value unchanged
val showTopBar by remember { derivedStateOf { scrollState.value == 0 } }
// Without derivedStateOf: recomposes on EVERY scroll pixel
// With derivedStateOf: only recomposes when showTopBar CHANGES (true↔false)

// OPTIMIZATION 3: key() — give items stable identity
LazyColumn {
    items(users, key = { it.id }) { user -> // stable key = proper recomposition
        UserItem(user = user)
    }
}

// OPTIMIZATION 4: Move state down — lambda captures avoid recomposition
// WRONG: count change recomposes Parent AND Button unnecessarily
@Composable
fun Parent() {
    var count by remember { mutableStateOf(0) }
    ExpensiveChild(count = count, onClick = { count++ }) // recomposes every click
}
// BETTER: pass lambda instead of value
@Composable
fun Parent() {
    var count by remember { mutableStateOf(0) }
    ExpensiveChild(onClick = { count++ }) // lambda is stable — no recompose
}

Smart recomposition: only the scope on the state's read-path re-runs

When count changes, only Counter() and its child Text() — the functions that actually read count — are re-invoked. Header() is an unrelated sibling scope that never read the state, so Compose's slot table diffing skips it entirely rather than walking the whole tree.

Q2remember vs rememberSaveable — what is the difference?Medium

remember and rememberSaveable both cache a value across recompositions so Compose doesn't recreate it every time the function re-runs, but they differ in how long that value survives. remember only holds the value in memory for as long as the composable stays in the composition — the moment the activity is recreated for a configuration change like rotation, or the process dies and restarts, that value is gone and reinitializes from scratch. rememberSaveable additionally persists the value into the saved instance state Bundle, the same mechanism Views use with onSaveInstanceState, so it survives rotation and even light process death when the system restores the UI. The tradeoff is that whatever you store must fit into a Bundle, so it needs to be a primitive, Parcelable, or something you supply a custom Saver for. As a rule of thumb: use remember for transient UI state you don't mind losing, rememberSaveable for anything the user would be annoyed to lose on rotation, and hoist truly durable state into a ViewModel.

// remember: survives RECOMPOSITION. Lost on rotation or process death.
var count by remember { mutableStateOf(0) }

// rememberSaveable: survives recomposition AND configuration changes (rotation)
// Stores in Bundle — same limits as onSaveInstanceState
var text by rememberSaveable { mutableStateOf("") } // survives rotation

// For complex types: use custom Saver
val userSaver = listSaver<User, Any>(
    save = { listOf(it.id, it.name) },
    restore = { User(it[0] as String, it[1] as String) }
)
var user by rememberSaveable(stateSaver = userSaver) { mutableStateOf(User("", "")) }

// When to use which:
// remember: ephemeral UI state (animation values, expanded state while visible)
// rememberSaveable: user-entered data, scroll position, selection state
// ViewModel state: everything that outlives the screen (data from network)
Q3What is State Hoisting and why is it important?Medium

State hoisting = moving state up to the caller, making the composable stateless (just renders what it's given). Pattern: replace internal state with a parameter + callback pair.

// STATEFUL (hard to test, hard to reuse)
@Composable
fun SearchBar() {
    var query by remember { mutableStateOf("") }
    TextField(value = query, onValueChange = { query = it })
}

// STATELESS — hoisted (easy to test, reusable)
@Composable
fun SearchBar(query: String, onQueryChange: (String) -> Unit) {
    TextField(value = query, onValueChange = onQueryChange)
}

// Stateful wrapper (ViewModel owns state)
@Composable
fun SearchScreen(viewModel: SearchViewModel = hiltViewModel()) {
    val query by viewModel.query.collectAsStateWithLifecycle()
    SearchBar(query = query, onQueryChange = viewModel::onQueryChange)
}
// Benefits: SearchBar is pure function — preview works, easy to test, reusable

Side Effects

Q4Explain all Compose side effects: LaunchedEffect, SideEffect, DisposableEffect, produceStateHard — Google Favorite

Compose splits side-effect handling into several dedicated APIs, each meant for a different kind of "talk to the outside world" problem, because you can't just fire off arbitrary work inside a composable body — that body can run any number of times, for reasons that have nothing to do with your business logic. LaunchedEffect launches a coroutine tied to the composable's lifecycle, restarting it when its keys change and cancelling it automatically when the composable leaves composition, which makes it the tool for one-shot suspend work like a network call keyed off an ID. SideEffect runs a plain block after every successful recomposition and is for publishing Compose state out to a non-Compose system that isn't itself observable, like an analytics logger. DisposableEffect is the effect for anything that needs explicit setup and teardown — registering a listener and unregistering it — firing onDispose whenever its keys change or the composable leaves. produceState bridges non-Compose asynchronous data sources into a Compose State so the rest of the tree can just read it like any other snapshot state. Interviewers use this question to check whether you understand that a composable function is a description of UI Compose is free to re-invoke as it likes, not a place to put side effects directly.

// LaunchedEffect: launch a coroutine scoped to the composable's lifecycle
// Restarts when keys change. Cancelled when composable leaves composition.
@Composable
fun UserProfile(userId: String) {
    LaunchedEffect(userId) { // re-runs when userId changes
        viewModel.loadUser(userId) // suspend call ok here
    }
}
// LaunchedEffect(Unit) = run once on first composition
// LaunchedEffect(key1, key2) = re-run when either key changes

// SideEffect: runs after every SUCCESSFUL recomposition
// Use to sync Compose state to non-Compose code
@Composable
fun TrackScreen(screenName: String, analytics: Analytics) {
    SideEffect {
        analytics.logScreenView(screenName) // sync analytics after every recompose
    }
}

// DisposableEffect: setup + cleanup for non-coroutine effects
// onDispose called when keys change OR composable leaves composition
@Composable
fun LocationTracker(onLocationUpdate: (Location) -> Unit) {
    val context = LocalContext.current
    DisposableEffect(Unit) {
        val listener = LocationListener { onLocationUpdate(it) }
        locationManager.requestUpdates(listener)
        onDispose {
            locationManager.removeUpdates(listener) // cleanup!
        }
    }
}

// produceState: convert non-Compose async data to State
@Composable
fun remoteImage(url: String): State<Bitmap?> = produceState<Bitmap?>(initialValue = null, url) {
    value = imageLoader.load(url) // suspend call, sets value when done
    awaitDispose { imageLoader.cancel(url) }
}

// rememberCoroutineScope: get scope tied to composition (for event-triggered coroutines)
@Composable
fun SnackbarDemo() {
    val scope = rememberCoroutineScope() // tied to composition
    val snackbarHost = remember { SnackbarHostState() }
    Button(onClick = {
        scope.launch { snackbarHost.showSnackbar("Done!") } // triggered by event
    }) { Text("Show") }
}
⚠ Never start coroutines directly in composable body — they run on every recomposition! Use LaunchedEffect or rememberCoroutineScope.

Navigation & Architecture

Q5How does Navigation in Compose work? Type-safe navigation?Medium

Navigation Compose gives Compose its own navigation library built around a NavController and a NavHost, replacing the fragment-based navigation graph with composable destinations registered by route. In the string-route approach you register each destination with a route string and declare its arguments explicitly, then read them back out of the NavBackStackEntry, which works but loses compile-time safety — a typo in a route string or an argument key only fails at runtime. Newer Navigation Compose versions (2.8+) add type-safe navigation built on Kotlin Serialization, where each destination is a serializable class or object and you navigate by passing an actual instance, so the compiler checks that the destination and its arguments match. This matters for interviews because it shows you know navigation moved from an imperative, string-keyed API to a statically-typed one, and that each destination composable still gets its own scoped ViewModel via hiltViewModel() the same way it would with fragments.

// Basic Navigation (Navigation Compose)
val navController = rememberNavController()
NavHost(navController = navController, startDestination = "home") {
    composable("home") { HomeScreen(onNavigate = { navController.navigate("detail/42") }) }
    composable("detail/{id}", arguments = listOf(navArgument("id") { type = NavType.IntType })) {
        val id = it.arguments?.getInt("id")
        DetailScreen(id = id)
    }
}

// Type-safe navigation (Navigation 2.8+ with Kotlin Serialization)
@Serializable object Home
@Serializable data class Detail(val id: Int)

NavHost(navController, startDestination = Home) {
    composable<Home> { HomeScreen(onNavigate = { navController.navigate(Detail(42)) }) }
    composable<Detail> { backStackEntry ->
        val detail = backStackEntry.toRoute<Detail>()
        DetailScreen(id = detail.id)
    }
}

// Navigate to ViewModel via Hilt
@Composable
fun HomeScreen(viewModel: HomeViewModel = hiltViewModel()) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()
}
Q6How do you collect flows safely in Compose?Hard

Flows exposed by a ViewModel need to be turned into Compose State to be read during composition, and the way you do that collection matters because a naive collector keeps running even when the screen isn't visible. collectAsState collects for as long as the composable is in composition, with no awareness of the Android lifecycle, so a backgrounded screen still keeps its flow collector active, burning battery and CPU on updates nobody can see. collectAsStateWithLifecycle, from the lifecycle-runtime-compose artifact, wraps that collection so it automatically stops when the lifecycle drops below STARTED and resumes when the screen comes back to the foreground, which is why it's the version Google recommends for production code. For one-time events — navigation triggers, snackbar messages — you don't want a State at all since those aren't meant to be redrawn on recomposition; instead you collect a Flow of events directly inside a LaunchedEffect(Unit), so each event is consumed exactly once as it arrives.

// collectAsState — always collecting, even when screen is in background
val state = viewModel.uiState.collectAsState()

// collectAsStateWithLifecycle — CORRECT approach for production
// Stops collection when lifecycle is below STARTED (app backgrounded)
// Saves battery, prevents background processing
val state by viewModel.uiState.collectAsStateWithLifecycle()

// For one-time events from ViewModel
@Composable
fun MyScreen(viewModel: MyViewModel = hiltViewModel(), navController: NavController) {
    LaunchedEffect(Unit) {
        viewModel.events.collect { event ->
            when (event) {
                is Event.Navigate -> navController.navigate(event.route)
                is Event.ShowError -> /* show snackbar */
            }
        }
    }
}
✓ Google's lifecycle-aware library: implementation("androidx.lifecycle:lifecycle-runtime-compose:2.7.0")
Q7What is CompositionLocal and when should you use it?Medium

CompositionLocal is Compose's mechanism for passing data implicitly down the composition tree without threading it through every function parameter, similar to React's Context — any descendant can read the value without the composables in between needing to know about it. Compose itself relies on this heavily — LocalContext, LocalDensity, and the current MaterialTheme colors are all backed by CompositionLocals — which is why it's worth knowing even if you never define a custom one. You provide a value with CompositionLocalProvider scoped to part of the tree, and any descendant reads it with .current; this is best reserved for genuinely cross-cutting concerns like theming, a logging/analytics dependency, or layout direction, not as a general substitute for passing parameters or hoisting state, since overusing it makes data flow harder to trace. The two flavors differ in their recomposition cost: compositionLocalOf tracks reads and only recomposes the composables that actually read .current when the value changes, while staticCompositionLocalOf skips that tracking entirely and recomposes the whole subtree under the provider, trading correctness granularity for lower overhead — appropriate only when the value essentially never changes during the app's lifetime.

// CompositionLocal: implicit data passing down the composition tree
// Like React Context — avoids passing params through every layer

// Built-in CompositionLocals:
val context = LocalContext.current
val density = LocalDensity.current
val colorScheme = MaterialTheme.colorScheme // uses CompositionLocal internally

// Custom CompositionLocal
val LocalAnalytics = compositionLocalOf<Analytics> { error("No analytics provided") }

@Composable
fun App() {
    CompositionLocalProvider(LocalAnalytics provides AnalyticsImpl()) {
        MainNavigation() // all descendants can access LocalAnalytics.current
    }
}

@Composable
fun SomeDeepChild() {
    val analytics = LocalAnalytics.current // no need to pass through every parent
}

// compositionLocalOf vs staticCompositionLocalOf:
// compositionLocalOf: only recomposes READERS when value changes (smart)
// staticCompositionLocalOf: recomposes ALL children when value changes (use for truly static data)

Performance & Interop

Q8What are the three phases of Compose (Composition, Layout, Drawing)? What do "recomposition", "re-layout", and "redraw" each mean?Hard — Must Know

Every frame, Compose runs up to three independent phases. Each one can be skipped on its own if its inputs didn't change — that's the real source of Compose's performance, not just "smart recomposition" at the Composition level.

  • Composition — runs composable functions, builds/updates the in-memory tree of what to emit. Triggered by a state read inside a composable changing. Output: a tree of LayoutNodes with their emitted modifiers/params.
  • Layout — each node's measure()/place() runs to decide size and position. Triggered when Composition changed something a node measures/places by (size, padding, weight, arrangement). Can run without Composition re-running (e.g. a constraint from a parent changes).
  • Drawing — pixels are actually rasterized to the canvas/layer. Triggered whenever Layout finishes, or independently when only draw-time properties change (color, alpha, translation, shadow via graphicsLayer). This is the cheapest phase to hit alone.
@Composable
fun FadingBox(alphaState: State<Float>) {
    Box(
        modifier = Modifier.size(100.dp).graphicsLayer {
            this.alpha = alphaState.value // read happens in the DRAW phase, not Composition
        }
    )
}
// alphaState.value changes -> Composition: SKIPPED, Layout: SKIPPED, Drawing: RUNS only
// Compare: fun FadingBoxSlow(alpha: Float) reads alpha as a normal PARAMETER —
// that read happens during Composition, so every change forces all three phases
Recomposition, re-layout, and redraw are three separate, independently-skippable operations. Interviewers probe this to see if you know Compose's performance model goes deeper than "does it recompose or not."
Q9What makes a type "stable" to the Compose compiler? Difference between @Stable and @Immutable?Hard — Google Favorite

Stability determines whether Compose can safely skip recomposing a function when its parameters are "equal" to last time. The compiler infers stability structurally; when it can't prove a type is stable, it marks it unstable and disables skipping for any composable that takes it as a parameter.

  • A type is inferred stable when: all its public properties are val and are themselves stable types (primitives, String, function types/lambdas, or other stable classes) — or it's explicitly annotated @Stable/@Immutable.
  • @Immutable — a promise that once constructed, the object never changes (every property is permanently fixed for the object's lifetime). Use on plain data classes with val properties whose types the compiler can't otherwise prove are stable (e.g. they come from another module without stability metadata).
  • @Stable — a weaker promise: the object can mutate over time, but (1) equals() is consistent — if two instances are equal, they'll stay equal — and (2) any change to a publicly-readable property is reported to Compose (typically because it's backed by MutableState). Use on state-holder classes that expose mutable, observable state.
// interface types are ALWAYS unstable — the compiler can't prove the
// caller won't pass a MutableList that mutates in place at runtime
@Composable
fun UserList(users: List<User>) { // unstable param -> skipping disabled
    LazyColumn { items(users) { UserRow(it) } }
}

// fix: a genuinely immutable, stable collection type
fun UserList(users: ImmutableList<User>) { // stable -> Compose can skip
    LazyColumn { items(users) { UserRow(it) } }
}

// @Stable: object MUTATES, but every change is observable via MutableState
@Stable
class SearchFieldState {
    var query by mutableStateOf("")
        private set
}
A single unstable parameter disables skipping for the WHOLE composable — not just for that parameter. Check the Compose Compiler Metrics report (reportsDestination Gradle option) to find "unstable" params in a real codebase.
Q10When do you actually need derivedStateOf vs a plain remember(key) { ... }?Medium

Use derivedStateOf specifically when you're computing a value from state that changes far more often than the derived result itself — it converts a high-frequency input into a low-frequency output, so readers of the derived state only recompose when that output actually flips.

// NEEDS derivedStateOf: scrollState.firstVisibleItemIndex changes on EVERY pixel
// scrolled, but "show scroll-to-top button" only flips true/false rarely
val listState = rememberLazyListState()
val showButton by remember {
    derivedStateOf { listState.firstVisibleItemIndex > 0 }
}
// WITHOUT derivedStateOf (reading listState.firstVisibleItemIndex directly):
// the composable reading it recomposes on every single scroll tick
// WITH derivedStateOf: it only recomposes when showButton flips true<->false
if (showButton) { ScrollToTopFab() }

// DOESN'T need derivedStateOf: value only changes when its own key changes —
// there's no "high frequency source, low frequency output" mismatch to exploit
val formattedDate = remember(timestamp) { formatDate(timestamp) } // fine: recomputes only when timestamp itself changes
// Using derivedStateOf here adds overhead for nothing — timestamp doesn't
// change more often than formattedDate would; there's no extra reads to dedupe
Rule of thumb: reach for derivedStateOf only when profiling/reasoning shows a composable re-running many times per "meaningful" change — e.g. scroll offsets, drag deltas, animation progress feeding a boolean/threshold. For everything else, remember(key) is simpler and cheaper (derivedStateOf still re-evaluates its lambda on every underlying change — it just skips notifying readers when the result is unchanged).
Q11How do you build a custom layout with the Layout composable? What are intrinsic measurements for?Hard

The Layout composable is the primitive every built-in layout (Row, Column, Box) is built on. You get the raw list of child Measurables and the incoming Constraints, measure each child yourself, then declare this layout's own size and place the children at custom offsets.

Layout(content = content) { measurables, constraints ->
    val placeables = measurables.map { it.measure(constraints) } // 1. measure children
    layout(placeables.sumOf { it.width }, placeables.maxOf { it.height }) { // 2. declare own size
        var x = 0
        placeables.forEach { it.placeRelative(x, 0); x += it.width } // 3. place children
    }
}

Intrinsic measurements answer "how big would this child be" without a real measure pass — needed when a parent must size sibling A based on sibling B before either is measured for real (e.g. Modifier.height(IntrinsicSize.Min) so a divider matches its sibling Text's height). You implement minIntrinsicWidth/maxIntrinsicHeight etc. alongside measure() on a custom MeasurePolicy — it costs an extra measure pass under the hood, so reserve it for cases you can't solve by restructuring constraints.

Q12How does Compose interop with the View system, and how does Compose UI testing differ from Espresso?Medium

AndroidView embeds a legacy View inside Compose (factory runs once, update runs on relevant recompositions); ComposeView does the reverse, embedding a Compose hierarchy inside a legacy View/Fragment tree. Compose UI tests query the semantics tree instead of view IDs — there's no R.id.* to reference, so tests match by text, role, or an explicit Modifier.testTag().

AndroidView(factory = { MapView(it) }, update = { it.moveCamera(target) })

// Compose test: queries the semantics tree, not a view id
composeRule.onNodeWithTag("increment_btn").performClick()
composeRule.onNodeWithText("Count: 1").assertIsDisplayed()
Espresso matches the rendered View hierarchy by resource id/type; SemanticsNodeInteraction queries walk the same semantics tree TalkBack/accessibility services use — good testTag/content-description coverage improves accessibility for free.
