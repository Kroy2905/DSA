🎨 Jetpack Compose — Interview Questions

Compose is now standard Android. Google expects deep knowledge of recomposition, state, side effects, and how it differs from the View system.

Recomposition & State

Q1What is recomposition? What triggers it and how can you optimize it?Hard — Must Know

Recomposition = Compose re-executing a Composable function because its inputs (state/parameters) changed. Compose uses smart recomposition — only re-runs functions whose inputs actually changed, not the entire tree.

// Triggers recomposition:
// 1. State read inside the composable changes
// 2. Parameters passed to composable change

@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }
    // Clicking triggers recomposition of Counter() only
    Button(onClick = { count++ }) { Text("Count: $count") }
}

// OPTIMIZATION 1: Stable types avoid unnecessary recomposition
// Compose considers a type "stable" if:
// - All public properties are immutable (val), OR
// - Annotated with @Stable/@Immutable
@Immutable // tells Compose: this never changes internally
data class UserUiState(val name: String, val age: Int)

// OPTIMIZATION 2: derivedStateOf — avoid recomposing when derived value unchanged
val showTopBar by remember { derivedStateOf { scrollState.value == 0 } }
// Without derivedStateOf: recomposes on EVERY scroll pixel
// With derivedStateOf: only recomposes when showTopBar CHANGES (true↔false)

// OPTIMIZATION 3: key() — give items stable identity
LazyColumn {
    items(users, key = { it.id }) { user -> // stable key = proper recomposition
        UserItem(user = user)
    }
}

// OPTIMIZATION 4: Move state down — lambda captures avoid recomposition
// WRONG: count change recomposes Parent AND Button unnecessarily
@Composable
fun Parent() {
    var count by remember { mutableStateOf(0) }
    ExpensiveChild(count = count, onClick = { count++ }) // recomposes every click
}
// BETTER: pass lambda instead of value
@Composable
fun Parent() {
    var count by remember { mutableStateOf(0) }
    ExpensiveChild(onClick = { count++ }) // lambda is stable — no recompose
}
Q2remember vs rememberSaveable — what is the difference?Medium 
// remember: survives RECOMPOSITION. Lost on rotation or process death.
var count by remember { mutableStateOf(0) }

// rememberSaveable: survives recomposition AND configuration changes (rotation)
// Stores in Bundle — same limits as onSaveInstanceState
var text by rememberSaveable { mutableStateOf("") } // survives rotation

// For complex types: use custom Saver
val userSaver = listSaver<User, Any>(
    save = { listOf(it.id, it.name) },
    restore = { User(it[0] as String, it[1] as String) }
)
var user by rememberSaveable(stateSaver = userSaver) { mutableStateOf(User("", "")) }

// When to use which:
// remember: ephemeral UI state (animation values, expanded state while visible)
// rememberSaveable: user-entered data, scroll position, selection state
// ViewModel state: everything that outlives the screen (data from network)
Q3What is State Hoisting and why is it important?Medium

State hoisting = moving state up to the caller, making the composable stateless (just renders what it's given). Pattern: replace internal state with a parameter + callback pair.

// STATEFUL (hard to test, hard to reuse)
@Composable
fun SearchBar() {
    var query by remember { mutableStateOf("") }
    TextField(value = query, onValueChange = { query = it })
}

// STATELESS — hoisted (easy to test, reusable)
@Composable
fun SearchBar(query: String, onQueryChange: (String) -> Unit) {
    TextField(value = query, onValueChange = onQueryChange)
}

// Stateful wrapper (ViewModel owns state)
@Composable
fun SearchScreen(viewModel: SearchViewModel = hiltViewModel()) {
    val query by viewModel.query.collectAsStateWithLifecycle()
    SearchBar(query = query, onQueryChange = viewModel::onQueryChange)
}
// Benefits: SearchBar is pure function — preview works, easy to test, reusable

Side Effects

Q4Explain all Compose side effects: LaunchedEffect, SideEffect, DisposableEffect, produceStateHard — Google Favorite 
// LaunchedEffect: launch a coroutine scoped to the composable's lifecycle
// Restarts when keys change. Cancelled when composable leaves composition.
@Composable
fun UserProfile(userId: String) {
    LaunchedEffect(userId) { // re-runs when userId changes
        viewModel.loadUser(userId) // suspend call ok here
    }
}
// LaunchedEffect(Unit) = run once on first composition
// LaunchedEffect(key1, key2) = re-run when either key changes

// SideEffect: runs after every SUCCESSFUL recomposition
// Use to sync Compose state to non-Compose code
@Composable
fun TrackScreen(screenName: String, analytics: Analytics) {
    SideEffect {
        analytics.logScreenView(screenName) // sync analytics after every recompose
    }
}

// DisposableEffect: setup + cleanup for non-coroutine effects
// onDispose called when keys change OR composable leaves composition
@Composable
fun LocationTracker(onLocationUpdate: (Location) -> Unit) {
    val context = LocalContext.current
    DisposableEffect(Unit) {
        val listener = LocationListener { onLocationUpdate(it) }
        locationManager.requestUpdates(listener)
        onDispose {
            locationManager.removeUpdates(listener) // cleanup!
        }
    }
}

// produceState: convert non-Compose async data to State
@Composable
fun remoteImage(url: String): State<Bitmap?> = produceState<Bitmap?>(initialValue = null, url) {
    value = imageLoader.load(url) // suspend call, sets value when done
    awaitDispose { imageLoader.cancel(url) }
}

// rememberCoroutineScope: get scope tied to composition (for event-triggered coroutines)
@Composable
fun SnackbarDemo() {
    val scope = rememberCoroutineScope() // tied to composition
    val snackbarHost = remember { SnackbarHostState() }
    Button(onClick = {
        scope.launch { snackbarHost.showSnackbar("Done!") } // triggered by event
    }) { Text("Show") }
}
⚠ Never start coroutines directly in composable body — they run on every recomposition! Use LaunchedEffect or rememberCoroutineScope.

Navigation & Architecture

Q5How does Navigation in Compose work? Type-safe navigation?Medium 
// Basic Navigation (Navigation Compose)
val navController = rememberNavController()
NavHost(navController = navController, startDestination = "home") {
    composable("home") { HomeScreen(onNavigate = { navController.navigate("detail/42") }) }
    composable("detail/{id}", arguments = listOf(navArgument("id") { type = NavType.IntType })) {
        val id = it.arguments?.getInt("id")
        DetailScreen(id = id)
    }
}

// Type-safe navigation (Navigation 2.8+ with Kotlin Serialization)
@Serializable object Home
@Serializable data class Detail(val id: Int)

NavHost(navController, startDestination = Home) {
    composable<Home> { HomeScreen(onNavigate = { navController.navigate(Detail(42)) }) }
    composable<Detail> { backStackEntry ->
        val detail = backStackEntry.toRoute<Detail>()
        DetailScreen(id = detail.id)
    }
}

// Navigate to ViewModel via Hilt
@Composable
fun HomeScreen(viewModel: HomeViewModel = hiltViewModel()) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()
}
Q6How do you collect flows safely in Compose?Hard 
// collectAsState — always collecting, even when screen is in background
val state = viewModel.uiState.collectAsState()

// collectAsStateWithLifecycle — CORRECT approach for production
// Stops collection when lifecycle is below STARTED (app backgrounded)
// Saves battery, prevents background processing
val state by viewModel.uiState.collectAsStateWithLifecycle()

// For one-time events from ViewModel
@Composable
fun MyScreen(viewModel: MyViewModel = hiltViewModel(), navController: NavController) {
    LaunchedEffect(Unit) {
        viewModel.events.collect { event ->
            when (event) {
                is Event.Navigate -> navController.navigate(event.route)
                is Event.ShowError -> /* show snackbar */
            }
        }
    }
}
✓ Google's lifecycle-aware library: implementation("androidx.lifecycle:lifecycle-runtime-compose:2.7.0")
Q7What is CompositionLocal and when should you use it?Medium 
// CompositionLocal: implicit data passing down the composition tree
// Like React Context — avoids passing params through every layer

// Built-in CompositionLocals:
val context = LocalContext.current
val density = LocalDensity.current
val colorScheme = MaterialTheme.colorScheme // uses CompositionLocal internally

// Custom CompositionLocal
val LocalAnalytics = compositionLocalOf<Analytics> { error("No analytics provided") }

@Composable
fun App() {
    CompositionLocalProvider(LocalAnalytics provides AnalyticsImpl()) {
        MainNavigation() // all descendants can access LocalAnalytics.current
    }
}

@Composable
fun SomeDeepChild() {
    val analytics = LocalAnalytics.current // no need to pass through every parent
}

// compositionLocalOf vs staticCompositionLocalOf:
// compositionLocalOf: only recomposes READERS when value changes (smart)
// staticCompositionLocalOf: recomposes ALL children when value changes (use for truly static data)
