Activity & Lifecycle

Q1Explain the complete Activity lifecycle and when each callback is calledHard

Every Activity moves through a well-defined set of lifecycle callbacks that the system calls as the user navigates to, away from, and back to your screen — Android owns this lifecycle, not your app, so knowing exactly when each callback fires is how you decide where it's safe to acquire and release resources. The three states candidates most often get wrong are the transient ones: onPause fires when the Activity partially loses focus but might still be visible, onStop fires only once it's completely hidden, and onDestroy means the Activity object itself is going away. Interviewers ask this because so many real bugs — leaked camera or sensor handles, crashes on rotation, wasted battery from work that never stops — trace back to doing the wrong thing in the wrong callback. The mental model to lead with: onCreate/onDestroy bookend the Activity's entire existence, onStart/onStop bookend visibility, and onResume/onPause bookend whether it's actually in the foreground receiving input.

Complete lifecycle:

// onCreate → onStart → onResume → [RUNNING]
// [RUNNING] → onPause → onStop → onDestroy

class MainActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        // Called once. Initialize UI, set content view, restore state
        // Activity not visible yet
    }
    override fun onStart() {
        // Activity becoming visible but not interactive yet
    }
    override fun onResume() {
        // Activity in foreground, interactive. Register sensors, animations
    }
    override fun onPause() {
        // Partially visible (another activity on top). Release sensors/camera
        // MUST be fast — other activity waits for this to complete
    }
    override fun onStop() {
        // Fully hidden. Release heavy resources, save data
    }
    override fun onDestroy() {
        // Activity being destroyed. Check isFinishing() to know if user exited
    }
    override fun onRestart() {
        // Called before onStart() when coming back from STOPPED state
    }
}

Key interview scenarios:

  • Rotation: onPause → onStop → onDestroy → onCreate → onStart → onResume. Use ViewModel to survive!
  • Home button: onPause → onStop (activity still alive in memory)
  • Back button: onPause → onStop → onDestroy (activity finished)
  • Another activity on top: A.onPause → B.onCreate → B.onStart → B.onResume → A.onStop
  • Coming back from B to A: B.onPause → A.onRestart → A.onStart → A.onResume → B.onStop → B.onDestroy
✓ Google tip: onPause must be fast. Never do heavy operations here. Do them in onStop.
Q2What is the difference between onSaveInstanceState and ViewModel for state preservation?Hard

This question is really about two different survival mechanisms that solve different problems and get confused constantly. onSaveInstanceState hooks into the system's own state-restoration pipeline — it's a Bundle the OS keeps around and hands back to you in onCreate/onRestoreInstanceState, and its whole reason to exist is surviving process death, not just rotation. A ViewModel takes a completely different approach: it's an object that survives configuration changes because the system deliberately keeps the same instance alive across an Activity recreation, but if the OS kills your process entirely while it's backgrounded, that ViewModel and everything in it is gone. Knowing when to reach for which — and why modern code often uses both together via SavedStateHandle — is exactly the kind of practical judgment interviewers are probing for.

onSaveInstanceState (Bundle):

  • Survives: rotation, process death (system kills app while backgrounded)
  • Capacity: small data only (~1MB limit, it's IPC binder transaction)
  • Types: primitives, Parcelable, Serializable
  • When called: before onStop() on API 28+, before onPause() on older

ViewModel:

  • Survives: rotation and configuration changes ONLY
  • Does NOT survive process death — data is gone if system kills the process
  • Capacity: unlimited (holds any object)
  • Best for: complex objects, lists, network results
// Best practice: use BOTH together
class MyViewModel(private val savedStateHandle: SavedStateHandle) : ViewModel() {
    // SavedStateHandle bridges ViewModel + onSaveInstanceState
    // Survives BOTH rotation AND process death
    var searchQuery = savedStateHandle.getStateFlow("query", "")

    fun setQuery(query: String) {
        savedStateHandle["query"] = query // automatically persisted
    }
}
💡 SavedStateHandle is the modern solution — it gives you ViewModel + process death survival.
Q3Explain Fragment lifecycle and how it differs from Activity lifecycleMedium

A Fragment's lifecycle layers on top of the Activity's — it has everything an Activity has (onCreate, onStart, onResume, etc.) plus extra callbacks that exist purely because a Fragment has two separate lifespans: the Fragment object itself, and the View it inflates. onAttach/onDetach mark when the Fragment is connected to or disconnected from its host Activity, while onCreateView/onDestroyView mark when its View hierarchy specifically exists. Interviewers care about this because it's the root cause of one of the most common Android memory leaks: a Fragment can sit on the back stack with its view destroyed while the Fragment object is still very much alive, so anything tied to the view needs to be cleaned up in onDestroyView, not left until onDestroy.

// Fragment has ADDITIONAL callbacks vs Activity:
onAttach()        // Fragment attached to host Activity
onCreate()        // Fragment created (no view yet)
onCreateView()    // Inflate layout, return view
onViewCreated()   // View ready, set up UI here (not onCreateView!)
onStart()
onResume()
onPause()
onStop()
onDestroyView()   // View destroyed but Fragment still alive (backstack)
onDestroy()
onDetach()        // Fragment detached from Activity

Critical difference — onDestroyView: When a Fragment goes to the back stack, only its view is destroyed (onDestroyView), NOT the Fragment itself. The Fragment object stays alive. This is why you must use viewLifecycleOwner (not just lifecycleOwner) when observing LiveData in Fragments — to avoid memory leaks.

// WRONG - leaks if fragment goes to backstack
viewModel.data.observe(this) { ... }

// CORRECT - tied to view lifecycle
viewModel.data.observe(viewLifecycleOwner) { ... }
⚠ This is one of the most common memory leak questions. Always use viewLifecycleOwner in Fragments.
Q4What are the different types of Context and when do you use each?Hard

Context is Android's handle to "everything about the environment your code is running in" — access to resources, system services, the ability to start components — but there isn't just one Context, and picking the wrong one is a classic source of crashes and memory leaks. Application Context lives as long as the whole app process does, which makes it the safe choice for anything you want to outlive a single screen, like a Singleton or a database instance. Activity Context, by contrast, is tied to that specific screen's lifecycle and carries its theme, which is exactly why some UI operations — showing a Dialog, inflating a themed layout — require it and will crash or render incorrectly with an Application Context instead. Interviewers ask this to see if you understand the leak risk of holding an Activity Context longer than the Activity itself lives.

Types:

  • Application Context: Tied to application lifecycle. Use for: creating Singletons, accessing resources, starting Services, registering broadcast receivers when you want them alive as long as the app is alive.
  • Activity Context: Tied to Activity lifecycle. Use for: showing Dialogs, starting Activities (preserves task stack), inflating layouts (gets correct theme), loading theme-dependent resources.
  • Service Context: Tied to Service lifecycle.
// Application Context — for long-lived objects
class ImageLoader(private val context: Context) {
    init {
        // Use applicationContext to avoid leaking Activity
        val appContext = context.applicationContext
    }
}

// Dialog NEEDS Activity context
AlertDialog.Builder(this) // 'this' = Activity ✓
AlertDialog.Builder(applicationContext) // CRASH! ✗
⚠ Memory leak pattern: storing Activity context in a Singleton or static field. Always use application context for Singletons.

Intents & Components

Q5What is the difference between explicit and implicit intents? What is Intent resolution?Medium

An Intent is Android's messaging object for asking some component — your own or another app's — to do something, and the explicit/implicit distinction really comes down to whether you already know exactly who should handle it. An explicit Intent names the target component directly by class, so it's the right choice whenever you're talking to your own app's Activities or Services and there's no ambiguity about the target. An implicit Intent instead just describes an action and some data and leaves it to the system to figure out who can handle it — useful for things like "open this URL" or "share this text" where you don't want to, or can't, know which app will respond. This matters in interviews because it leads directly into how Android actually resolves implicit intents and the security implications around PendingIntents, which is where a lot of real-world bugs and vulnerabilities live.

// Explicit — specifies exact component class
val intent = Intent(this, DetailActivity::class.java)
intent.putExtra("id", userId)
startActivity(intent)

// Implicit — declares action, system resolves which app handles it
val intent = Intent(Intent.ACTION_VIEW).apply {
    data = Uri.parse("https://google.com")
}
if (intent.resolveActivity(packageManager) != null) {
    startActivity(intent) // Opens browser
}

Intent resolution: Android's PackageManager matches implicit intents against all apps' AndroidManifest intent-filter declarations, comparing: action, category, and data (URI/MIME type). If multiple apps match, user sees a chooser.

PendingIntent: A token given to another process to start your Activity/Service/Broadcast on your behalf (e.g. notifications). Always specify mutability flag in API 31+.

// PendingIntent for notification
val pendingIntent = PendingIntent.getActivity(
    context, 0, intent,
    PendingIntent.FLAG_IMMUTABLE // Required API 31+
)
Q6Explain Activity launch modes and how they affect the back stackHard

Launch modes control what happens to the back stack when you start an Activity that might already have an instance running somewhere in the current task — do you get a brand new instance, or does Android reuse an existing one? This matters because the default behavior, standard, creates a new instance every single time, which is fine most of the time but can leave you with a stack full of duplicate screens if you're not careful, for example when a user repeatedly taps the same notification. The four modes trade off exactly how aggressively Android reuses and collapses the stack, from standard's "always create new" all the way to singleInstance's "this Activity owns its own isolated task and nothing else can join it." Interviewers use this question to check whether you can reason about real navigation bugs, like duplicate screens after notification taps or broken back-button behavior after deep links.

  • standard (default): New instance created every time, even if already on stack. Stack: A→B→B→B possible.
  • singleTop: If target is at the TOP of stack, reuses it (calls onNewIntent()). If not on top, creates new. Good for: notifications that launch an activity already open.
  • singleTask: Only ONE instance in the entire task. If exists, all activities on top of it are POPPED and onNewIntent() called. Creates a new task if needed. Good for: deep links, main activity.
  • singleInstance: Like singleTask but the activity lives in its OWN isolated task — no other activities can be added to its task.
// Set via manifest:
<activity android:name=".MainActivity"
    android:launchMode="singleTask"/>

// Or via Intent flags (overrides manifest):
intent.addFlags(Intent.FLAG_ACTIVITY_SINGLE_TOP)
intent.addFlags(Intent.FLAG_ACTIVITY_CLEAR_TOP) // like singleTask
intent.addFlags(Intent.FLAG_ACTIVITY_NEW_TASK) // start in new task
💡 Intent flags take precedence over manifest launchMode. FLAG_ACTIVITY_CLEAR_TOP + FLAG_ACTIVITY_SINGLE_TOP together = singleTask behavior.

Services & Background Work

Q7What are the different types of Services and when would you use each?Hard

A Service is a component for doing work without a UI, but "doing work in the background" means very different things depending on how long it runs and whether anything needs to talk to it — which is why Android splits this into several distinct flavors instead of one generic Service. A started Service is fire-and-forget: something starts it, it runs until it decides to stop itself, and it's vulnerable to being killed under memory pressure since the system has no automatic signal that it's important. A bound Service flips that around — it exists specifically so other components can communicate with it two-way, and it only lives as long as something is bound to it. A foreground Service is the one that comes with a real protection guarantee, but that guarantee costs you a mandatory persistent notification, which is exactly why interviewers want to hear you reach for WorkManager first for anything that can be deferred, rather than defaulting to a Service for every background task.

  • Started Service: Runs indefinitely after startService(). Must call stopSelf() or stopService(). Risk of being killed by OS under memory pressure.
  • Bound Service: Clients bind to it via bindService(). Lives as long as there are bound clients. Returns an IBinder interface. Good for: IPC, two-way communication.
  • Foreground Service: Requires a visible notification. Cannot be killed by OS. Mandatory for user-aware long tasks (music playback, navigation, file download).
  • IntentService (deprecated): Was a started service that ran on a background thread and stopped itself. Replaced by WorkManager or coroutines + Service.
// Foreground Service (API 26+)
class MusicService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val notification = buildNotification()
        startForeground(NOTIF_ID, notification) // Must call within 5s
        return START_STICKY // Restart if killed
    }
}

// WorkManager is preferred for deferrable background work
val request = OneTimeWorkRequestBuilder<SyncWorker>()
    .setConstraints(Constraints(requiresNetwork = true))
    .build()
WorkManager.getInstance(context).enqueue(request)
✓ Modern recommendation: Use WorkManager for deferrable work, Foreground Service for user-aware work, coroutines for in-scope async operations.

Threading & Concurrency

Q8What is the main thread, why can't you do network/disk I/O on it, and what is ANR?Medium

The main thread (UI thread) is responsible for drawing UI frames. Android tries to render at 60fps, giving you ~16ms per frame. If any operation blocks the main thread:

  • UI becomes unresponsive
  • If blocked for >5 seconds (user input) or >10 seconds (broadcast): ANR dialog appears

Common ANR causes: Network call on main thread, slow database query, large bitmap decode, holding a lock that another thread owns, long computation.

// WRONG — Network on main thread (throws NetworkOnMainThreadException)
val data = apiService.fetchData() // in Activity.onCreate()

// CORRECT — Use coroutines with IO dispatcher
class MyViewModel : ViewModel() {
    fun loadData() {
        viewModelScope.launch {
            val data = withContext(Dispatchers.IO) {
                apiService.fetchData() // off main thread
            }
            _uiState.update { it.copy(data = data) } // back on main thread
        }
    }
}
Q9Explain Handler, Looper, and MessageQueue — how does Android's message system work?Hard

Before coroutines existed, this was THE mechanism Android used to move work between threads, and it's still what coroutine dispatchers are built on top of under the hood, which is why interviewers still ask about it. The core idea is simple: a Looper sits on a thread and continuously pulls messages off that thread's MessageQueue and executes them one at a time, and the main thread is only special because Android gives it a Looper automatically at startup. A Handler is your entry point into that queue — it lets you post a Runnable or a Message onto a specific Looper's queue from any other thread, which is exactly how you "hop back to the main thread" after finishing background work. Understanding this model makes it much easier to reason about what something like withContext(Dispatchers.Main) is actually doing underneath the coroutine abstraction.

This is the foundation of Android's threading model (predates coroutines):

  • Looper: Attached to a thread. Runs an infinite loop reading from MessageQueue. The main thread has a Looper by default (Looper.getMainLooper()).
  • MessageQueue: Ordered queue of Messages and Runnables for a specific Looper/thread.
  • Handler: Sends messages/runnables to a specific MessageQueue. When you create Handler(Looper.getMainLooper()), any post() call dispatches to the main thread.
// HandlerThread — creates a thread with a Looper
val handlerThread = HandlerThread("BackgroundThread").apply { start() }
val bgHandler = Handler(handlerThread.looper)
val mainHandler = Handler(Looper.getMainLooper())

bgHandler.post {
    val result = doHeavyWork() // background thread
    mainHandler.post { updateUI(result) } // switch to main
}

// Modern equivalent with coroutines:
viewModelScope.launch(Dispatchers.IO) {
    val result = doHeavyWork()
    withContext(Dispatchers.Main) { updateUI(result) }
}
💡 Coroutines abstract away Handler/Looper complexity, but understanding the underlying model helps debug threading issues.
Q10What are common memory leak patterns in Android and how do you detect them?Hard

Memory leaks in Android almost always come down to the same root cause: something that should be garbage collected — usually an Activity or Fragment — is still being held onto by a reference that outlives it, so the whole View tree and everything it points to stays in memory even after the screen is gone. This matters enormously on mobile because devices have far less memory headroom than a server or desktop, so a handful of leaked Activities can be the difference between smooth performance and the OS killing your app for using too much RAM. Most of the classic patterns are variations on the same mistake — a long-lived object like a static field, a singleton, or a pending callback holding a reference to a short-lived one like an Activity, a View, or a Context — which is why the fix is almost always either scoping the reference correctly or explicitly clearing it when the short-lived object is destroyed.

Common leak patterns:

  • Static reference to Activity/View: Static companion objects holding Context or View
  • Non-static inner class: AsyncTask, Handler inner class implicitly holds outer Activity reference
  • Fragment viewLifecycleOwner: Observing LiveData with this instead of viewLifecycleOwner
  • Unregistered listeners: Registering BroadcastReceiver, SensorManager, LocationManager but not unregistering
  • Bitmap held in static: Large bitmaps held by static fields
  • RxJava/Flow subscriptions: Not disposing/cancelling subscriptions on destroy
// LEAK: static handler holds Activity reference
class MainActivity : Activity() {
    private val handler = object : Handler(Looper.getMainLooper()) {
        override fun handleMessage(msg: Message) {
            // Implicit reference to MainActivity — leaks if delayed message pending
        }
    }
    override fun onDestroy() {
        handler.removeCallbacksAndMessages(null) // Fix: remove pending messages
        super.onDestroy()
    }
}

Detection:

  • LeakCanary: Add to debugImplementation, it automatically detects and reports leaks
  • Android Profiler: Memory tab → take heap dump → look for Activity/Fragment instances that shouldn't exist
  • StrictMode: Enables strict VM/thread policies in debug builds

BroadcastReceiver & ContentProvider

Q11What is a BroadcastReceiver? Static vs dynamic registration?Medium

A BroadcastReceiver is Android's publish-subscribe mechanism for system-wide and app-wide events — things like battery state changes, connectivity changes, or your own app's custom events — where you want to react without polling or holding a persistent connection open. The static-vs-dynamic choice really comes down to lifetime and cost: a manifest-declared receiver can wake your app up even when it isn't running at all, which is powerful but also exactly why Google locked it down hard starting in API 26, since apps were abusing it to launch themselves constantly in the background and drain battery. A dynamically registered receiver only exists while the registering component is alive and must be explicitly unregistered, trading that always-on capability for being lighter weight and safer by default. Interviewers ask this to see whether you know that registering without unregistering is a leak, and whether you understand why the manifest approach was restricted in the first place.

  • Static (manifest): System can launch app to deliver broadcast even if app not running. Severely restricted since API 26 — only certain system broadcasts allowed (BOOT_COMPLETED, etc.).
  • Dynamic (code): Registered while app is running. Must unregister to avoid leaks.
// Dynamic registration — register in onStart, unregister in onStop
private val receiver = object : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        when (intent.action) {
            Intent.ACTION_BATTERY_LOW -> handleLowBattery()
        }
    }
}

override fun onStart() {
    super.onStart()
    val filter = IntentFilter(Intent.ACTION_BATTERY_LOW)
    registerReceiver(receiver, filter)
}
override fun onStop() {
    unregisterReceiver(receiver) // ALWAYS unregister
    super.onStop()
}
💡 Ordered broadcasts: receivers process in order of priority. A receiver can abort the chain with abortBroadcast().
Q12When would you use a ContentProvider and how does it work?Medium

ContentProvider is Android's abstraction for exposing a structured, queryable dataset behind a stable URI, with the OS enforcing permission checks on every access — it's how apps share data with each other and with the system without any of them needing direct file-system access to another app's private storage. It matters because it decouples the data's storage format from how other components consume it: the consumer just queries a URI and gets back a Cursor, with no idea, or need to know, whether the data lives in SQLite, a network cache, or in-memory. It's also the mechanism the platform itself uses for shared data like Contacts and MediaStore, and it's why several libraries piggyback a hidden ContentProvider onto your app purely to get an early, guaranteed initialization hook before your own Application code runs.

ContentProvider exposes structured data via a URI scheme, allowing cross-process data sharing with access control.

Use cases: Contacts, Calendar, MediaStore, sharing data between apps, providing data to system (SearchSuggestions).

// URI pattern: content://authority/path/id
val uri = Uri.parse("content://com.example.provider/users/42")

// Querying (runs on binder thread pool — NOT main thread)
val cursor = contentResolver.query(uri, null, null, null, null)
cursor?.use {
    while (it.moveToNext()) {
        val name = it.getString(it.getColumnIndexOrThrow("name"))
    }
}

// FileProvider — secure file sharing between apps
val fileUri = FileProvider.getUriForFile(
    context, "com.example.fileprovider", file
)

Process, Lifecycle & System Internals

Q13Explain the Application class lifecycle relative to the first Activity, and the multi-process footgun with singletonsHard

Startup order (classic trick question): the Application's constructor and attachBaseContext() run first, then every ContentProvider declared in the manifest gets its onCreate() called — before Application.onCreate(). Only after that does Application.onCreate() run once per process, and only THEN does whichever component actually triggered the process start (your launcher Activity, a Service, a BroadcastReceiver) get its own onCreate(). This ordering is exactly why libraries like Firebase, WorkManager, and Jetpack App Startup bootstrap via a hidden ContentProvider — it guarantees they're ready before your own Application code runs.

Multi-process apps: adding android:process=":remote" to a component gives it its own Linux process with its own ART heap. Android instantiates a separate Application object per process — static fields and singletons are never shared across the boundary; the only way to communicate is real IPC (Binder, ContentProvider, files, sockets).

⚠ The footgun: a singleton built in Application.onCreate() assuming "this runs once for my whole app" actually runs once per process. A :remote Service gets its own Room connection, its own analytics session (duplicate events), its own Hilt component — wasting memory and risking two processes writing the same SQLite file concurrently.
override fun onCreate() {
    super.onCreate()
    if (getProcessName() != packageName) return // skip heavy init in :remote
    Analytics.init(this)
    AppDatabase.getInstance(this)
}
Q14Explain Android's process priority levels and how the low-memory killer decides what to kill. How does onTrimMemory() fit in?Hard

Android devices have no swap, so instead of paging to disk under memory pressure the system kills entire processes. Every process gets an importance score from what's running inside it — from most to least protected: a foreground process (a RESUMED Activity, a startForeground() Service, an executing BroadcastReceiver), a visible process (Activity visible but not focused), a service process (started Service doing background work), and finally cached/background processes with no active components, kept only so re-launching feels instant. The killer works strictly bottom-up — it reclaims the least-recently-used cached process first, and only reaches into higher tiers if that's not enough.

onTrimMemory(level) is your warning shot before the killer gets to you: the system calls it on your Application/Activity/Fragment/Service to ask you to release memory voluntarily. UI_HIDDEN fires when your whole UI just left the screen (drop view/bitmap caches); RUNNING_LOW/CRITICAL fire while you're still in the foreground but the device overall is tight; BACKGROUND/COMPLETE fire once you're cached, with COMPLETE meaning you're near the top of the kill list.

override fun onTrimMemory(level: Int) {
    if (level >= ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN) {
        imageCache.evictAll() // app not visible — safe to drop UI caches
    }
}
Q15What does a PendingIntent actually wrap, and why is the mutable/immutable flag a security-critical choice?Hard

A PendingIntent wraps an Intent together with your app's identity and permissions, as a token you hand to another process (NotificationManager, AlarmManager, a launcher widget host). When that process later calls send(), your Intent fires as if your app itself had called it — even though the trigger runs in someone else's process.

Since Android 12 you must pick one of: FLAG_IMMUTABLE (nobody holding the token can alter the wrapped Intent — default, safe) or FLAG_MUTABLE (only needed when the receiver must fill in data, e.g. notification RemoteInput).

⚠ Classic vulnerability: pairing an implicit Intent (no explicit target component) with a mutable PendingIntent lets anyone who obtains the token overwrite its action/data/component via a "fill-in" Intent — hijacking it to launch an attacker component with your app's permissions. This exact pattern was found in dozens of popular apps in 2020 security audits.
val pendingIntent = PendingIntent.getActivity(
    context, 0,
    Intent(context, ResultActivity::class.java), // explicit — safe target
    PendingIntent.FLAG_IMMUTABLE
)
Q16Bundle vs Parcelable vs Serializable — how does Parcelable actually work under the hood, and what does @Parcelize do?Medium

Bundle is a Map-like container (Intent extras, Fragment arguments, onSaveInstanceState) that is itself backed by a Parcel. Parcelable is Android's own serialization contract: writeToParcel() marshals each field directly into a shared native buffer in a fixed order, and the CREATOR reads them back in that same order — no reflection, minimal allocation, built for the thousands of IPC calls Android makes per second. Serializable is a plain Java interface that uses reflection to walk the whole object graph at runtime — much slower, more garbage, and fragile across app versions without a manually-maintained serialVersionUID.

@Parcelize
data class User(val id: Int, val name: String) : Parcelable
// compiler generates writeToParcel()/CREATOR for you — same mechanism as manual Parcelable:
override fun writeToParcel(parcel: Parcel, flags: Int) {
    parcel.writeInt(id)       // order must match CREATOR's read order exactly
    parcel.writeString(name)
}
✓ Always prefer Parcelable (via @Parcelize) for anything crossing an Intent/Bundle boundary. Serializable's only edge is portability to plain-JVM code/tests where Parcel isn't available.
Q17Explain Doze mode and App Standby Buckets — how does Android throttle background work, and what does battery-optimization "whitelisting" do?Hard

Doze (API 23+) kicks in when the device is stationary, unplugged, and screen-off for a while: network access, wake locks, JobScheduler/WorkManager jobs, syncs, and normal alarms are all suspended except during brief periodic maintenance windows. Only setExactAndAllowWhileIdle() alarms still fire outside those windows, rate-limited to roughly once per 9 minutes.

App Standby Buckets (API 28+) apply on top of Doze, independent of device idle state — they throttle based on how recently/often this specific app is used: Active → Working set → Frequent → Rare → Restricted, each with fewer daily job windows and tighter FCM quotas.

Whitelisting (REQUEST_IGNORE_BATTERY_OPTIMIZATIONS) exempts your app's alarms/network/jobs from Doze deferral once the user explicitly grants it — reserved for apps with a genuine real-time need (VOIP, alarm clocks); Play Store policy flags misuse. WorkManager jobs are simply deferred to the next maintenance window like any JobScheduler job (unless setExpedited()); FCM high-priority messages are explicitly designed to punch through Doze and wake the app briefly, which is why sync-triggering pushes should always be sent high-priority.

val intent = Intent(Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS)
    .apply { data = Uri.parse("package:$packageName") }
startActivity(intent) // user must approve explicitly
Q18What are the modern (Android 14) requirements for a Foreground Service, and why can't a regular Service reliably do long-running work anymore?Hard

A plain started Service has no protection beyond "service process" priority — as soon as your app leaves the foreground it drifts toward the cached bucket and can be reclaimed. Worse, since API 26 an app that's itself in the background cannot even call startService() for long work — it throws, forcing startForegroundService() and a promotion to foreground within 5 seconds. There's no reliable way to run indefinite work from a plain Service anymore; that gap is exactly what WorkManager and Foreground Services exist to fill.

Requirements accumulated across API levels: a persistent notification within 5s of starting (26+), the FOREGROUND_SERVICE permission (28+), a declared android:foregroundServiceType for sensitive work (29+), background-start restrictions with narrow exceptions (31+), runtime POST_NOTIFICATIONS permission (33+), and — new in Android 14 (34) — every Foreground Service must declare a specific type (dataSync, location, mediaPlayback, camera, microphone, phoneCall, connectedDevice, health, remoteMessaging, shortService, specialUse, …) both in the manifest and at startForeground(), each gated by its own permission. Some types now carry a hard runtime cap — dataSync is capped around 6 hours per 24h — and omitting the type throws MissingForegroundServiceTypeException.

<service android:name=".SyncService"
    android:foregroundServiceType="dataSync"/>

startForeground(
    NOTIF_ID, buildNotification(),
    ServiceInfo.FOREGROUND_SERVICE_TYPE_DATA_SYNC // required on API 34+
)
✓ Interview takeaway: prefer WorkManager for anything deferrable (it self-promotes to expedited/foreground execution when needed); reserve manual Foreground Services for genuinely user-aware, continuous work where the persistent notification is a feature, not a checkbox.

Permissions & Manifest

Q19Explain the runtime permission flow — dangerous vs normal vs signature permissions, and shouldShowRequestPermissionRationaleEasy

Android's permission model isn't one-size-fits-all — it splits permissions into tiers based on how much privacy or security risk they carry, and only the risky ones ever interrupt the user with a runtime dialog. Permissions that don't expose sensitive data or capabilities are granted automatically at install time so the user isn't nagged for things like checking network state. The ones that genuinely touch sensitive data — camera, location, contacts — must be requested at runtime starting with API 23, and critically the user can revoke any of them individually at any time from Settings, so your app can never assume a permission it had yesterday is still granted today. Interviewers ask this to see if you handle the full state machine correctly: not just the happy path of asking and getting granted, but denial, rationale, and the "don't ask again" case that you can't even detect directly.

Protection levels:

  • normal: Auto-granted at install time (INTERNET, ACCESS_NETWORK_STATE) — low risk to privacy, no user prompt needed.
  • dangerous: Grouped into permission groups (CAMERA, LOCATION, CONTACTS...) and must be requested at runtime on API 23+; user can revoke individually anytime from Settings.
  • signature: Auto-granted only to apps signed with the same certificate as the app that declared the permission — used for permissions between your own apps.
private val requestPermission = registerForActivityResult(
    ActivityResultContracts.RequestPermission()
) { granted: Boolean ->
    if (granted) startCamera() else showRationaleUi()
}

fun checkCameraPermission() {
    when {
        ContextCompat.checkSelfPermission(this, Manifest.permission.CAMERA)
            == PackageManager.PERMISSION_GRANTED -> startCamera()

        shouldShowRequestPermissionRationale(Manifest.permission.CAMERA) ->
            // user denied once before but didn't check "don't ask again" — explain WHY you need it
            showRationaleDialog { requestPermission.launch(Manifest.permission.CAMERA) }

        else -> requestPermission.launch(Manifest.permission.CAMERA)
        // covers both "never asked" AND "denied + checked don't ask again" — you can't tell them apart!
    }
}
💡 shouldShowRequestPermissionRationale() returning false has two meanings: never asked yet, or permanently denied. You can't distinguish them programmatically — track "have I asked before" yourself in SharedPreferences if you need to show a "go to Settings" prompt.
Q20What are special permissions and one-time permissions, and how does permission auto-reset work?Medium

Some capabilities are too sensitive for a simple runtime dialog and require an explicit Settings redirect instead of requestPermissions():

  • SYSTEM_ALERT_WINDOW (draw over other apps) — granted only via Settings.ACTION_MANAGE_OVERLAY_PERMISSION.
  • SCHEDULE_EXACT_ALARM (API 31+) — check with AlarmManager.canScheduleExactAlarms(), redirect to ACTION_REQUEST_SCHEDULE_EXACT_ALARM if denied.
  • Background location (API 29+) — must be requested as a SEPARATE second step after foreground location is already granted; the system won't even show a combined dialog on API 30+, forcing a two-step flow so users understand exactly what they're granting.

One-time permission (API 30+): the permission dialog offers "Only this time" — the grant is automatically revoked once the user leaves the app (backgrounds it or swipes it away).

Permission auto-reset (API 30+, and Play-enforced on older targets via Google Play services): if a user hasn't opened your app for a few months, the system automatically revokes all granted runtime permissions to reduce the app's ambient attack surface — your app must gracefully re-request on next launch rather than assume a prior grant still holds.

val canScheduleExact = alarmManager.canScheduleExactAlarms()
if (!canScheduleExact) {
    startActivity(Intent(Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM))
}
Q21How does manifest merging work when a project has multiple modules and libraries?Medium

Gradle merges every manifest that contributes to a build variant — the app module's main manifest, its build-variant-specific manifest (e.g. debug/AndroidManifest.xml), and every AAR library's own manifest — into one final manifest. Priority order (highest wins on conflict): build-variant manifest > build-type manifest > app main manifest > library manifest > lower-priority library manifest (dependency order).

Merging is attribute-by-attribute: matching elements (same tag + same identifying attribute, e.g. same android:name on an <activity>) merge their non-conflicting attributes; a real conflict (e.g. two libraries requesting different android:value for the same meta-data key) fails the build unless resolved explicitly.

<!-- force-remove a permission a library declares that you don't want -->
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION"
    tools:node="remove"/>

<!-- override a conflicting attribute instead of merging -->
<activity android:name="com.lib.SomeActivity"
    android:theme="@style/MyTheme"
    tools:node="replace"/>
✓ Android Studio's "Merged Manifest" tab (bottom of the manifest editor) shows exactly which source file contributed each line — the fastest way to debug an unexpected permission or attribute.
Q22Walk through the intent-filter matching algorithm — how does Android decide which components can handle an implicit Intent?Medium

PackageManager runs three independent tests against every declared <intent-filter>; all three must pass for a match:

  • Action test: if the Intent specifies an action, the filter must list that exact action (a filter can list several). If the Intent has no action, it passes automatically.
  • Category test: every category on the Intent must be present in the filter (filter can have extra categories, that's fine — it's a subset check). Note: startActivity() implicitly adds CATEGORY_DEFAULT to the Intent, so a filter that omits <category android:name="android.intent.category.DEFAULT"/> will never match an implicit startActivity() call.
  • Data test: compares scheme, host, port, path, and MIME type against the filter's <data> tags. If the Intent supplies a URI/type and the filter declares no <data> at all, it fails — unless the Intent also supplies neither.
<intent-filter>
    <action android:name="android.intent.action.VIEW"/>
    <category android:name="android.intent.category.DEFAULT"/>
    <category android:name="android.intent.category.BROWSABLE"/>
    <data android:scheme="https" android:host="example.com" android:pathPrefix="/product"/>
</intent-filter>
💡 If multiple installed apps match, the system shows a disambiguation chooser (unless the caller used createChooser() to force it, or the target uses App Links / autoVerify to skip it entirely).

Fragments Deep Dive

Q23Explain FragmentManager's back stack, and when to use childFragmentManager vs parentFragmentManagerMedium

A FragmentTransaction (add/replace/remove) becomes undoable history only if you call addToBackStack(name) before commit() — pressing Back then pops the transaction rather than the whole Activity. commit() is asynchronous (queued on the main thread's message queue); commitNow() executes synchronously but is incompatible with addToBackStack.

parentFragmentManager is the FragmentManager that hosts THIS fragment (usually the Activity's, or another fragment's if nested) — use it when a fragment needs to replace itself or a sibling. childFragmentManager belongs to this fragment and manages fragments nested INSIDE it (e.g. a ViewPager's pages, or a nested tab layout) — using it instead of the parent's keeps container view IDs, back stack entries, and fragment tags scoped to this fragment, avoiding ID collisions when the same fragment class is reused in multiple places.

// Inside a Fragment hosting its own nested tabs
childFragmentManager.beginTransaction()
    .replace(R.id.nested_container, TabContentFragment())
    .addToBackStack(null)
    .commit()
⚠ Using parentFragmentManager (or the Activity's manager) for nested UI is a classic bug source: two instances of the same fragment end up sharing container IDs and stomping each other's back stack entries.
Q24How does the Fragment Result API work, and why did it replace setTargetFragment()?Medium

setTargetFragment() was deprecated because it created a direct, non-lifecycle-aware reference between two fragments — if the target fragment was recreated (e.g. after a config change) the link silently broke, and it only worked one level deep (no support for Activity-to-Fragment results).

The Fragment Result API routes results through the shared FragmentManager using a String key, so the sender and listener never hold a direct reference to each other — either side can be recreated independently:

// Fragment B sets a result before popping back
setFragmentResult("requestKey", bundleOf("selectedId" to id))

// Fragment A listens — lifecycle-aware, only delivered when STARTED
parentFragmentManager.setFragmentResultListener("requestKey", viewLifecycleOwner) { _, bundle ->
    val id = bundle.getInt("selectedId")
    updateSelection(id)
}

Both fragments must share the same FragmentManager (i.e. the listener is registered on the manager that hosts the fragment sending the result, or an ancestor of it) — a child fragment's result naturally propagates up through parentFragmentManager calls.

✓ Results are cached if the listener isn't STARTED yet, and delivered as soon as it reaches STARTED — no race condition on rotation.
Q25A single Fragment instance can have its view created and destroyed multiple times — how does that affect ViewBinding and RecyclerView adapter setup?Medium

The Fragment object (and its non-view state) can survive across multiple view creations: every time the fragment becomes visible again from the back stack, onCreateView()/onViewCreated() run again on the SAME Fragment instance, and every time it's pushed under another fragment, onDestroyView() runs — the Fragment itself is not recreated. Anything tied to the view (ViewBinding, RecyclerView adapters, listeners) must therefore be created in onViewCreated() and explicitly released in onDestroyView(), never held for the Fragment's full lifetime.

class ListFragment : Fragment(R.layout.fragment_list) {
    private var _binding: FragmentListBinding? = null
    private val binding get() = _binding!! // only valid between onViewCreated..onDestroyView

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        _binding = FragmentListBinding.bind(view)
        binding.recyclerView.adapter = ItemAdapter() // created fresh every time the view exists
    }

    override fun onDestroyView() {
        super.onDestroyView()
        binding.recyclerView.adapter = null // break the adapter → view reference
        _binding = null // prevents leaking the old View through the binding
    }
}
⚠ Forgetting to null out the binding in onDestroyView leaks the entire View tree for as long as the Fragment instance survives on the back stack — a very common LeakCanary finding.

Resources, Configuration & Packaging

Q26What actually happens to an Activity on a configuration change like rotation, and when (if ever) should you handle it manually with android:configChanges?Medium

By default, ANY relevant configuration change (orientation, screen size, locale, keyboard availability, UI mode/night mode, density...) destroys and recreates the current Activity: onPause→onStop→onDestroy, then onCreate→onStart→onResume, so it can reload resources from the newly-matching qualifier buckets (e.g. a layout-land/ folder) and rebuild its views against the new configuration.

<!-- Manually handle instead of recreating — Activity gets a callback instead -->
<activity android:name=".CameraActivity"
    android:configChanges="orientation|screenSize|keyboardHidden"/>
override fun onConfigurationChanged(newConfig: Configuration) {
    super.onConfigurationChanged(newConfig)
    // you're now responsible for re-laying-out anything orientation-dependent yourself
}

When it's justified: rare cases where recreation is genuinely too expensive or disruptive to restart mid-operation — e.g. an active Camera preview or a video call where tearing down the surface would be jarring.

⚠ It's discouraged as a general fix for "rotation breaks my screen": it silently skips the entire resource-reload mechanism (you won't pick up layout-land/values-w600dp/etc. automatically), and it doesn't exist as an option for most real config-change bugs — the correct fix is almost always ViewModel + proper state restoration, not opting out of recreation.
Q27How does Android pick the best-matching resource when you have multiple qualified resource folders (drawable-hdpi, values-fr, layout-sw600dp...)?Easy

At runtime, Android walks a fixed precedence order of qualifier types and, for each one in turn, eliminates every resource folder that doesn't match the device's current value for that qualifier — unless eliminating would leave zero candidates, in which case that qualifier is skipped. Roughly, from highest to lowest precedence: MCC/MNC → language/region → layout direction (ltr/rtl) → smallest width (sw<N>dp) → available width/height → screen size (small/normal/large) → screen aspect → round screen → orientation → UI mode (car/tv/watch) → night mode → density → touchscreen → keyboard/nav availability → platform version.

res/
  values/strings.xml           // default fallback
  values-fr/strings.xml        // French locale
  layout/activity_main.xml     // default
  layout-sw600dp/activity_main.xml   // tablets (≥600dp smallest width)
  drawable-hdpi/icon.png
  drawable-xxhdpi/icon.png     // closest density match preferred, else scaled

Density is special: if no exact density match exists, Android picks the nearest available bucket and scales the bitmap (e.g. an xxhdpi asset scaled down for an hdpi screen) rather than failing — which is why shipping only one very high-res density folder still "works" everywhere, just with runtime scaling cost and blur risk on very low-density devices.

Q28What's the difference between an APK and an Android App Bundle (.aab), and what are dynamic feature modules?Medium

An APK is the installable unit — one file containing all code and resources for every device configuration you support. An App Bundle (.aab) is NOT installable directly; it's a publishing format you upload to Play Console containing everything unsplit, plus metadata. Play's servers then perform dynamic delivery: they generate and serve a set of small split APKs tailored to each requesting device — a base APK plus splits for its specific ABI, screen density, and language only — instead of shipping every density/ABI/language to every device.

  • Base APK: core code + resources needed to launch.
  • Configuration splits: device-specific density/ABI/language splits, auto-generated by Play — you never write these yourself.
  • Dynamic feature modules: separate Gradle modules (com.android.dynamic-feature plugin) for optional functionality, delivered on-demand (fetched only when requested via SplitInstallManager), install-time but as a separate split, or conditionally (device meets criteria like minSdk or feature availability).
✓ Since August 2021, Play Console requires AAB for new apps — the size savings from per-device splitting (often 15-50% smaller downloads) are the main driver, on top of enabling dynamic feature delivery.
Q29What was Multidex, why was it needed, and is it still relevant?Easy

A single classic DEX file can reference at most 65,536 methods (the "64K limit") — the method reference index is a 16-bit short. Once an app plus its dependencies crossed that count (very easy with libraries like Google Play Services, AndroidX, etc.), the build would fail with DexIndexOverflowException.

The androidx.multidex support library solved this pre-API 21 by splitting compiled code across multiple classes.dex files and patching the Application class (MultiDexApplication, or manually calling MultiDex.install(this) in attachBaseContext()) to load them all at startup.

// build.gradle — only relevant if minSdk < 21
android {
    defaultConfig { multiDexEnabled = true }
}
dependencies { implementation("androidx.multidex:multidex:2.0.1") }
💡 Is it still relevant? Since API 21, ART (Android RunTime) natively supports loading multiple DEX files at install time with no extra work — so if your minSdk is 21+, you almost never need to touch multidex config manually; AGP handles multiple dex files transparently. It only still matters for very large legacy apps targeting API <21, which is now rare.

Notifications & Deep Links

Q30How do notification channels work (API 26+), and why can't your app change a channel's importance after creating it?Easy

Since Android 8.0, every notification must belong to a NotificationChannel (grouped further into optional channel groups), each with its own importance level controlling how intrusive it is: from IMPORTANCE_NONE (blocked, no display) up through LOW (no sound, shows in shade), DEFAULT (sound, no peek), to HIGH/MAX (sound + heads-up peek).

val channel = NotificationChannel(
    "messages", "New Messages", NotificationManager.IMPORTANCE_HIGH
).apply { description = "Incoming chat messages" }
notificationManager.createNotificationChannel(channel) // safe to call every launch — no-op if it already exists

Why the app can't change importance later: once a channel is created, its behavioral settings (importance, sound, vibration) become user-owned — only the user can change them via system Settings, exactly to stop apps from silently escalating themselves back to noisy after a user turns a channel down. Calling createNotificationChannel() again with a different importance on an existing channel ID is silently ignored; only non-behavioral fields like name/description can still be updated by the app.

💡 Design implication: create channels granularly (e.g. separate "Messages" vs "Promotions" channels) from day one — you can't retroactively split a channel's users into finer-grained importance buckets.
Q31What's the difference between a plain deep link and a verified Android App Link?Medium

Both mechanisms let a URL open your app directly instead of a browser, but they differ in exactly how much the system trusts that your app is the right one to handle it, and that trust gap is a real security concern, not just a technicality. A plain deep link is just a claim — any app can declare an intent-filter for any scheme or host it wants, so if two apps both claim the same URL pattern the user gets a disambiguation dialog, and worse, a malicious app can deliberately claim your domain's URLs to intercept traffic meant for you. An Android App Link closes that gap by requiring cryptographic proof of domain ownership: you host a JSON file at a well-known path on your actual domain, signed against your app's certificate, and once the system verifies that it routes matching links straight to your app with no chooser and no way for another app to spoof it. This is exactly the kind of distinction interviewers probe to see if you understand deep linking as a security surface, not just a navigation convenience.

  • Standard deep link: any <intent-filter> with ACTION_VIEW + a matching scheme/host (custom scheme like myapp://, or an http/https URL without verification). Any app declaring a matching filter is a candidate — if more than one app matches, the user sees a disambiguation chooser, and the link can be silently hijacked by a malicious app claiming the same host.
  • Android App Link (verified): an https intent-filter with android:autoVerify="true", backed by a assetlinks.json file hosted at https://domain/.well-known/assetlinks.json proving you control that domain (signed by your app's certificate fingerprint). Once verified, the system opens the link directly in your app with no chooser, and it can't be spoofed by another app since domain ownership was cryptographically checked.
<intent-filter android:autoVerify="true">
    <action android:name="android.intent.action.VIEW"/>
    <category android:name="android.intent.category.DEFAULT"/>
    <category android:name="android.intent.category.BROWSABLE"/>
    <data android:scheme="https" android:host="example.com"/>
</intent-filter>
// hosted at https://example.com/.well-known/assetlinks.json
[{
  "relation": ["delegate_permission/common.handle_all_urls"],
  "target": {"namespace": "android_app", "package_name": "com.example.app", "sha256_cert_fingerprints": ["..."]}
}]
Q32A notification or deep link opens a detail screen deep in your app's hierarchy — how do you make the system Back button behave correctly?Hard

If you just startActivity() straight to a detail screen with FLAG_ACTIVITY_NEW_TASK, pressing Back exits the app entirely — there's no parent screen underneath because the task's back stack only ever contained that one Activity. TaskStackBuilder synthesizes a fake back stack so Back navigates up through the app's natural hierarchy instead of straight out.

TaskStackBuilder.create(context)
    .addNextIntentWithParentStack(Intent(context, DetailActivity::class.java))
    .getPendingIntent(0, PendingIntent.FLAG_IMMUTABLE)

addNextIntentWithParentStack() reads the target Activity's declared android:parentActivityName chain (the same one used for the toolbar's Up button) from the manifest to know which ancestor screens to synthesize:

<activity android:name=".DetailActivity"
    android:parentActivityName=".CategoryActivity"/>
✓ This is the same mechanism behind the toolbar's "Up" button — Up and a synthesized Back both walk the parentActivityName chain, so setting it up once fixes both.

Storage Permissions & Scoped Storage

Q33What is Scoped Storage and why can't apps freely access other apps' files anymore?Hard

Before API 29, any app holding READ/WRITE_EXTERNAL_STORAGE could read or write almost anywhere on shared external storage — a huge privacy leak (one app could snoop on every other app's downloads/photos). Scoped Storage (opt-in on API 29 via requestLegacyExternalStorage="true", enforced for all apps targeting API 30+) confines each app to a sandbox instead:

  • App-private directory (getExternalFilesDir(), getFilesDir()): always fully accessible, no permission needed, wiped on uninstall.
  • Shared media collections (MediaStore.Images/Video/Audio): apps can insert their OWN media without any storage permission at all, and can read/query media they created without permission too; reading media created by OTHER apps needs READ_MEDIA_IMAGES/VIDEO/AUDIO (API 33+, replacing the old blanket READ_EXTERNAL_STORAGE).
  • Arbitrary user-chosen files (any other app's documents, Downloads, etc.): only via the Storage Access Framework — ACTION_OPEN_DOCUMENT / ACTION_CREATE_DOCUMENT — which hands your app a scoped, user-approved Uri, not a raw file path.
val values = ContentValues().apply {
    put(MediaStore.Images.Media.DISPLAY_NAME, "photo.jpg")
    put(MediaStore.Images.Media.MIME_TYPE, "image/jpeg")
}
val uri = contentResolver.insert(MediaStore.Images.Media.EXTERNAL_CONTENT_URI, values)
// no WRITE_EXTERNAL_STORAGE needed — you own what you insert
⚠ Raw java.io.File paths into other apps' storage (e.g. hardcoded /storage/emulated/0/DCIM/...) silently stop working under Scoped Storage — this is the single most common Android 10/11 migration bug.
Q34What is the Photo Picker API and how does it avoid needing storage permissions entirely?Medium

The Photo Picker (built into API 33+, and backported to API 21+ via an updatable Google Play services module) is a system-provided, privacy-friendly picker UI for images/video. It runs as a separate process/UI outside your app and hands back only the specific items the user selected as temporary read-only Uris — your app never needs READ_MEDIA_IMAGES or any storage permission at all to use it, since the user's selection IS the grant.

private val pickMedia = registerForActivityResult(
    ActivityResultContracts.PickVisualMedia()
) { uri: Uri? ->
    uri?.let { loadImage(it) }
}

pickMedia.launch(PickVisualMediaRequest(ActivityResultContracts.PickVisualMedia.ImageOnly))
✓ Prefer the Photo Picker over MediaStore queries whenever you just need the user to pick a few images/videos — zero permission prompts means fewer users bouncing off a permission dialog.

Build Tooling & Optimization

Q35What do ProGuard/R8 actually do, and what's the most common way keep-rule mistakes surface?Medium

R8 is the default compiler/optimizer since AGP 3.4 (it replaced ProGuard's separate optimization pass while staying compatible with ProGuard's -keep rule syntax) and performs three distinct jobs in one pass:

  • Shrinking: removes classes/methods/fields that static analysis proves are unreachable from your app's entry points — smaller APK/AAB.
  • Obfuscation: renames remaining classes/members to short meaningless names (a, b, c...) — smaller AND harder to reverse-engineer.
  • Optimization: inlines short methods, removes dead branches, merges classes where safe — faster bytecode.
// build.gradle
buildTypes {
    release {
        isMinifyEnabled = true
        proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro")
    }
}
// proguard-rules.pro — keep anything reflection/serialization touches
-keep class com.example.model.** { *; }   // e.g. Gson model classes
-keepclassmembers class * implements android.os.Parcelable {
    public static final android.os.Parcelable$Creator *;
}
⚠ The classic gotcha: R8 strips/renames anything it can't prove is used, but reflection (Gson field access, Retrofit's dynamic proxy interfaces, Room, custom Parcelable CREATOR lookups) is invisible to static analysis. Debug builds don't minify by default, so everything "works" until the FIRST release build — where it crashes with ClassNotFoundException/NoSuchFieldException. Always test the actual release/minified build before shipping, and prefer @Keep annotations on specific classes over broad -keep class ** { *; } rules that defeat shrinking entirely.
Q36Explain build types vs product flavors and how they combine into build variantsMedium

Gradle gives you two independent axes for customizing a build, and conflating them is a common early mistake. Build types answer "how is this build compiled and packaged" — is it debuggable, is it minified, which keystore signs it — and every project needs at least a debug and a release type. Product flavors answer a completely different question, "what variant of the app am I building" — different branding, different backend environment, different feature set, different applicationId — and you can have as many as your product needs, organized into dimensions when there's more than one independent axis, like environment crossed with tier. Gradle then multiplies every flavor by every build type to produce the full matrix of build variants, which is exactly why interviewers ask this: it's the foundation for how real Android projects manage things like free/paid tiers or dev/staging/prod environments without duplicating code.

  • Build types (debug/release by default, you can add more like staging): control HOW the app is built — signing config, minification, debuggable flag, resource shrinking. Every project needs at least one.
  • Product flavors (e.g. free/paid, or dev/staging/prod as one dimension crossed with internal/external as another): control WHAT is built — different applicationId suffix, different feature sets, different backend URLs, different resources — grouped into flavor dimensions when you need more than one axis.

Gradle computes the cross-product: every flavor × every build type = one build variant (e.g. freeDebug, freeRelease, paidDebug, paidRelease). Each flavor can have its own source set (src/free/kotlin/..., src/free/res/...) that overlays on top of src/main.

android {
    flavorDimensions += "tier"
    productFlavors {
        create("free") { dimension = "tier"; applicationIdSuffix = ".free"
            buildConfigField("boolean", "HAS_ADS", "true") }
        create("paid")  { dimension = "tier"
            buildConfigField("boolean", "HAS_ADS", "false") }
    }
}
// generated per-variant, usable at runtime
if (BuildConfig.HAS_ADS) { showAdBanner() }
Q37What's the difference between an upload key and an app signing key, and what is Play App Signing?Medium

Every release APK/AAB must be cryptographically signed — the certificate proves update authenticity (Android refuses to install an update whose signature doesn't match the currently-installed app's). Play App Signing splits this into two keys:

  • Upload key: yours, used only to sign the AAB you upload to Play Console — if leaked, Google lets you revoke and rotate it.
  • App signing key: held securely by Google, used to actually sign the APKs Play generates and delivers to users. Google re-signs your uploaded bundle with this key after verifying your upload key's signature.

This separation means a leaked upload key is recoverable (rotate it), whereas historically a leaked signing key was catastrophic (you could never publish a trusted update to existing installs again).

// build.gradle — separate signing config per build type
signingConfigs {
    create("release") {
        storeFile = file("upload-keystore.jks")
        storePassword = System.getenv("KEYSTORE_PASSWORD")
        keyAlias = "upload"
        keyPassword = System.getenv("KEY_PASSWORD")
    }
}
buildTypes { release { signingConfig = signingConfigs.getByName("release") } }
💡 Never commit keystore files or passwords to source control — pull them from environment variables or a secrets manager in CI.

App Startup & Performance Diagnostics

Q38Explain cold, warm, and hot app starts, and what the App Startup library optimizesMedium

Not every app launch is equally expensive, and knowing which kind of start you're optimizing for is the first thing a performance-focused interviewer wants to hear, because the fix looks completely different depending on which one is slow. The three types differ in exactly how much the system has to rebuild from scratch: whether a fresh process needs to be created, whether the Activity needs to be recreated, or whether everything is already sitting in memory and just needs to come back to the foreground. Google explicitly measures and reports cold start time as a key vital in Play Console because it's the worst first impression a slow app can make, and it's the one type of start where your Application.onCreate() and any eager initialization work sit squarely on the critical path.

Cold start: the OS process doesn't exist — full chain of process fork, ART class loading, Application object + attachBaseContext + all manifest ContentProviders + Application.onCreate(), THEN the launching Activity's onCreate/onStart/onResume and first frame draw. Warm start: process is still alive (e.g. user backgrounded and returned, or the Activity was destroyed by the system but process survived) — Application init is skipped, but the Activity still needs full onCreate. Hot start: both process and Activity instance are still resident — just bringing it back to the foreground (onRestart→onStart→onResume), no inflation needed.

App Startup library (androidx.startup) replaces the old pattern of every library declaring its own manifest ContentProvider purely to get an early, guaranteed init call. Each ContentProvider adds fixed per-process overhead (its own onCreate() call, binder registration) — App Startup collapses ALL of them into a single ContentProvider that runs a dependency-ordered graph of your Initializers, cutting cold-start cost when you have several libraries that each used to bootstrap this way.

class LoggerInitializer : Initializer<Logger> {
    override fun create(context: Context): Logger = Logger.init(context)
    override fun dependencies(): List<Class<out Initializer<*>>> = emptyList()
}
Q39What does the Android 12+ SplashScreen API provide that a custom splash Activity didn't?Easy

Before API 31, "splash screens" were a hack: a themed launcher Activity showing a static drawable as its window background, then transitioning to the real Activity — fragile, and every app reinvented it slightly differently. The SplashScreen API (native on API 31+, backported to API 21+ via androidx.core.splashscreen) makes it a real system feature: the OS itself draws a splash (app icon/branding + background color) immediately from the app's theme while your process is still cold-starting, then automatically hands off to your first frame — no extra Activity, no manual transition code.

<!-- themes.xml -->
<style name="Theme.App.Starting" parent="Theme.SplashScreen">
    <item name="windowSplashScreenBackground">@color/brand</item>
    <item name="windowSplashScreenAnimatedIcon">@drawable/ic_splash</item>
    <item name="postSplashScreenTheme">@style/Theme.App</item>
</style>
override fun onCreate(savedInstanceState: Bundle?) {
    val splashScreen = installSplashScreen() // must be called before super.onCreate()
    super.onCreate(savedInstanceState)
    splashScreen.setKeepOnScreenCondition { viewModel.isLoading } // hold splash until data ready
}
Q40What exactly triggers an ANR — walk through the different timeout types — and how do you diagnose one from a trace?Hard

ANR (Application Not Responding) isn't one single timeout — the system watches several distinct conditions on the main thread, each with its own budget:

  • Input dispatch timeout (5s): the most common — main thread hasn't responded to a key or touch event in time.
  • Broadcast timeout (10s foreground / 60s background): a BroadcastReceiver's onReceive() took too long — remember onReceive() itself must be fast; spin off real work to WorkManager/a service instead.
  • Service timeout (~20s foreground / ~200s background): onCreate()/onStartCommand()/onBind() blocking the main thread too long.
  • ContentProvider publish timeout: a provider's own onCreate() hanging during the app's startup phase.

Diagnosing: when an ANR fires, the system dumps a trace to /data/anr/traces.txt (or via adb shell dumpsys activity processes) containing the stack of EVERY thread at that instant — the main thread's stack shows exactly which call was blocking (waiting on a lock, doing I/O, in an infinite loop). Android Vitals in Play Console aggregates ANR rate across your real user base and lets you download traces for the worst offenders; StrictMode and Perfetto/systrace traces help catch the underlying blocking call in development before it ever reaches production.

⚠ A deadlock (main thread blocked waiting on a lock held by a background thread) shows up in the trace as the main thread "waiting to lock" a monitor owned by another named thread — always check the OTHER thread's stack too, not just the main thread's.
Q41What does StrictMode catch, and how do you enable it?Easy

StrictMode is a developer tool (never enable its penalties in production release builds) that detects accidental violations of good practice at runtime, split into two policies:

  • ThreadPolicy: catches disk reads/writes, network calls, and custom slow calls made on the main thread — the exact class of bug that causes janky UI and ANRs.
  • VmPolicy: catches leaked Closeable objects (e.g. an unclosed Cursor/Stream finalized by the GC), leaked SQLite objects, leaked registration objects (an unregistered BroadcastReceiver/ServiceConnection), and non-SDK (hidden API) usage.
override fun onCreate() {
    super.onCreate()
    if (BuildConfig.DEBUG) {
        StrictMode.setThreadPolicy(
            StrictMode.ThreadPolicy.Builder()
                .detectDiskReads().detectDiskWrites().detectNetwork()
                .penaltyLog() // logs to Logcat — use penaltyDeath() to crash immediately and force a fix
                .build()
        )
        StrictMode.setVmPolicy(
            StrictMode.VmPolicy.Builder().detectLeakedClosableObjects().penaltyLog().build()
        )
    }
}
💡 penaltyDeath() during development is a great forcing function — it turns a silent main-thread disk read into an immediate crash you can't ignore, instead of a subtle jank you'd only spot in profiling.

Views, Windows & Input

Q42Why does edge-to-edge matter and how do you handle WindowInsets correctly?Medium

"Edge-to-edge" means your app's content draws behind the system status bar and navigation bar rather than being letterboxed above/below them — Android has pushed this direction for years, and starting with apps targeting API 35 (Android 15) it's enforced: you can no longer opt out via the old android:windowFullscreen/android:fitsSystemWindows tricks. If you don't handle insets yourself, your toolbar, FAB, and bottom navigation end up drawn UNDER the status/nav bars, unreadable or unclickable.

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    WindowCompat.setDecorFitsSystemWindows(window, false) // opt into drawing behind system bars
    setContentView(R.layout.activity_main)

    ViewCompat.setOnApplyWindowInsetsListener(toolbar) { view, insets ->
        val bars = insets.getInsets(WindowInsetsCompat.Type.systemBars())
        view.updatePadding(top = bars.top) // push toolbar below the status bar
        insets // return so children can also consume remaining insets
    }
}
✓ Rule of thumb: apply top inset padding to your topmost app-bar-like view, bottom inset padding to your bottom bar/FAB container, and let the actual scrolling content ignore insets (or use them for extra scroll padding) so it can still scroll edge-to-edge visually.
Q43Walk through Android's touch event dispatch chain — dispatchTouchEvent, onInterceptTouchEvent, onTouchEventHard

Every touch event in Android has to travel down through a tree of nested Views before anything actually responds to it, and the system gives each ViewGroup along the way a chance to grab the gesture for itself before letting a child handle it. This dispatch-then-intercept pattern is what makes it possible for a ViewGroup like a ViewPager or a swipeable RecyclerView to "steal" a gesture from a child View, and it's also the direct cause of one of the most common real-world bugs: nested scrollable views fighting over the same drag gesture. Interviewers ask this to see if you can reason about that conflict concretely — not just recite the method names, but explain why a horizontal swiper living inside a vertical scroller needs requestDisallowInterceptTouchEvent to work correctly.

Touch dispatch flows down the view tree and can be intercepted on the way: Activity.dispatchTouchEvent() hands the event to the root ViewGroup, which first asks its own onInterceptTouchEvent() whether IT wants to steal the gesture (returning true means the ViewGroup handles it itself via its own onTouchEvent() and the child never sees it); returning false forwards the event down to the appropriate child, which repeats the same dispatch/intercept/handle process if it's also a ViewGroup, eventually reaching a leaf View's onTouchEvent().

Critical rule: whichever view/ViewGroup consumes ACTION_DOWN becomes the target for the REST of that gesture (MOVE, UP) — intercept decisions for MOVE events are re-evaluated each time unless the child calls requestDisallowInterceptTouchEvent(true) to explicitly veto further interception (the classic fix for a horizontal ViewPager nested inside a vertically-scrolling parent, where both want to claim the same drag).

// Inside a horizontally-scrolling child living inside a vertical ScrollView
override fun onTouchEvent(event: MotionEvent): Boolean {
    when (event.action) {
        MotionEvent.ACTION_DOWN -> parent.requestDisallowInterceptTouchEvent(true)
        MotionEvent.ACTION_UP -> parent.requestDisallowInterceptTouchEvent(false)
    }
    return super.onTouchEvent(event)
}
Q44Explain the RecyclerView ViewHolder pattern — why is onBindViewHolder cheap but onCreateViewHolder expensive?Medium

onCreateViewHolder() inflates a brand new item layout (XML parsing + View object graph construction) — genuinely expensive — but RecyclerView only calls it enough times to fill the screen plus a small buffer; once enough ViewHolders of a given view type exist, scrolled-off holders are recycled into a pool and reused instead of re-inflated. onBindViewHolder() just pushes new data into an already-inflated holder's views (setText, setImageResource...) — cheap, called on every scroll as items recycle.

class ItemAdapter(private val items: List<Item>) : RecyclerView.Adapter<ItemAdapter.VH>() {
    class VH(val binding: ItemRowBinding) : RecyclerView.ViewHolder(binding.root)

    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): VH {
        val binding = ItemRowBinding.inflate(LayoutInflater.from(parent.context), parent, false)
        return VH(binding) // expensive — called only when the recycled pool has nothing to reuse
    }
    override fun onBindViewHolder(holder: VH, position: Int) {
        holder.binding.title.text = items[position].name // cheap — called on every scroll
    }
}

RecycledViewPool can be shared across multiple RecyclerViews (e.g. a horizontal RecyclerView nested inside each item of a vertical one) via setRecycledViewPool(), so identical inner-item view types are reused across all the outer rows instead of each maintaining its own pool. For updates, use DiffUtil (or ListAdapter) to compute a minimal set of insert/remove/change operations instead of calling notifyDataSetChanged(), which forces a full unnecessary rebind of every visible row and loses animations.

Q45What's the difference between invalidate(), requestLayout(), and postInvalidate()?Medium

These three methods all trigger some form of view refresh, but they operate at very different levels of the rendering pipeline, and reaching for the expensive one when the cheap one would do is a real performance smell interviewers watch for. invalidate() only asks the system to redraw what's already been measured and laid out — the right call when a view's appearance changed but its size and position didn't. requestLayout() is much heavier: it asks the system to re-measure and re-position the view, and potentially its parent and siblings too, which is only necessary when the view's dimensions themselves need to change. postInvalidate() exists purely to solve a threading problem — plain invalidate() must be called from the main thread, so postInvalidate() gives you a safe way to request a redraw from a background thread without touching the UI thread directly.

  • invalidate(): schedules only a redraw (onDraw()) — use when a view's appearance changed but its size/position didn't (e.g. a background color or a custom-drawn progress value). Cheapest of the three.
  • requestLayout(): schedules a full measure + layout pass (then draw) — use when the view's size or position needs to be recalculated (e.g. text content changed enough to need a different width). More expensive: it can cascade up to the parent and affect sibling layout.
  • postInvalidate(): the thread-safe version of invalidate(), callable from a background thread — internally posts the invalidation request onto the main thread's Handler/Looper so it's safe even though you're not on the UI thread (calling plain invalidate() off the main thread throws).
class ProgressView(context: Context) : View(context) {
    var progress = 0f
        set(value) { field = value; invalidate() } // same size, just redraw

    fun updateFromBackgroundThread(newProgress: Float) {
        progress = newProgress
        postInvalidate() // safe to call off the main thread
    }
}
💡 Calling requestLayout() when invalidate() would suffice is a common perf smell — it forces the whole view hierarchy to re-measure when only a repaint was needed.

WorkManager Fundamentals

Q46What's the difference between OneTimeWorkRequest and PeriodicWorkRequest, and how do constraints behave?Easy

OneTimeWorkRequest runs a single deferrable task once. PeriodicWorkRequest repeats on an interval — but the system enforces a minimum interval of 15 minutes (and the actual run time can drift within a flex window) specifically to protect battery life; you cannot schedule tighter recurring background work through WorkManager.

val constraints = Constraints.Builder()
    .setRequiredNetworkType(NetworkType.CONNECTED)
    .setRequiresCharging(true)
    .setRequiresBatteryNotLow(true)
    .build()

val syncOnce = OneTimeWorkRequestBuilder<SyncWorker>()
    .setConstraints(constraints)
    .build()

val syncPeriodic = PeriodicWorkRequestBuilder<SyncWorker>(15, TimeUnit.MINUTES)
    .setConstraints(constraints)
    .build()

Constraints are continuously monitored, not just checked at enqueue time — if a running worker's required constraint stops being satisfied mid-execution (e.g. network drops for a network-required job), the system stops it and reschedules it for when the constraint is satisfied again.

Q47How do you chain WorkManager tasks and prevent duplicate scheduling of the same periodic work?Medium

Chaining: beginWith().then().enqueue() builds a dependency graph — each worker's output Data becomes an input to the next, and downstream workers only run after upstream ones succeed (a Result.failure() anywhere cancels the rest of that chain).

WorkManager.getInstance(context)
    .beginWith(compressRequest)
    .then(uploadRequest)
    .then(notifyRequest)
    .enqueue()

// inside CompressWorker
override fun doWork(): Result {
    val path = compressFile()
    return Result.success(workDataOf("path" to path)) // feeds into UploadWorker's input
}

Unique work policies stop you from accidentally scheduling the same logical job twice (e.g. re-enqueuing a sync on every app launch):

  • KEEP: if work with this name is already pending/running, ignore the new request entirely.
  • REPLACE: cancel the existing one and enqueue the new definition.
  • APPEND: chain the new request after the existing one finishes.
  • APPEND_OR_REPLACE: like APPEND, but doesn't fail the whole chain if a prior link in it failed.
WorkManager.getInstance(context).enqueueUniquePeriodicWork(
    "daily-sync", ExistingPeriodicWorkPolicy.KEEP, syncPeriodic
)

Failure handling uses setBackoffCriteria() (LINEAR or EXPONENTIAL) so retries don't hammer a struggling backend or dead network immediately.

Q48How does WorkManager guarantee execution even across process death and device reboot — what runs underneath it?Hard

The promise WorkManager makes — "this work will run eventually, even across process death or a reboot" — sounds like magic unless you understand it's built by layering a persistence guarantee underneath a scheduling API, not by WorkManager itself doing anything while your process is dead. Interviewers ask this specifically to see if you understand WorkManager is really a coordination layer on top of existing OS primitives, JobScheduler or AlarmManager, plus a database, rather than some entirely new execution mechanism — that's the insight that explains both why it's so reliable and why it still can't run more often than the OS scheduler allows.

WorkManager is a persistence + scheduling layer, not the execution engine itself. Every request you enqueue is written as a WorkSpec row into an internal Room database — this is the key to durability: the work definition survives your app process dying, because it's on disk, not just in memory.

The actual OS-level trigger delegates to whatever's available on the device: JobScheduler on API 23+ (native constraint-aware background job scheduling), or a combination of AlarmManager + a BroadcastReceiver on API 14-22 where JobScheduler doesn't exist. When the trigger fires, WorkManager's own component wakes up, reads the pending WorkSpecs back out of Room, and executes them.

Surviving reboot: WorkManager registers a BOOT_COMPLETED receiver itself (declared in its own manifest, merged into yours) so that on next boot it re-reads Room and re-schedules everything whose constraints still need to be met — you don't need to write any boot-handling code yourself, just make sure you haven't stripped that permission via manifest merging.

✓ Interview takeaway: WorkManager's durability guarantee comes specifically from persisting to Room before scheduling — it's the same reason it can safely promise "this will run eventually" even through a process kill, unlike a plain in-memory Handler.postDelayed() or coroutine job.

Home Screen Integration: Widgets & Shortcuts

Q49What are the three types of App Shortcuts and how do they differ?Easy

App Shortcuts give users a fast path into specific actions or content in your app straight from the launcher, without having to open the app and navigate there manually, and the three types exist because they trade off flexibility against how much control you retain over them. Static shortcuts are the simplest — fixed at build time in XML — good for actions that never change, like composing a new message. Dynamic shortcuts are your escape hatch for anything that needs to reflect live app state, like recent contacts or recently viewed items, but the system caps how many you can have at once. Pinned shortcuts are different in kind rather than degree: once the user drags one onto their home screen it becomes independent of your app's shortcut list entirely, which is why interviewers like this question — it tests whether you understand shortcuts have a lifecycle partly outside your control once the user pins one.

  • Static shortcuts: declared entirely in an XML resource, fixed at build time (e.g. "Compose new email"). Shown on long-press of the launcher icon. Can't change at runtime beyond enabling/disabling.
  • Dynamic shortcuts: published/updated at runtime via ShortcutManager, so they can be context-sensitive (e.g. "Message [most recent contact]"). Limited to a device-defined max count (typically 4-5, check getMaxShortcutCountPerActivity()).
  • Pinned shortcuts: the user explicitly drags a shortcut onto the home screen. Once pinned, it persists as its own launcher icon independently — even if you later remove it from your dynamic shortcut list, the pinned copy stays until the user removes it (though you can still update its icon/label via updateShortcuts()).

    <shortcut android:shortcutId="compose" android:icon="@drawable/ic_compose"
        android:shortcutShortLabel="@string/compose_short">
        <intent android:action="android.intent.action.VIEW"
            android:targetPackage="com.example.app"
            android:targetClass="com.example.app.ComposeActivity"/>
    </shortcut>
</shortcuts>
// dynamic shortcut — published/updated at runtime

    .build()

Q50How do AppWidgets work under the hood — what is AppWidgetProvider and why is RemoteViews needed?Medium

An AppWidget's UI is drawn by the launcher/home-screen process, not your app's process — your app never gets direct access to widget Views, since they live across a process boundary. That's what RemoteViews solves: it's a serializable description of a view hierarchy (limited to a whitelisted subset of layouts/views: FrameLayout, LinearLayout, RelativeLayout, GridLayout, TextView, ImageView, Button, ProgressBar, etc. — no custom Views) that can be parceled across processes and inflated remotely by the host.

AppWidgetProvider is just a thin BroadcastReceiver subclass that the system calls with lifecycle-like broadcasts: onUpdate() (periodically, per android:updatePeriodMillis in the widget's metadata XML — minimum effectively ~30 minutes, you cannot refresh a widget faster than that through this mechanism), onAppWidgetOptionsChanged() (widget resized), onDeleted(), onEnabled()/onDisabled() (first instance added / last removed).

class MyWidgetProvider : AppWidgetProvider() {
    override fun onUpdate(context: Context, manager: AppWidgetManager, ids: IntArray) {
        for (id in ids) {
            val views = RemoteViews(context.packageName, R.layout.widget_layout).apply {
                setTextViewText(R.id.widget_title, "Updated!")
            }
            manager.updateAppWidget(id, views) // pushes the new RemoteViews to the host process
        }
    }
}

For refresh rates faster than the ~30-minute floor (e.g. a live score widget), schedule your own WorkManager periodic job (still subject to its own 15-minute floor, so combine with push-triggered updates via FCM for true near-real-time refresh) that calls updateAppWidget() directly instead of relying on onUpdate() alone.

💡 Modern alternative: Jetpack Glance lets you describe widget UI declaratively (Compose-like syntax) while still compiling down to RemoteViews under the hood — the RemoteViews process-boundary constraint doesn't go away, Glance just hides the imperative builder code.
