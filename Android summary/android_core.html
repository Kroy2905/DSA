📱 Android Core — Interview Questions

Activity, Fragment, Intents, Services, Context, Lifecycle, Threading — the foundation every Android interviewer will probe deeply.

Activity & Lifecycle

Q1Explain the complete Activity lifecycle and when each callback is calledHard

Complete lifecycle:

// onCreate → onStart → onResume → [RUNNING]
// [RUNNING] → onPause → onStop → onDestroy

class MainActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        // Called once. Initialize UI, set content view, restore state
        // Activity not visible yet
    }
    override fun onStart() {
        // Activity becoming visible but not interactive yet
    }
    override fun onResume() {
        // Activity in foreground, interactive. Register sensors, animations
    }
    override fun onPause() {
        // Partially visible (another activity on top). Release sensors/camera
        // MUST be fast — other activity waits for this to complete
    }
    override fun onStop() {
        // Fully hidden. Release heavy resources, save data
    }
    override fun onDestroy() {
        // Activity being destroyed. Check isFinishing() to know if user exited
    }
    override fun onRestart() {
        // Called before onStart() when coming back from STOPPED state
    }
}

Key interview scenarios:

  • Rotation: onPause → onStop → onDestroy → onCreate → onStart → onResume. Use ViewModel to survive!
  • Home button: onPause → onStop (activity still alive in memory)
  • Back button: onPause → onStop → onDestroy (activity finished)
  • Another activity on top: A.onPause → B.onCreate → B.onStart → B.onResume → A.onStop
  • Coming back from B to A: B.onPause → A.onRestart → A.onStart → A.onResume → B.onStop → B.onDestroy
✓ Google tip: onPause must be fast. Never do heavy operations here. Do them in onStop.
Q2What is the difference between onSaveInstanceState and ViewModel for state preservation?Hard

onSaveInstanceState (Bundle):

  • Survives: rotation, process death (system kills app while backgrounded)
  • Capacity: small data only (~1MB limit, it's IPC binder transaction)
  • Types: primitives, Parcelable, Serializable
  • When called: before onStop() on API 28+, before onPause() on older

ViewModel:

  • Survives: rotation and configuration changes ONLY
  • Does NOT survive process death — data is gone if system kills the process
  • Capacity: unlimited (holds any object)
  • Best for: complex objects, lists, network results
// Best practice: use BOTH together
class MyViewModel(private val savedStateHandle: SavedStateHandle) : ViewModel() {
    // SavedStateHandle bridges ViewModel + onSaveInstanceState
    // Survives BOTH rotation AND process death
    var searchQuery = savedStateHandle.getStateFlow("query", "")

    fun setQuery(query: String) {
        savedStateHandle["query"] = query // automatically persisted
    }
}
💡 SavedStateHandle is the modern solution — it gives you ViewModel + process death survival.
Q3Explain Fragment lifecycle and how it differs from Activity lifecycleMedium 
// Fragment has ADDITIONAL callbacks vs Activity:
onAttach()        // Fragment attached to host Activity
onCreate()        // Fragment created (no view yet)
onCreateView()    // Inflate layout, return view
onViewCreated()   // View ready, set up UI here (not onCreateView!)
onStart()
onResume()
onPause()
onStop()
onDestroyView()   // View destroyed but Fragment still alive (backstack)
onDestroy()
onDetach()        // Fragment detached from Activity

Critical difference — onDestroyView: When a Fragment goes to the back stack, only its view is destroyed (onDestroyView), NOT the Fragment itself. The Fragment object stays alive. This is why you must use viewLifecycleOwner (not just lifecycleOwner) when observing LiveData in Fragments — to avoid memory leaks.

// WRONG - leaks if fragment goes to backstack
viewModel.data.observe(this) { ... }

// CORRECT - tied to view lifecycle
viewModel.data.observe(viewLifecycleOwner) { ... }
⚠ This is one of the most common memory leak questions. Always use viewLifecycleOwner in Fragments.
Q4What are the different types of Context and when do you use each?Hard

Types:

  • Application Context: Tied to application lifecycle. Use for: creating Singletons, accessing resources, starting Services, registering broadcast receivers when you want them alive as long as the app is alive.
  • Activity Context: Tied to Activity lifecycle. Use for: showing Dialogs, starting Activities (preserves task stack), inflating layouts (gets correct theme), loading theme-dependent resources.
  • Service Context: Tied to Service lifecycle.
// Application Context — for long-lived objects
class ImageLoader(private val context: Context) {
    init {
        // Use applicationContext to avoid leaking Activity
        val appContext = context.applicationContext
    }
}

// Dialog NEEDS Activity context
AlertDialog.Builder(this) // 'this' = Activity ✓
AlertDialog.Builder(applicationContext) // CRASH! ✗
⚠ Memory leak pattern: storing Activity context in a Singleton or static field. Always use application context for Singletons.

Intents & Components

Q5What is the difference between explicit and implicit intents? What is Intent resolution?Medium 
// Explicit — specifies exact component class
val intent = Intent(this, DetailActivity::class.java)
intent.putExtra("id", userId)
startActivity(intent)

// Implicit — declares action, system resolves which app handles it
val intent = Intent(Intent.ACTION_VIEW).apply {
    data = Uri.parse("https://google.com")
}
if (intent.resolveActivity(packageManager) != null) {
    startActivity(intent) // Opens browser
}

Intent resolution: Android's PackageManager matches implicit intents against all apps' AndroidManifest intent-filter declarations, comparing: action, category, and data (URI/MIME type). If multiple apps match, user sees a chooser.

PendingIntent: A token given to another process to start your Activity/Service/Broadcast on your behalf (e.g. notifications). Always specify mutability flag in API 31+.

// PendingIntent for notification
val pendingIntent = PendingIntent.getActivity(
    context, 0, intent,
    PendingIntent.FLAG_IMMUTABLE // Required API 31+
)
Q6Explain Activity launch modes and how they affect the back stackHard
  • standard (default): New instance created every time, even if already on stack. Stack: A→B→B→B possible.
  • singleTop: If target is at the TOP of stack, reuses it (calls onNewIntent()). If not on top, creates new. Good for: notifications that launch an activity already open.
  • singleTask: Only ONE instance in the entire task. If exists, all activities on top of it are POPPED and onNewIntent() called. Creates a new task if needed. Good for: deep links, main activity.
  • singleInstance: Like singleTask but the activity lives in its OWN isolated task — no other activities can be added to its task.
// Set via manifest:
<activity android:name=".MainActivity"
    android:launchMode="singleTask"/>

// Or via Intent flags (overrides manifest):
intent.addFlags(Intent.FLAG_ACTIVITY_SINGLE_TOP)
intent.addFlags(Intent.FLAG_ACTIVITY_CLEAR_TOP) // like singleTask
intent.addFlags(Intent.FLAG_ACTIVITY_NEW_TASK) // start in new task
💡 Intent flags take precedence over manifest launchMode. FLAG_ACTIVITY_CLEAR_TOP + FLAG_ACTIVITY_SINGLE_TOP together = singleTask behavior.

Services & Background Work

Q7What are the different types of Services and when would you use each?Hard
  • Started Service: Runs indefinitely after startService(). Must call stopSelf() or stopService(). Risk of being killed by OS under memory pressure.
  • Bound Service: Clients bind to it via bindService(). Lives as long as there are bound clients. Returns an IBinder interface. Good for: IPC, two-way communication.
  • Foreground Service: Requires a visible notification. Cannot be killed by OS. Mandatory for user-aware long tasks (music playback, navigation, file download).
  • IntentService (deprecated): Was a started service that ran on a background thread and stopped itself. Replaced by WorkManager or coroutines + Service.
// Foreground Service (API 26+)
class MusicService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val notification = buildNotification()
        startForeground(NOTIF_ID, notification) // Must call within 5s
        return START_STICKY // Restart if killed
    }
}

// WorkManager is preferred for deferrable background work
val request = OneTimeWorkRequestBuilder<SyncWorker>()
    .setConstraints(Constraints(requiresNetwork = true))
    .build()
WorkManager.getInstance(context).enqueue(request)
✓ Modern recommendation: Use WorkManager for deferrable work, Foreground Service for user-aware work, coroutines for in-scope async operations.

Threading & Concurrency

Q8What is the main thread, why can't you do network/disk I/O on it, and what is ANR?Medium

The main thread (UI thread) is responsible for drawing UI frames. Android tries to render at 60fps, giving you ~16ms per frame. If any operation blocks the main thread:

  • UI becomes unresponsive
  • If blocked for >5 seconds (user input) or >10 seconds (broadcast): ANR dialog appears

Common ANR causes: Network call on main thread, slow database query, large bitmap decode, holding a lock that another thread owns, long computation.

// WRONG — Network on main thread (throws NetworkOnMainThreadException)
val data = apiService.fetchData() // in Activity.onCreate()

// CORRECT — Use coroutines with IO dispatcher
class MyViewModel : ViewModel() {
    fun loadData() {
        viewModelScope.launch {
            val data = withContext(Dispatchers.IO) {
                apiService.fetchData() // off main thread
            }
            _uiState.update { it.copy(data = data) } // back on main thread
        }
    }
}
Q9Explain Handler, Looper, and MessageQueue — how does Android's message system work?Hard

This is the foundation of Android's threading model (predates coroutines):

  • Looper: Attached to a thread. Runs an infinite loop reading from MessageQueue. The main thread has a Looper by default (Looper.getMainLooper()).
  • MessageQueue: Ordered queue of Messages and Runnables for a specific Looper/thread.
  • Handler: Sends messages/runnables to a specific MessageQueue. When you create Handler(Looper.getMainLooper()), any post() call dispatches to the main thread.
// HandlerThread — creates a thread with a Looper
val handlerThread = HandlerThread("BackgroundThread").apply { start() }
val bgHandler = Handler(handlerThread.looper)
val mainHandler = Handler(Looper.getMainLooper())

bgHandler.post {
    val result = doHeavyWork() // background thread
    mainHandler.post { updateUI(result) } // switch to main
}

// Modern equivalent with coroutines:
viewModelScope.launch(Dispatchers.IO) {
    val result = doHeavyWork()
    withContext(Dispatchers.Main) { updateUI(result) }
}
💡 Coroutines abstract away Handler/Looper complexity, but understanding the underlying model helps debug threading issues.
Q10What are common memory leak patterns in Android and how do you detect them?Hard

Common leak patterns:

  • Static reference to Activity/View: Static companion objects holding Context or View
  • Non-static inner class: AsyncTask, Handler inner class implicitly holds outer Activity reference
  • Fragment viewLifecycleOwner: Observing LiveData with this instead of viewLifecycleOwner
  • Unregistered listeners: Registering BroadcastReceiver, SensorManager, LocationManager but not unregistering
  • Bitmap held in static: Large bitmaps held by static fields
  • RxJava/Flow subscriptions: Not disposing/cancelling subscriptions on destroy
// LEAK: static handler holds Activity reference
class MainActivity : Activity() {
    private val handler = object : Handler(Looper.getMainLooper()) {
        override fun handleMessage(msg: Message) {
            // Implicit reference to MainActivity — leaks if delayed message pending
        }
    }
    override fun onDestroy() {
        handler.removeCallbacksAndMessages(null) // Fix: remove pending messages
        super.onDestroy()
    }
}

Detection:

  • LeakCanary: Add to debugImplementation, it automatically detects and reports leaks
  • Android Profiler: Memory tab → take heap dump → look for Activity/Fragment instances that shouldn't exist
  • StrictMode: Enables strict VM/thread policies in debug builds

BroadcastReceiver & ContentProvider

Q11What is a BroadcastReceiver? Static vs dynamic registration?Medium
  • Static (manifest): System can launch app to deliver broadcast even if app not running. Severely restricted since API 26 — only certain system broadcasts allowed (BOOT_COMPLETED, etc.).
  • Dynamic (code): Registered while app is running. Must unregister to avoid leaks.
// Dynamic registration — register in onStart, unregister in onStop
private val receiver = object : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        when (intent.action) {
            Intent.ACTION_BATTERY_LOW -> handleLowBattery()
        }
    }
}

override fun onStart() {
    super.onStart()
    val filter = IntentFilter(Intent.ACTION_BATTERY_LOW)
    registerReceiver(receiver, filter)
}
override fun onStop() {
    unregisterReceiver(receiver) // ALWAYS unregister
    super.onStop()
}
💡 Ordered broadcasts: receivers process in order of priority. A receiver can abort the chain with abortBroadcast().
Q12When would you use a ContentProvider and how does it work?Medium

ContentProvider exposes structured data via a URI scheme, allowing cross-process data sharing with access control.

Use cases: Contacts, Calendar, MediaStore, sharing data between apps, providing data to system (SearchSuggestions).

// URI pattern: content://authority/path/id
val uri = Uri.parse("content://com.example.provider/users/42")

// Querying (runs on binder thread pool — NOT main thread)
val cursor = contentResolver.query(uri, null, null, null, null)
cursor?.use {
    while (it.moveToNext()) {
        val name = it.getString(it.getColumnIndexOrThrow("name"))
    }
}

// FileProvider — secure file sharing between apps
val fileUri = FileProvider.getUriForFile(
    context, "com.example.fileprovider", file
