🏗 Mobile System Design — Interview

Google expects you to design complete mobile systems. Use this framework for every question. Practice these 6 designs until you can do each in 45 minutes.

The Framework

★Framework for ANY mobile system design questionMust Know

Mobile system design questions are deliberately open-ended — "design Instagram's feed" has no single right answer, and candidates who don't bring their own structure either freeze up or ramble through implementation details without ever stating what they're building or why. Having a fixed, rehearsed sequence of steps solves that: it forces you to nail down requirements before you start solving anything, it moves top-down from architecture to specifics so the interviewer can follow your reasoning, and it guarantees you reach offline behavior and edge cases instead of running out of time deep in one layer. It also mirrors how a senior engineer actually approaches ambiguous work — clarify scope, sketch the shape of the system, then drill into the parts that matter most — which is exactly the signal the interviewer is grading for.

  1. Clarify requirements (5 min): Functional (what features?), Non-functional (scale, offline, latency), Platform (Android only? iOS too?)
  2. High-level architecture (5 min): Layers — Presentation, Domain, Data. Draw the box diagram.
  3. Data models (5 min): What entities? What does the local DB store? What does the API return?
  4. API design (5 min): What endpoints does the app call? Request/response shapes.
  5. Key screens + navigation (5 min): Main screens, navigation graph, what's cached.
  6. Networking strategy (10 min): Pagination, caching strategy, offline behavior, sync.
  7. Performance + optimization (5 min): Image loading, lazy loading, prefetching, memory.
  8. Edge cases (5 min): No network, partial data, large lists, expired cache.

The box diagram (step 2): a clean layered box diagram is what separates a senior answer from a junior one — draw dependencies flowing one way (top → bottom) and data flowing back up through observable streams (Flow/StateFlow).

Design: Instagram Feed

D1Design Instagram-style infinite scroll feed for AndroidHard

An infinite-scroll feed is really three problems stacked on top of each other: cursor-based pagination that fetches posts in pages without the client hand-rolling offset math, a local cache that stays in sync with the network so the feed still shows something useful the moment the app opens offline, and an image pipeline that has to keep loading and recycling bitmaps without ever dropping below 60fps while the user flings through the list. The interviewer is really checking whether you reach for the Paging library instead of writing your own pagination state machine, whether you make Room the single source of truth so the UI never blocks on a network call, and whether you can talk concretely about memory pressure and cancellation once dozens of images are streaming in and out of view.

Requirements: Infinite scroll, images, likes/comments, offline support, smooth 60fps scroll

Architecture:

// Data model
@Entity
data class Post(
    @PrimaryKey val id: String,
    val userId: String,
    val imageUrl: String,
    val caption: String,
    val likesCount: Int,
    val createdAt: Long,
    val page: Int  // for invalidation
)

// Paging 3 — handles pagination, loading states, errors
class FeedPagingSource(
    private val api: FeedApi
) : PagingSource<String, Post>() { // key=cursor, value=Post
    override suspend fun load(params: LoadParams<String>): LoadResult<String, Post> {
        return try {
            val response = api.getFeed(cursor = params.key, limit = params.loadSize)
            LoadResult.Page(
                data = response.posts,
                prevKey = null,           // no back-paging in feed
                nextKey = response.nextCursor
            )
        } catch (e: Exception) { LoadResult.Error(e) }
    }
}

// RemoteMediator for offline-first (network + Room)
@OptIn(ExperimentalPagingApi::class)
class FeedRemoteMediator(
    private val api: FeedApi,
    private val db: AppDatabase
) : RemoteMediator<Int, Post>() {
    override suspend fun load(loadType: LoadType, state: PagingState<Int, Post>): MediatorResult {
        val posts = api.getFeed(/* ... */)
        db.withTransaction {
            if (loadType == LoadType.REFRESH) db.postDao().clearAll()
            db.postDao().insertAll(posts)
        }
        return MediatorResult.Success(endOfPaginationReached = posts.isEmpty())
    }
}

Image loading strategy:

  • Use Coil: memory cache (LRU, ~25% heap) + disk cache + placeholder + crossfade
  • Pre-fetch next 3 images while user scrolls using CoilPrefetcher
  • Different quality for scroll vs stopped (low-res thumbnail → full res)
  • Cancel image loads for off-screen items via ImageRequest lifecycle

Performance optimizations:

  • DiffUtil with stable IDs — only rebind changed items
  • RecycledViewPool shared across multiple RecyclerViews
  • ViewHolder caching: setRecycledViewPool, setItemViewCacheSize
  • Avoid nested RecyclerViews — use ConcatAdapter instead

Design: Chat Application

D2Design a WhatsApp-style chat appHard

A chat app is fundamentally a state-sync problem wearing a UI: every message a user sends has to appear in their own screen instantly, survive them going offline mid-send, get delivered to the other device exactly once, and settle into an order both sides agree on even though the network can deliver things late or out of order. The interviewer wants to see you cleanly separate "what the UI is showing right now" from "what the server has actually confirmed" — using a local Room row with an explicit status field (PENDING → SENT → DELIVERED → READ) as the source of truth the UI observes — and pick the right transport for each job rather than defaulting to polling: a persistent WebSocket for messages while the app is open, FCM to wake a killed app when one arrives.

Key challenges: Real-time messages, delivery receipts, offline queue, message ordering

// Message data model
@Entity
data class Message(
    @PrimaryKey val id: String,
    val chatId: String,
    val senderId: String,
    val content: String,
    val type: MessageType, // TEXT, IMAGE, AUDIO
    val status: MessageStatus, // PENDING, SENT, DELIVERED, READ
    val timestamp: Long,
    val localId: String // client-generated before server confirms
)

// Optimistic UI: show message as PENDING immediately, update on server ACK
fun sendMessage(text: String) {
    val localMessage = Message(localId = UUID.randomUUID(), status = PENDING)
    db.messageDao().insert(localMessage) // show immediately in UI
    viewModelScope.launch(Dispatchers.IO) {
        try {
            val serverMsg = api.sendMessage(text)
            db.messageDao().update(serverMsg.copy(status = SENT))
        } catch (e: Exception) {
            db.messageDao().update(localMessage.copy(status = FAILED))
            outbox.add(localMessage) // retry queue
        }
    }
}

Real-time transport options:

  • WebSocket: Persistent connection, truly real-time. Battery cost.
  • FCM: Google's push — app doesn't need to be open. Use for offline messages.
  • Long polling: Simpler but inefficient. Avoid.
  • SSE: Server-sent events — server to client only. Good for notifications.

Recommended: FCM for wakeup + WebSocket when app is foreground. Foreground Service keeps WebSocket alive while app is in background during active chat.

Message sync: On reconnect, fetch all messages with timestamp > last_received_at. Use Room as single source of truth. UI observes Room, not network directly.

Design: Image Loading Library

D3Design an image loading library (like Coil/Glide) from scratchHard — Google Favorite

An image-loading library exists to answer one question as cheaply as possible: "do I already have this bitmap, and if not, where's the least expensive place to get it from?" That answer is a layered lookup — an in-memory LRU cache for bitmaps you just displayed, a disk cache for bitmaps you've downloaded before but evicted from memory, and the network only as a last resort — where each layer is only touched on a miss from the one above it. On top of that layering you need request deduplication, so that ten ImageViews binding the same URL in a fast-scrolling list don't trigger ten separate downloads, and cancellation, so an ImageView that's already been recycled doesn't keep fetching a bitmap nobody will ever see.

This is a classic Google interview question. They want to see you think in layers.

// Architecture: 3-level cache + request deduplication
class ImageLoader(context: Context) {

    // L1: Memory cache (LRU, ~25% of available heap)
    private val memoryCache = LruCache<String, Bitmap>(
        (Runtime.getRuntime().maxMemory() / 1024 / 4).toInt()
    )

    // L2: Disk cache (DiskLruCache, ~250MB)
    private val diskCache: DiskLruCache = DiskLruCache.open(cacheDir, 1, 1, 250L*1024*1024)

    // L3: Network (OkHttp with HTTP cache headers)
    private val httpClient: OkHttpClient = OkHttpClient.Builder()
        .cache(Cache(cacheDir, 50L * 1024 * 1024))
        .build()

    // Deduplication: if same URL loading, return same Deferred
    private val inFlight = ConcurrentHashMap<String, Deferred<Bitmap>>()

    suspend fun load(url: String): Bitmap {
        // 1. Check memory cache (main thread ok, fast)
        memoryCache.get(url)?.let { return it }

        // 2. Deduplicate in-flight requests
        return inFlight.getOrPut(url) {
            async(Dispatchers.IO) {
                // 3. Check disk cache
                diskCache.get(url)?.let {
                    val bmp = BitmapFactory.decodeStream(it)
                    memoryCache.put(url, bmp); bmp
                } ?:
                // 4. Fetch from network
                fetchFromNetwork(url).also {
                    diskCache.put(url, it); memoryCache.put(url, it)
                }
            }
        }.await().also { inFlight.remove(url) }
    }
}

Additional considerations Google will ask about:

  • Bitmap pool: Reuse existing Bitmap memory with inBitmap option
  • Downsampling: Never decode full-res if target view is 100x100 — use inSampleSize
  • Transformation pipeline: Crop, circle, blur as post-processing steps
  • Placeholder/error: Show while loading, show on error
  • Cancellation: Cancel request when view is recycled or detached
  • GIF/animated images: Separate decode pipeline

Design: Offline-First App

D4Design an offline-first architecture for a news reading appHard

Core idea: the UI never talks to the network directly. It only ever observes Room through a Flow. A separate refresh() call fetches from the network and writes into Room — the existing Flow emits automatically. This means the UI always has something to show (last-known-good data), refresh failures degrade gracefully instead of blanking the screen, and there's only one code path to test.

// Single source of truth: Room is the only source UI observes
// Network → Room → UI. Never Network → UI directly.

class NewsRepository(
    private val api: NewsApi,
    private val dao: NewsDao,
    private val networkMonitor: NetworkMonitor
) {
    // UI observes this Flow — always gets Room data
    fun getArticles(): Flow<List<Article>> = dao.getArticlesFlow()

    // Refresh called separately — fetches from network and stores in Room
    suspend fun refresh() {
        if (!networkMonitor.isOnline) return // fail silently, show cached
        val articles = api.getLatestArticles()
        dao.insertAll(articles)
        dao.deleteOlderThan(System.currentTimeMillis() - 7 * 24 * 60 * 60 * 1000L)
    }
}

// Network status monitoring
class NetworkMonitor(context: Context) {
    val isOnline: StateFlow<Boolean> = callbackFlow {
        val cm = context.getSystemService(ConnectivityManager::class.java)
        val callback = object : NetworkCallback() {
            override fun onAvailable(network: Network) = trySend(true)
            override fun onLost(network: Network) = trySend(false)
        }
        cm.registerDefaultNetworkCallback(callback)
        awaitClose { cm.unregisterNetworkCallback(callback) }
    }.stateIn(scope, SharingStarted.Eagerly, true)
}

Cache invalidation strategies:

  • Time-based: Delete articles older than N days
  • Size-based: Keep only latest N articles
  • Pull-to-refresh: User-initiated refresh
  • WorkManager: Periodic background refresh when on WiFi + charging

Design: Notification System

D5Design a notification system: push + local scheduling + dedupeHard

Requirements: server-driven push (FCM), device-scheduled reminders that must fire even without network, Android O+ channels with grouping/bundling, tapping a notification must deep-link into the right screen with a correct back stack, and no duplicate notification when both a push and a local trigger exist for the same event.

Core idea: the same logical event can reach the notification tray from two independent triggers — a push from the server, or a device-local alarm/worker that doesn't need connectivity. Both paths must be funneled through one eventId-keyed dedupe check before anything is posted, otherwise a flaky network can cause the same reminder to show twice (once locally, once when the delayed push finally arrives).

// Push arrives — dedupe against a locally-fired reminder for the same event
override fun onMessageReceived(msg: RemoteMessage) {
    val eventId = msg.data["eventId"] ?: return
    if (dedupeStore.wasShown(eventId)) return // local alarm already fired it
    dedupeStore.markShown(eventId, ttl = 24.hours)
    showNotification(eventId, msg.data)
}

// Deep link rebuilds the back stack; grouping puts it under one summary
fun showNotification(eventId: String, data: Map<String, String>) {
    val pendingIntent = TaskStackBuilder.create(context)
        .addNextIntentWithParentStack(deepLinkIntent(data["chatId"]))
        .getPendingIntent(eventId.hashCode(), PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE)

    NotificationCompat.Builder(context, "messages")
        .setContentTitle(data["title"]).setContentIntent(pendingIntent)
        .setGroup(data["chatId"]).setAutoCancel(true).build()
        .let { NotificationManagerCompat.from(context).notify(eventId.hashCode(), it) }
}

Grouping / bundling: give every notification in the same thread the same groupKey so the tray bundles them, and post one extra setGroupSummary(true) notification per group — otherwise 10 messages from the same chat spam the tray as 10 separate entries.

De-duplication: key every notification-worthy event with a stable eventId that both server and client agree on. Keep a small "shown" store (Room row or pref set) with a TTL, and check-and-mark it atomically before posting — whichever trigger (push or local) arrives first wins, the other becomes a no-op.

Tradeoffs: AlarmManager.setExactAndAllowWhileIdle gives an exact wall-clock fire time but you own retry/persistence yourself; WorkManager survives reboot and handles constraints (network, charging) but isn't exact-time guaranteed under Doze — use Alarm for "remind me at 9am", WorkManager for "sync roughly daily". Android 13+ also requires the runtime POST_NOTIFICATIONS permission, requested contextually rather than on first launch.

Design: Real-Time Location Sharing

D6Design a live location-sharing feature (Uber / Find My Friends style)Hard

Requirements: one user's live location visible to one or more viewers, a tunable battery-vs-accuracy tradeoff, updates that keep flowing while the app is backgrounded, and low end-to-end latency getting an update from the sharer to the viewer.

Core idea: accuracy and update frequency should scale with how much anyone actually cares right now — tight interval and high accuracy while the sharing screen is on-screen, a coarser and slower request once backgrounded. Delivery to viewers should ride a WebSocket while someone is actively watching (near-instant fan-out), falling back to plain REST writes when it isn't worth holding a socket open.

// Interval/accuracy tuned by whether the sharing screen is visible
fun locationRequest(isForeground: Boolean): LocationRequest =
    LocationRequest.Builder(
        if (isForeground) Priority.PRIORITY_HIGH_ACCURACY else Priority.PRIORITY_BALANCED_POWER_ACCURACY,
        if (isForeground) 3_000L else 15_000L
    ).setMinUpdateDistanceMeters(5f).build()

// Foreground service keeps updates flowing once backgrounded (Android 10+)
override fun onStartCommand(intent: Intent?, flags: Int, id: Int): Int {
    startForeground(NOTIF_ID, sharingNotification()) // type="location" in manifest
    fusedClient.requestLocationUpdates(locationRequest(isForeground = appIsVisible()), callback, Looper.getMainLooper())
    return Service.START_STICKY
}

// WebSocket while live; REST is the fallback if the socket isn't connected
fun send(update: LocationUpdate) {
    val sent = webSocket?.send(json.encodeToString(update)) ?: false
    if (!sent) scope.launch(Dispatchers.IO) { api.postLocation(update) }
}

Battery vs accuracy: high accuracy + short interval only while the sharing screen is on-screen; balanced-power priority with a longer interval once backgrounded; setMinUpdateDistanceMeters skips redundant updates when stationary. Always stop updates when the share session ends or hits its TTL (e.g. "share for 1 hour").

Transport choice: WebSocket gives sub-second fan-out but costs a persistent connection — worth it while a viewer screen is actually open. REST polling is simpler and firewall-friendly but adds polling-interval latency; use it as the fallback path, not the primary one.

Background location (Android 10+): requesting location while backgrounded needs a foreground service with android:foregroundServiceType="location" and an immediate startForeground() call. ACCESS_BACKGROUND_LOCATION is a separate runtime permission that must be requested after foreground location — and only when the user does something that clearly needs it, per Play Store policy. Android 12+ also lets users grant only "approximate" location, so the feature must degrade gracefully rather than fail outright.

Design: Short-Form Video Feed

D7Design a short-form video feed for Android (TikTok/Reels style)Hard

Requirements: a vertically-swipeable feed of short videos with instant playback on swipe (no spinner), memory bounded regardless of feed length, playback that adapts to network conditions, and a prefetch strategy tied to scroll position.

Core idea: never create one ExoPlayer per feed item — hold a small fixed pool (2-4 instances) and reassign players as the user scrolls, releasing anything more than one page away. Combine that with eager prepare() of the next item or two so its manifest and first segments are already buffering by the time the user swipes to it.

// Small fixed pool — reassigned by position, not one player per item
class PlayerPool(context: Context, private val size: Int = 3) {
    private val pool = List(size) { ExoPlayer.Builder(context).build() }
    private val assigned = HashMap<Int, ExoPlayer>() // position -> player

    fun acquire(position: Int, item: MediaItem): ExoPlayer =
        assigned.getOrPut(position) {
            pool.first { it !in assigned.values }.apply { setMediaItem(item); prepare() }
        }

    // bound memory: drop players more than one page away from the visible one
    fun trimTo(visible: Int) = assigned.entries.removeAll { (pos, player) ->
        (pos - visible).let { kotlin.math.abs(it) > 1 }.also { farAway -> if (farAway) player.stop() }
    }
}

// ViewPager2 wiring: play current, pre-buffer next, trim the rest
override fun onPageSelected(position: Int) {
    pool.acquire(position, items[position].hlsMediaItem).playWhenReady = true
    items.getOrNull(position + 1)?.let { pool.acquire(position + 1, it.hlsMediaItem) } // prefetch, paused
    pool.trimTo(position)
}

Bounding memory: a fixed pool means memory is bounded no matter how long the feed gets — the tradeoff is pool size vs how far ahead you can pre-buffer, and real devices only have 4-8 concurrent hardware decoders anyway.

Prefetch strategy: prepare the next 1-2 items on onPageSelected so their manifest and first segments are buffered before the swipe lands; going further ahead wastes cellular data on clips the user may skip. Pair it with an instantly-shown poster frame so there's never a blank frame while the player attaches.

Adaptive bitrate: serve an HLS/DASH master manifest with multiple renditions; Media3's track selector + bandwidth estimator switches renditions mid-playback as network conditions change, and starting every clip on a lower rendition keeps first-frame time low.

Tradeoffs: a bigger pool smooths fast scrolling but holds more decoders and buffers at once; releasing a player mid-playback drops its buffer, so cache the last position per item so scrolling back doesn't restart from zero.
