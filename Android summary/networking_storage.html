Retrofit & OkHttp

Q1How does Retrofit work internally? What is the role of OkHttp?Hard

Retrofit is a type-safe HTTP client that converts your interface definitions into HTTP calls. It's a layer on top of OkHttp.

  • OkHttp: Raw HTTP client. Handles connections, TLS, HTTP/2, caching, interceptors.
  • Retrofit: Uses Java/Kotlin reflection + annotation processing to turn your interface methods into OkHttp Calls. Uses ConverterFactory (Gson/Moshi/Kotlinx) to serialize/deserialize.
// Full production setup
val okHttpClient = OkHttpClient.Builder()
    .connectTimeout(30, TimeUnit.SECONDS)
    .readTimeout(30, TimeUnit.SECONDS)
    .addInterceptor(HttpLoggingInterceptor().apply { level = HttpLoggingInterceptor.Level.BODY }) // debug only
    .addInterceptor { chain ->
        // Auth interceptor: add token to every request
        val request = chain.request().newBuilder()
            .addHeader("Authorization", "Bearer ${tokenProvider.getToken()}")
            .build()
        chain.proceed(request)
    }
    .addInterceptor(RetryInterceptor(maxRetries = 3))
    .cache(Cache(cacheDir, 50L * 1024 * 1024)) // 50MB HTTP cache
    .build()

val retrofit = Retrofit.Builder()
    .baseUrl("https://api.example.com/")
    .client(okHttpClient)
    .addConverterFactory(MoshiConverterFactory.create()) // or Gson
    .build()

// Suspend functions work natively with Retrofit 2.6+
interface UserApi {
    @GET("users/{id}")
    suspend fun getUser(@Path("id") id: String): Response<UserDto>

    @POST("users")
    suspend fun createUser(@Body user: CreateUserRequest): UserDto

    @GET("users")
    suspend fun searchUsers(@Query("q") query: String, @Query("page") page: Int): PaginatedResponse<UserDto>
}
Q2How do you handle API errors robustly? Sealed Result type pattern.Hard 
// Sealed Result type — wrap every network call
sealed class ApiResult<out T> {
    data class Success<T>(val data: T) : ApiResult<T>()
    data class Error(val code: Int, val message: String) : ApiResult<Nothing>()
    data class Exception(val e: Throwable) : ApiResult<Nothing>()
}

// Extension function to safely execute any Retrofit call
suspend fun <T> safeApiCall(call: suspend () -> Response<T>): ApiResult<T> {
    return try {
        val response = call()
        if (response.isSuccessful()) {
            ApiResult.Success(response.body()!!)
        } else {
            ApiResult.Error(response.code(), response.errorBody()?.string() ?: "Unknown")
        }
    } catch (e: IOException) {
        ApiResult.Exception(NetworkException("No network", e))
    } catch (e: Exception) {
        ApiResult.Exception(e)
    }
}

// Usage in Repository
suspend fun getUser(id: String) = safeApiCall { api.getUser(id) }

// Handling in ViewModel
when (val result = repo.getUser(id)) {
    is ApiResult.Success -> _uiState.update { it.copy(user = result.data) }
    is ApiResult.Error -> _uiState.update { it.copy(error = result.message) }
    is ApiResult.Exception -> handleException(result.e)
}

Room Database

Q3Explain Room's core components and how to handle schema migrationsHard 
// 1. Entity — maps to a database table
@Entity(tableName = "users", indices = [Index(value = ["email"], unique = true)])
data class UserEntity(
    @PrimaryKey val id: String,
    val name: String,
    val email: String,
    @ColumnInfo(name = "created_at") val createdAt: Long
)

// 2. DAO — Data Access Object
@Dao
interface UserDao {
    @Query("SELECT * FROM users WHERE id = :id")
    fun getUserById(id: String): Flow<UserEntity?> // Room emits on DB change

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertAll(users: List<UserEntity>)

    @Query("DELETE FROM users WHERE created_at < :cutoff")
    suspend fun deleteOlderThan(cutoff: Long)

    @Transaction // combines DAO calls in one transaction
    suspend fun refreshUsers(users: List<UserEntity>) {
        deleteAll(); insertAll(users)
    }
}

// 3. Database
@Database(entities = [UserEntity::class, PostEntity::class], version = 3)
@TypeConverters(Converters::class)
abstract class AppDatabase : RoomDatabase() {
    abstract fun userDao(): UserDao
}

// 4. Migration — schema changes between versions
val MIGRATION_2_3 = object : Migration(2, 3) {
    override fun migrate(database: SupportSQLiteDatabase) {
        database.execSQL("ALTER TABLE users ADD COLUMN bio TEXT")
    }
}

val db = Room.databaseBuilder(context, AppDatabase::class.java, "app.db")
    .addMigrations(MIGRATION_2_3)
    .fallbackToDestructiveMigration() // dev only — deletes data
    .build()
⚠ Room queries run on a background thread. If you use Flow, Room automatically emits on a background thread. Collect on main. Never expose Cursor directly to UI.

DataStore vs SharedPreferences

Q4Why replace SharedPreferences with DataStore? How does each work?Medium

SharedPreferences — Avoid

  • Synchronous on first load (ANR risk)
  • No type safety
  • apply() is async but errors silently
  • Not safe for complex objects

DataStore — Use This

  • Fully async (coroutines/Flow)
  • Type-safe (Proto DataStore)
  • Handles exceptions properly
  • No main-thread risk
// Preferences DataStore (key-value, like SharedPreferences but async)
val Context.dataStore by preferencesDataStore(name = "settings")

object PreferencesKeys {
    val IS_DARK_MODE = booleanPreferencesKey("dark_mode")
    val USER_ID = stringPreferencesKey("user_id")
}

// Read — returns Flow (reactive)
val isDarkMode: Flow<Boolean> = context.dataStore.data
    .map { prefs -> prefs[PreferencesKeys.IS_DARK_MODE] ?: false }

// Write — suspend function
suspend fun setDarkMode(enabled: Boolean) {
    context.dataStore.edit { prefs ->
        prefs[PreferencesKeys.IS_DARK_MODE] = enabled
    }
}

Paging 3

Q5How does Paging 3 work? PagingSource vs RemoteMediator?Hard 
// PagingSource: network ONLY pagination (no local DB)
class UserPagingSource(private val api: UserApi) : PagingSource<Int, User>() {
    override suspend fun load(params: LoadParams<Int>): LoadResult<Int, User> {
        val page = params.key ?: 1
        return try {
            val response = api.getUsers(page = page, pageSize = params.loadSize)
            LoadResult.Page(
                data = response.users,
                prevKey = if (page == 1) null else page - 1,
                nextKey = if (response.users.isEmpty()) null else page + 1
            )
        } catch (e: IOException) { LoadResult.Error(e) }
    }
    override fun getRefreshKey(state: PagingState<Int, User>) =
        state.anchorPosition?.let { state.closestPageToPosition(it)?.prevKey?.plus(1) }
}

// RemoteMediator: network + DB (offline-first pagination)
// DB is source of truth, network populates DB, Pager reads from DB
@OptIn(ExperimentalPagingApi::class)
class UserRemoteMediator(
    private val api: UserApi, private val db: AppDatabase
) : RemoteMediator<Int, User>() {
    override suspend fun load(loadType: LoadType, state: PagingState<Int, User>): MediatorResult {
        val page = when (loadType) {
            LoadType.REFRESH -> 1
            LoadType.PREPEND -> return MediatorResult.Success(endOfPaginationReached = true)
            LoadType.APPEND -> db.remoteKeyDao().getNextPage() ?: return MediatorResult.Success(true)
        }
        val users = api.getUsers(page)
        db.withTransaction {
            if (loadType == LoadType.REFRESH) db.userDao().clearAll()
            db.userDao().insertAll(users)
            db.remoteKeyDao().insert(RemoteKey(nextPage = page + 1))
        }
        return MediatorResult.Success(endOfPaginationReached = users.isEmpty())
    }
}

// In ViewModel
val users: Flow<PagingData<User>> = Pager(
    config = PagingConfig(pageSize = 20, prefetchDistance = 5),
    remoteMediator = UserRemoteMediator(api, db),
    pagingSourceFactory = { db.userDao().pagingSource() }
).flow.cachedIn(viewModelScope)

Advanced Networking & Data Consistency

Q6Application vs network interceptors in OkHttp — how does the interceptor chain actually execute?Hard

OkHttp has two interceptor registration points and mixing them up is a classic interview trip-wire.

Application interceptor — addInterceptor()

  • Registered outside the core OkHttp engine, runs exactly once per logical call — never re-invoked for redirects or retries
  • Sees the request as your code wrote it, and the response after redirects/retries/cache have already been resolved
  • Can short-circuit entirely (return a response without calling chain.proceed()) — e.g. serve from an in-memory cache
  • Good for: auth headers, high-level logging, business-level retry logic

Network interceptor — addNetworkInterceptor()

  • Sits right next to the socket, only invoked when a request actually hits the network — skipped entirely on a cache hit
  • Can run multiple times for one logical call if OkHttp follows a redirect internally
  • Sees the literal bytes on the wire — compressed body, real Content-Length, intermediate redirect responses
  • Good for: gzip/compression handling, caching that must see the true network response

Ordering rule: interceptors execute in the order you call addInterceptor()/addNetworkInterceptor(). On the way down, application interceptors run first (in add order), then OkHttp's internal RetryAndFollowUpInterceptor → BridgeInterceptor → CacheInterceptor → ConnectInterceptor, then your network interceptors (in add order), then finally CallServerInterceptor which writes to the socket. The response then unwinds back up through every interceptor in reverse, so each one gets a chance to inspect/transform the response too.

// Worked example: refresh an expired auth token transparently, retry once
class AuthRefreshInterceptor(private val tokenProvider: TokenProvider) : Interceptor {
    private val refreshLock = Any() // only one refresh in flight at a time (avoid a stampede)

    override fun intercept(chain: Interceptor.Chain): Response {
        val request = chain.request().newBuilder()
            .addHeader("Authorization", "Bearer ${tokenProvider.currentToken}").build()
        val response = chain.proceed(request)
        if (response.code != 401) return response

        synchronized(refreshLock) {
            response.close()
            val newToken = runBlocking { tokenProvider.refreshBlocking() } // interceptors can't suspend
                ?: return response // refresh failed → propagate the 401, caller signs the user out
            val retried = request.newBuilder().header("Authorization", "Bearer $newToken").build()
            return chain.proceed(retried)
        }
    }
}
⚠ Interceptors are synchronous, blocking code — no suspend allowed inside intercept(). For a token refresh that must call a suspend API, either bridge with runBlocking (as above, on a background OkHttp dispatcher thread — safe) or use an Authenticator (client.authenticator(...)), which OkHttp calls specifically on a 401/407 and is designed for exactly this retry-with-new-credentials flow.
Q7What is certificate pinning and how do you configure it with network security config vs OkHttp?Medium

Certificate pinning hard-codes which certificate (or public key) the app will trust for a given host, on top of normal CA validation. It defends against a compromised or coerced Certificate Authority, a rogue corporate MITM proxy, or a malicious Wi-Fi hotspot installing a trusted root — all cases where the TLS handshake looks perfectly valid to the OS but the certificate wasn't actually issued to your real backend.

1. Network Security Config (declarative, OS-level)

An XML resource referenced from the manifest. Applies to every HTTP client in the app — HttpsURLConnection, WebView, and OkHttp (if it defers to platform trust).

<!-- res/xml/network_security_config.xml -->
<network-security-config>
    <domain-config>
        <domain includeSubdomains="true">api.example.com</domain>
        <pin-set expiration="2027-01-31">
            <pin digest="SHA-256">base64LeafOrIntermediatePin==</pin>
            <pin digest="SHA-256">base64BackupPin==</pin>
        </pin-set>
    </domain-config>
</network-security-config>

<!-- AndroidManifest.xml -->
<application android:networkSecurityConfig="@xml/network_security_config" ... >

2. OkHttp CertificatePinner (code-level)

Only affects requests made through that specific OkHttpClient instance — doesn't protect WebView or other clients, but easier to change per build variant/flavor.

val pinner = CertificatePinner.Builder()
    .add("api.example.com", "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
    .add("api.example.com", "sha256/BBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB=") // backup pin
    .build()

val client = OkHttpClient.Builder()
    .certificatePinner(pinner)
    .build()
⚠ Operational risk — "bricking" the app: a pin is tied to a specific public key. If the backend rotates its TLS certificate (renewal, CA migration, incident response) to a new key and the shipped app doesn't already contain a matching pin, every pinned request fails with an SSLPeerUnverifiedException — and since this is baked into an already-installed APK, you can't fix it without pushing an update, which itself takes time to roll out. Mitigations: always ship a backup pin for a not-yet-active key (e.g. pin the intermediate/root CA instead of the leaf, since leaf certs rotate far more often), set a sane pin-set expiration so an expired config fails open to normal validation rather than hard-locking, and keep certificate rotation calendars synced between backend and mobile release schedules.

Room — Relations & Type Conversion

Q8How do @Relation and @Embedded model nested objects in Room? How do TypeConverters store custom types?Medium

Room tables can only hold primitive-ish columns, but your domain model is rarely flat. Three tools bridge that gap, each solving a different shape of "nesting":

  • @Embedded — flattens a value object's fields directly into the same table's columns, no separate table, no join. Good for things like an Address that always belongs 1:1 to its parent row.
  • @Relation — models a real one-to-many (or many-to-many) association across separate tables, joined at query time via extra SELECTs, not stored denormalized.
  • @TypeConverter — serializes a single column's value to/from a SQLite-storable primitive (String/Long/etc.), for simple scalar-ish custom types.
@Entity data class UserEntity(@PrimaryKey val id: String,
    @Embedded(prefix = "addr_") val address: Address) // flattened into addr_street, addr_city columns

// query-result shape only — NOT an @Entity, joins posts by foreign key at query time
data class UserWithPosts(@Embedded val user: UserEntity,
    @Relation(parentColumn = "id", entityColumn = "userId") val posts: List<PostEntity>)

// TypeConverter: teach Room to store one non-primitive column as a primitive
class Converters {
    @TypeConverter fun fromDate(d: Date?): Long? = d?.time // epoch millis — sortable, indexable
    @TypeConverter fun toDate(ms: Long?): Date? = ms?.let { Date(it) }
}
⚠ Converters run synchronously, inline, per row — keep them cheap. If the "nested" data is queryable domain data, not an opaque blob, prefer a real @Relation table: a converted column can't be indexed or filtered with SQL WHERE.

Single Source of Truth & Background Sync

Q9How do you apply the single-source-of-truth pattern to the networking/storage layer specifically?Hard

The core rule: the UI never observes network data directly — it only ever observes Room. A refresh() function is the only thing allowed to touch the network, and its job is strictly to write the result into Room, not to hand data back to the caller. Room's Flow query — already being collected by the UI — automatically re-emits the moment that write lands, because Room's InvalidationTracker notifies every active Flow observer on any table it touches, regardless of what triggered the write.

class UserRepository(private val api: UserApi, private val dao: UserDao) {

    // The ONLY thing the UI ever collects. Doesn't care who last wrote to Room.
    fun observeUser(id: String): Flow<User> =
        dao.getUserById(id).filterNotNull().map { it.toDomain() }

    // Side-effect only — writes to Room, returns Unit (or Result for surfacing errors).
    // Notice it never returns a User: handing data back would create a second,
    // competing path for the UI to receive state from.
    suspend fun refresh(id: String): Result<Unit> = runCatching {
        val dto = api.getUser(id)
        dao.upsert(dto.toEntity())
    }
}

// ViewModel — one state stream, fed by Room, triggered from anywhere
val user = repo.observeUser(id)
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), null)

fun onPullToRefresh() = viewModelScope.launch {
    repo.refresh(id).onFailure { _errorEvents.emit(it.toUiError()) }
    // no need to touch `user` here at all — Room's Flow already updated it
}
✓ Because writes and reads are fully decoupled, it doesn't matter whether the write came from pull-to-refresh, a WorkManager periodic sync, or another screen editing the same row — every collector of observeUser() converges on the same, always-consistent state with zero extra plumbing.
Q10How do you make background sync reliable — combining Retrofit with WorkManager's retry/backoff?Medium

A CoroutineWorker that makes the Retrofit call and lets WorkManager own the retry policy is far more reliable than a hand-rolled in-memory retry loop, for one key reason: an in-memory loop (a while + delay() inside a ViewModel or Service scope) lives and dies with the process. If the OS kills the app under memory pressure, the user force-stops it, or the device reboots mid-backoff, all retry state — attempt count, next delay, the pending call itself — evaporates. WorkManager persists the work request (and its retry count) in its own Room-backed database, so it survives process death and even a reboot, and resumes exactly where it left off via the system's job scheduler.

class SyncUsersWorker(
    context: Context, params: WorkerParameters,
    private val api: UserApi, private val dao: UserDao
) : CoroutineWorker(context, params) {

    override suspend fun doWork(): Result = try {
        val remote = api.getUsers()
        dao.insertAll(remote.map { it.toEntity() })
        Result.success()
    } catch (e: HttpException) {
        if (e.code() in 500..599) Result.retry()   // transient server error → let WorkManager back off and retry
        else Result.failure()                        // 4xx → permanent, retrying won't help
    } catch (e: IOException) {
        Result.retry()                                // no network / timeout → transient
    }
}

val syncRequest = OneTimeWorkRequestBuilder<SyncUsersWorker>()
    .setConstraints(Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED).build())
    .setBackoffCriteria(
        BackoffPolicy.EXPONENTIAL,
        WorkRequest.MIN_BACKOFF_MILLIS, TimeUnit.MILLISECONDS // starts ~30s, doubles each attempt, caps at 5h
    )
    .build()

WorkManager.getInstance(context)
    .enqueueUniqueWork("sync_users", ExistingWorkPolicy.KEEP, syncRequest)
Note the same single-source-of-truth discipline as Q9: doWork() writes straight to Room and returns only a Result (success/retry/failure) to WorkManager — it never tries to push data to a ViewModel directly, since the Worker may run long after the screen that requested it has been destroyed.
